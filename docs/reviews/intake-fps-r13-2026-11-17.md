# INTAKE-FPS-R13 verification

The user reported that an iPhone 15 Pro video shown as roughly 170fps was rejected as 60fps after being saved to Files. The reported file is on Kim Min's device and was unavailable for this audit. The defect below is reproduced independently. It is a possible cause of the report, and the report's exact file remains unverified.

## Defect and correction

`readStts` selected the single stts entry with the largest sample count as the most common frame interval. A time-to-sample entry describes consecutive samples with one duration. The same duration may occur in many separated entries. Selecting one run loses their combined count.

The reader now groups all entries by duration and adds their sample counts before selecting the representative interval. The final sample exception, average rate, variability tolerance, 119.82fps threshold, MOV/MP4 parsing, edit-list handling and original-byte upload pipeline retain their existing behavior. The browser selection and server verification both use this reader.

Primary format reference — [Apple time-to-sample table](https://developer.apple.com/documentation/quicktime-file-format/time-to-sample_atom/time-to-sample_table.md).

## Reproduction

A 60,000-unit timebase contains 100 consecutive samples of duration 1,000, followed by 630 samples alternating duration 249 and 251. Its 730 samples span 4.2916667 seconds, averaging **170.097087fps**.

The previous reader selected the 100-sample continuous 60fps run over every one-sample high-rate entry and rejected the file. The corrected reader totals the repeated high-rate intervals and accepts it. The displayed average remains approximately 170fps. The representative interval measures 240.963855fps because the timebase uses integer intervals.

A playable 32×32 H.264 MOV was also generated locally with these packet times. Independent libav demuxing and decoding found 730 frames, the same 170.097087fps average, and duration counts 249×315, 251×315, 1,000×100. The corrected application reader matched these facts and accepted the file. This is a controlled test movie, not the reported iPhone original.

## Regression coverage

- The new regression failed against the previous implementation and passed after the correction.
- Every integer constant rate from 120 through 240fps is parsed without being converted to 60fps.
- Partitioning the same sample durations across different stts rows produces the same rate and variability decision.
- 119.88fps, dropped-frame tolerance and retimed high-rate input remain covered.
- Ordinary 30/60fps and a mixed-rate file averaging below 120fps remain rejected.
- The browser's actual `inspectPick` accepts the reproduced high-rate fixture.
- The isolated PGlite server verification accepts it, saves its average and representative rate, and matches size and SHA-256. Production DB and stored objects were not used.
