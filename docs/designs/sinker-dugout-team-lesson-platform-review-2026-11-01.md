# 싱커 × 덕아웃 통합 구현 검토 — 2026-11-01

검토 기준: `sinker-dugout-team-lesson-platform-claude-prompt.md` R01~R14, 한국어 계획, 현재 소스. 기준 HEAD `f0bcf076bf0f57fa76db7cb7243b4b938c2328c8`(a98062a8, bb51f499, f0bcf076). 운영 DB와 실제 회원 데이터는 읽거나 수정하지 않았다.

## 결론과 검토 범위

**전체 설계의 완성 구현은 아니다.** Claude 메인도 결과를 ‘0단계 + 1단계 첫 묶음 + DB 변경 없는 2단계 일부’로 보고했다. 사용자가 메인에서 DB 변경 없는 범위를 요청한 사실을 확인했다. 따라서 미구현 기능을 숨겼다고 해석하지 않는다. 다만 그 범위의 코드에도 수정해야 할 결함이 있다.

추가된 것은 조직 capability 기본 규칙, 앱/웹 동작의 capability 검사, 덕아웃 초대 코드 가입 화면, 동일 예약 완료 중복 차감 방지, 예약 취소 시 일정 보존이다. 보호자 관계·세부 위임 저장·관리 화면 이전·팀방·일정 반복·예약 변경·안정적 갱신은 전체 완료 조건에 도달하지 않았다.

검토 도중 다른 세션이 홈·투구·베타 코드를 수정하고 있었다. 그 변경은 보존했다. 아래 권한·예약 결함은 위 HEAD의 관련 파일에서 확인했으며, 실행한 release 시험 수치는 검토 당시 작업 트리 기준이다. 앱 UI 로그인 검증, 실제 두 기기 동기화, 실제 PostgreSQL 동시성 검증은 하지 않았다.

## 발견 사항 — 먼저 수정할 순서

### F01 · P1 · 완료와 취소가 경합하면 이용권은 차감됐는데 예약은 취소가 된다

근거: `app/actions/lessons.ts:367`의 `cancelBooking`, 특히 374행의 트랜잭션 밖 상태 검사와 381행의 id만 조건으로 한 update.

재현 순서: 취소 요청이 CONFIRMED를 읽음 → 다른 완료 요청이 DONE과 이용권 차감을 커밋 → 대기하던 취소 요청이 CANCELED를 덮어씀. 실제 cancelBooking 함수를 TypeScript 변환 후 외부 모듈/Prisma를 모의로 대체해 실행했다. 두 트랜잭션 사이 순서를 주입했을 때 결과는 `{status:"CANCELED", used:1, event:"canceled"}`다. 실제 DB 경합 시험이 아니라 **실제 액션의 제어 흐름을 실행한 결정적 모의 재현**이다.

수정: 취소도 트랜잭션 안에서 userId와 허용된 이전 상태를 포함하는 조건부 갱신으로 선점한다. 성공한 요청만 연결 일정을 변경한다. 완료/취소/확정/거절 모두 같은 전이 규칙을 사용한다. 완료 후 취소는 명시적 정정·복원 업무로만 처리하고 예약 상태 변경만으로 차감 이력을 남겨 두지 않는다. 승인된 취소의 정책과 원장 복원은 별도 기록으로 한 번만 실행한다.

### F02 · P1 · 같은 요청을 동시에 확정하면 일정이 두 개 생긴다

근거: `app/actions/lessons.ts:161`의 `confirmBooking`. REQUESTED 검사가 트랜잭션 밖이며 트랜잭션은 매번 `orgEvent.create` 후 조건 없는 예약 update를 한다. 거절도 동일한 사전 검사/무조건 update 구조다.

실제 confirmBooking과 실제 canConfirm 규칙을 모의 환경에서 실행했다. 두 호출이 REQUESTED를 함께 읽도록 맞추면 두 일정 e1/e2가 생성되고 예약은 마지막 e2만 가리킨다. 원자적 슬롯 용량 확인도 없다. 서로 다른 예약의 같은 시간 충돌 문제는 3단계 미구현 항목이며, 동일 예약의 중복 확정은 현재 코드에서 먼저 고칠 수 있는 결함이다.

수정: 먼저 같은 예약의 전이를 조건부로 선점하고 한 요청만 회원/일정을 연결한다. 다른 호출은 이미 확정/충돌 결과를 반환한다. 알림도 실제 성공 전이에 대해서만 보낸다. 추가로 코치·시간·시설 용량에 대한 DB 수준 직렬화/제약을 검증해 서로 다른 예약의 초과 확정을 막는다. 취소/거절 후 늦게 도착한 확정도 다시 살리지 못하게 한다.

### F03 · P1 · 일반 계정을 조직 담당자로 쓰는 실제 진입 흐름은 아직 막혀 있다

근거 세 곳:
- `lib/org/join.ts:32`: STAFF 코드는 accountType MASTER가 아니면 거절한다. 34행은 MASTER의 선수 참여도 거절한다.
- `app/actions/app-org.ts:67`: loadMySpaces의 코치 조직 조회를 여전히 isMasterUser로 제한한다.
- `lib/dal.ts:152`, `app/(master)/layout.tsx:23`, 웹 액션들: requireMaster가 일반 계정을 /today로 보낸다.

coachOrg만 수정했기 때문에 이미 존재하는 일반 STAFF의 앱 API는 열릴 수 있지만, 실제 초대 수락·공간 선택·덕아웃 웹 운영은 연결되지 않는다. HANDOFF의 ‘일반 계정이 스태프 초대로 들어오면 코치 화면이 열린다’는 설명은 이 범위에서 성립하지 않는다.

수정: 조직 업무의 진입과 데이터 접근은 조직 관계와 capability로 판단한다. 개인 운동 사용 여부는 별도로 유지한다. requireMaster를 전역으로 느슨하게 바꾸지 말고 조직 관리용 입구를 만들고 모든 조회/동작을 같은 정책으로 묶는다. 세부 위임 표가 없을 때 일반 부모를 STAFF로 만들어 총무를 흉내 내면 훈련 권한까지 주므로 금지한다. 기존 코치의 STAFF 권한과 새 운영 담당의 최소 권한을 구분한다.

### F04 · P2 · canGrant는 소유하지 않은 권한과 다른 대상 범위도 줄 수 있다

근거: `lib/org/capabilities.ts:80`. permission.manage 유무와 organization이라는 문자열만 비교한다. 실제 대상 선수/자녀/그룹 ID도 OrgGrant에 없다.

실제 순수 함수 재현: PLAYER에게 permission.manage(self)만 주어도 org.manage(explicit_group) 위임을 true로 반환한다. 다만 현재 grants는 저장·로딩되지 않으므로 **지금 실행 가능한 위임 API 취약점이라고 보고하지 않는다.** 저장 기능을 연결하기 전 수정해야 할 규칙 결함이다.

수정: 권한 위임 가능 목록과 위임자의 실제 capability, 대상 집합의 포함 관계를 모두 확인한다. self/linked_children/assigned_players/explicit_group을 크기 순서의 enum처럼 비교하지 않는다. 권한별 범위와 구체 대상 ID, 역할 기본값 축소·철회 의미, 여러 grant 합성 규칙, 감사 이력, 마지막 소유자 보호를 확정한다. 서비스 전역 역할과 조직 소유권은 일반 capability 부여와 분리한다.

### F05 · P2 · 액션 이름에 capability를 붙였지만 조회 데이터와 대상 범위는 아직 분리되지 않았다

근거: `lib/org/app-access.ts:28`와 `lib/org/access.ts`는 `hasCapability({role}, cap)`만 호출한다. capabilityScope는 서버 조회에서 사용하지 않는다. `loadOrgToday/loadOrgMembers`는 roster.read로 팔 상태까지 반환하고, `app/actions/app-team.ts:169` loadEventDetail은 schedule.read로 개별 수행 값·정정 요청·체크인 관련 정보를 반환한다. 웹 회원 상세도 requireCurrentOrg 뒤 여러 데이터 종류를 직접 읽는다.

현재 STAFF 기본 묶음이 넓기 때문에 ‘현행 일정 전용 총무가 이미 다른 선수 기록을 읽었다’고 단정하지 않는다. 하지만 grants를 읽기만 붙이면 최소 권한이 무너진다.

수정: 일정/명단/훈련/몸 상태/영상/회계 DTO를 분리한다. 기존 복합 응답을 유지해야 하면 서버에서 필드별 검사·삭제와 대상 필터를 한다. 공통 authorization 결과에 조직·허용 대상·공유 범위를 포함하고 쿼리 단계부터 적용한다. 버튼 숨기기만으로 처리하지 않는다. null membership을 STAFF로 간주하는 fallback도 제거하고 거절한다.

### F06 · P2 · 예약 요청만으로 개인 투구 기록 총건수가 노출된다

근거: `lib/market/lesson-load.ts:489` loadOrgBookings는 user._count.pitchLogs를 동의/기간/조직 범위 없이 읽고 536행에서 records로 반환한다. `app/(master)/manage/bookings/page.tsx`가 이를 ‘투구 기록 N건’으로 표시한다. 기존 코드의 잔존 문제이며 새 커밋이 만든 회귀는 아니다.

예약 요청자는 아직 회원/공유 동의가 없을 수 있다. 단순 숫자도 개인 운동 메타데이터이므로 ‘예약은 공유 동의가 아니다’라는 계약에 어긋난다.

수정: 예약 운영에 불필요한 전체 개인 기록 건수를 제거한다. 꼭 필요하면 별도 training.read와 유효한 해당 조직 공유 동의가 모두 있을 때 허용 기간/범위만 집계한다. 비공개를 0건으로 표현하지 않는다. 다른 화면/RPC/내보내기의 같은 누출도 점검한다.

### F07 · P2 · 이용권 없는 완료의 결과를 호출자가 버린다

근거: `lib/org/booking-complete.ts`는 `{done:true,passId:null}`을 반환하지만 `app/actions/lessons.ts:291`은 결과를 사용하지 않는다. `components/master/booking-actions.tsx`는 동일한 성공 문구만 표시한다. 자기 시험에는 ‘화면이 알린다’고 쓰였지만 현재 연결은 없다.

수정: 완료/이미 완료/유효 이용권 없음/권한 없음/상태 충돌/저장 실패의 구조화된 결과를 반환하고 UI에 연결한다. 이용권이 없어도 실시 완료를 허용할지는 정책으로 명시한다. 허용한다면 미차감 상태를 명확히 기록·표시하고 재시도로 과거 완료를 자동 차감하지 않는다. 원장과 정정 규칙은 후속 DB 단계로 관리한다.

### F08 · P2 · 운동-팀 일정 연결이 휘발성 복귀 정보와 일회성 호출에 의존한다

근거: `native/src/org/space-store.ts:123` orgReturn은 메모리에만 있고 setSpace는 102행에서 이를 비운다. consumeOrgReturn은 130행에서 먼저 비운 뒤 linkMyWork를 호출하고 137행에서 오류를 무시한다.

확인된 것은 연결 정보의 미저장과 실패 무시 경로다. 실제 기기에서 모든 공간 전환 경로가 운동 중 허용되는지는 이번에 실행 검증하지 않았다. 따라서 ‘모든 전환에서 반드시 기록이 유실된다’고 표현하지 않는다. 재시작/오프라인 후 연결 복구는 보장되지 않는 구조다.

수정: 활성 운동 원본과 함께 account/athlete/org/member/event/assignment 식별자를 보존한다. 화면 복귀 경로와 기록 귀속을 분리하고, 완료 저장·조직 연결을 멱등 키로 재시도한다. 서버 반영 전에 연결 대기 상태를 지우지 않는다. 권한 회수 시 개인 운동은 보존하고 조직 연결만 거절한다. 날짜+시각만으로 광범위한 개인 운동을 붙이지 않도록 명확한 원본 ID를 사용한다.

2. F04/F05의 정책과 서버 대상 필터를 설계하고, 준비되지 않은 세부 위임은 연결하지 않는다. DB 적용 없이도 정책·DTO·검사를 준비한다.
3. F08 활성 운동 연결의 내구성을 보완하고 오류·오프라인 표시를 추가한다.
4. 공유 DB 조율과 백업 뒤 보호자/위임/감사 원장부터 단계적으로 적용한다. 각 단계는 회원 등록→싱커 운동→덕아웃 조회까지 연결한 검증이 필요하다.
5. 예약 변경·용량·이용권 원장→조직 대화→일정/공지 편의→실기기/구버전/동기화 실측 순서로 전체 R01~R14를 끝낸다. 베타 해제와 운영 배포는 별도 결정이다.
