# 외부 투구 영상 접수(초대 링크) — 구현 결정

요구 원문은 사용자가 준 'guided, invitation-based original-video submission flow' 명세다. 이 문서는 그 명세를 이 저장소에 맞춘 결정이다.
비밀 값과 실제 초대 주소는 여기에 적지 않는다.

## 조사로 확인한 사실(2026-11-06)
- 버킷 `pitch-videos` 는 비공개 · 파일 한도 500MB(524,288,000) · MIME `video/*, image/jpeg, application/json`. 1GiB 를 못 받는다.
- 기존 올리기는 로그인 필요 · 파일당 150MB · 서명 PUT(재개 불가). 기존 지문(`fileFingerprint`)은 크기 + 앞뒤 1MB 라 전체 해시가 아니다.
- 3D 샘플은 DB 없이 `{userId}/pitch-lab/{id}/` 폴더(job.json 등). 소유권은 사용자 폴더 기준. 일반/마커 공유 규칙이 있다.
- GPU 호출(`startGpuJob`)은 서명 주소만 받으므로 저장 위치에 묶이지 않는다.
- `ANALYSIS_CONSENT` 는 PENDING 다섯 건으로 확정 전이다(받는 곳 연락처 · 보유 기간 · 처리 나라 · 법적 근거 · 만 14세 미만 절차).
- 개발 DB = 운영 DB. 이 맥에 postgres 는 없고 PGlite 시험 틀이 있다.

## 결정
1. **주소**: 공개 화면 `/submit`, 초대 토큰은 주소 조각(`/submit#<token>`). 조각은 서버 · 로그 · 링크 미리보기 · Referer 로 가지 않는다. API 는 `Authorization: Intake <token>` 머리로만 받는다. GET 화면은 아무 상태도 바꾸지 않는다.
2. **토큰**: 32바이트 난수 base64url, DB 에는 SHA-256 만. 이름을 주소에 넣지 않는다. 초대는 관리자 세션이 아니며 자기 접수 하나에만 쓴다.
3. **저장**: 새 비공개 버킷 `external-intake`(한도 1GiB, MIME video/* · application/octet-stream · application/json). 경로는 서버가 정한다 — `sub/<submissionId>/<assetId>/original`, 결과는 `sub/<submissionId>/runs/<runId>/…`. 이름 · 확장자 넣지 않음. 파일은 덮어쓰지 않는다(upsert 끔, 자산마다 새 경로). 버킷은 `scripts/intake-setup-bucket.mjs` 로 만들고 사람 허가 뒤에만 돌린다.
4. **전송**: Supabase TUS(`/storage/v1/upload/resumable/sign` + `x-signature`, 서버가 그 경로 하나에 발급한 서명 토큰). 6MB 조각, 순서대로 하나씩, tus-js-client. 영상 몸통은 Vercel 을 지나지 않는다. 정확한 프로토콜은 공식 문서로 확인한다.
5. **무결성**: 브라우저가 올리기 전 `file.slice` 조각으로 전체 SHA-256 을 점진 계산(메모리 한정) → 서버가 올라간 객체를 스트리밍으로 다시 계산해 크기 · 해시를 견준다. 같으면 '선택한 파일 그대로 전송됨'. 재선택은 크기 + 해시가 같아야 이어간다. 이름 · MIME · 크기 신고는 믿지 않고 서버가 파일 머리(ftyp/moov)를 읽는다.
6. **상태**: 파일(자산) · 접수 · 분석 · 공개를 따로 둔다. 전이는 `lib/intake/state.ts` 순수 함수 한 곳. 접수에 `version` 낙관 잠금, 자산은 `version` 불변. 완료(finalize)는 멱등 — 같은 요청 키 재호출은 같은 영수증을 돌려준다. 완료 때 짝을 `IntakeRevision` 으로 얼린다.
7. **지속 작업**: 표 `IntakeJob`(verify_asset · register_revision · poll_analysis · cleanup_uploads · purge_originals). finalize 뒤 `after()` 로 즉시 시도, `/api/cron/intake`(CRON_SECRET, 5분) 가 임대(lease) · 재시도로 이어 간다. 화면을 닫아도 돈다.
8. **분석**: 기존 폴더 · 소유권은 넓히지 않고 어댑터 `lib/intake/analysis.ts` 가 서명 주소를 `startGpuJob` 에 넘기고 결과를 intake 버킷에 받는다. 검증된 접수는 자동 등록(분석 가능 상태)되지만 GPU 는 관리자가 눌러야 돈다. 같은 두 원본 · 같은 엔진 · 같은 손의 중복 실행은 `IntakeAnalysisRun.dedupeKey` 유일 제약으로 막는다(실패하면 비워 재시도 허용).
9. **공개**: `IntakePublication` 이 특정 성공 실행에 묶인다. 재분석은 공개를 안 바꾼다. 공개 API 는 허용 칸만 고른 사본을 준다.
10. **동의**: `lib/intake/consent.ts` 판 문서 — 제출 · 처리(필수), 분석 서버 국외 이전(필수, `ANALYSIS_CONSENT` 사실만 인용하고 빈 칸은 '확인 중'으로 표시), 모델 개발 이용(선택 · 기본 꺼짐). 동의 줄은 판 · 본문 해시 · 시각 · 대리 여부와 함께 남긴다. 관리자 동의로 대신하지 않는다. 법정대리인 절차가 없으므로 **만 14세 미만 선수는 접수를 막는다**. `ANALYSIS_CONSENT` 가 확정 전이면 GPU 실행을 막고 `INTAKE_ALLOW_DRAFT_ANALYSIS=1` 일 때만 관리자 확인 뒤 허용한다.
11. **권한**: `lib/permissions.ts` 에 'intake'(대표관리자). 접수는 만든 사람에 묶이지 않는다. 읽음 상태는 관리자별 표.
12. **DB**: 새 표만 더한다(기존 표 칸 변경 없음) — 마이그레이션 파일은 만들되 공유 DB 적용은 백업 · 상대방 알림 · 사용자 허가 뒤. 시험은 PGlite.
13. **표시**: 시간대 Asia/Seoul. 접수일은 서버 시각, 촬영일은 파일 머리에서 읽은 값이며 출처를 함께 둔다.

## 구현하며 고친 결정(2026-11-06)
- **결정 4 보강**: 위 표대로. `apikey` 에 공개 키가 필요해 환경변수 `SUPABASE_PUBLISHABLE_KEY` 를 더했다(지금 `.env` 에 없다). 호스팅에서 꼭 필요한지는 실제 버킷으로 봐야 한다. `uploadDataDuringCreation` 은 문서 예시(true)와 달리 끈다 — 주소를 먼저 남긴 뒤 바이트를 보내야 첫 조각에서 끊겨도 이어 갈 수 있다.
- **결정 7 고침**: 검증 일감은 완료 뒤가 아니라 **전송 확인(confirmUpload) 때** 건다. 전송 단계에서 '확인하고 있어요'를 보일 수 있고, 완료는 '둘 다 도착'까지만 본다. 영수증은 완료가 주고, '선택한 파일 그대로 전송됨'은 서버 해시가 맞은 뒤에만 나온다.
- **결정 10 고침**: 명세의 '동의 전에는 바이트를 안 보낸다'를 지키려고 동의를 완료 때가 아니라 **전송 토큰 전에** 남긴다(recordConsents, issueUploadToken 이 확인). 완료도 다시 본다.
- **결정 10 보강**: 생년월일을 받지 않고 '만 14세 이상인가'만 받는다(`athleteAgeBand`) — 필요한 것만 받기. 대신 본인 신고라 증명이 아니다.
- **자산 판 번호**: 두 기기가 옆 · 뒤를 따로 올려도 안 부딪히게 칸마다 `expectedAssetId` 로 본다. 접수 `version` 은 고른 영상 · 글이 바뀔 때만 오르고 전송 진행은 안 올린다.
- **확인 기간**: 올리기 기간이 끝나도 `confirmUpload` 는 된다(끝난 전송의 바이트가 고아가 되지 않게). 새 토큰 · 완료는 막힌다.

- **서버 안 GET 은 늘 signal(격리 브라우저 시험으로 찾음)**: Next 의 fetch(`dedupe-fetch`)는 signal 없는 GET 응답을 둘로 갈라 한 갈래를 쥔다. `res.body.cancel()` 이 가비지 수집까지 안 끝나 전송 확인이 119초 멈췄고, 전체 해시 때는 안 읽는 갈래에 파일이 쌓일 수 있었다. `storage-core.ts` 의 읽기는 signal · `cache: 'no-store'` 를 준다. 가짜 fetch 로는 안 보여서 `intake:transfer-test` 가 Next 의 그 함수를 끼워 본다.

## 분석 · 공개 구현(2026-11-06)
- **파일**: `lib/intake/analysis.ts`(어댑터 · 상태 묻기) · `publication.ts`(공개 · 내리기 · 공개 경계) · `public-result.ts`(허용 칸, 브라우저도 부름) · `job-handlers.ts`(일감 넷 · 크론) · `app/api/cron/intake` · `app/api/intake/public/result` · `components/intake/result-view.tsx`. 시험 `npm run intake:analysis-test`.
- **입력 하나**: 중복 키는 옆 원본 + 뒤 원본 + 엔진 판 + 던지는 손이다. 손은 결과를 바꾸므로 입력에 넣었다. 판 번호는 안 넣었다 — 글 칸만 고쳐도 새 판이 생기는데 바이트는 같아서, 넣으면 같은 입력에 돈이 또 든다. 관리자가 정한 손은 접수 칸에만 쓰고 얼린 판은 그대로 둔다(`setAnalysisHand`).
- **글만 고친 새 판**: 같은 입력(두 원본 + 손)의 성공 실행을 그대로 잇는다. 분석 상태는 '분석 완료'로 이어 가고(`carryAnalysisForward` 를 등록 일감이 부른다. 관리자의 분석 단추 · 공개도 잇는다) 그 실행을 그대로 공개할 수 있다. 고치는 사이 끝난 실행의 성공도 받는다. 영상이나 손을 바꾼 고침은 다른 입력이라, 옛 실행은 지금 것으로 안 보이고 `allowOlderRevision` 없이는 공개되지 않는다(`runMatchesCurrent`).
- **도는 동안**: 같은 두 원본에 엔진이 달라도 하나만 돈다(`analysis_busy`). 영상을 바꾼 새 판은 따로 돌릴 수 있다.
- **엔진 판을 모를 때**: `/engine` 이 답을 안 주면 새 실행을 안 만들고 다시 시도하라고 알린다(`analysis_engine_unknown`). 시간 초과 하나로 키가 달라져 같은 입력이 또 돌면 안 돼서다.
- **걸기 순서와 비용 위험**: 실행 줄 · 상태 일감을 먼저 남기고 GPU 를 건다. 걸기의 답을 못 받으면(시간 초과 · 망 끊김 · 5xx · 서버 함수가 죽음) 서버는 이미 돌고 있을 수 있어 '안 돌았다'로 치지 않는다. 실패로 닫지 않고 키를 쥔 채 30분(대기 15분 + GPU 제한 15분, `START_UNKNOWN_WINDOW_MS`) 동안 약속한 결과 자리를 찾는다. 이 실행 번호의 결과가 나타나면 받고, 그동안 다시 분석은 막힌다. 창이 지나도 없으면 까닭을 적어 실패로 닫고 다시 돌릴 수 있게 한다. 남는 위험: 창이 지난 뒤 올라온 결과는 안 읽어서, 그때 다시 돌리면 비용이 두 번 든다. 분석 서버가 작업 번호로 멱등하게 받지 않는 한 없앨 수 없다. `gpu-client.ts` 는 시간 초과와 5xx 를 가르지 않아서, 서버가 분명히 거절한 5xx 도 창이 끝날 때까지 기다린다. 'gpu-auth' 만 바로 닫는다.
- **시간 지표**: 이 흐름은 영상 트랙만 있으면 받으므로 '원본 접수니까 원본'이라고 보지 않는다. 저장된 파일 사실을 실험실 검사에 대어 화면 녹화 모양 · 30fps 이하 · 장면 간격이 고르지 않거나 못 읽음 · 재생 속도를 바꿈이면, 영상 시간을 실제 시간으로 믿을 수 없다고 보고 엔진에 `screenRecorded: true, slowmoFps: null` 로 넘긴다. 엔진은 착지 → 릴리스 시간을 빼고 'screen' 경고를 단다. 엔진의 칸 이름을 빌린 것일 뿐 화면 녹화라고 단정한 것은 아니다. 대가: 재생 속도를 바꾼 진짜 슬로 모션 원본도 이 지표를 잃는다(틀린 값보다 없는 값을 골랐다). 주의는 GPU 를 누르기 전에 `analysisReadiness().inputNotes` 로 본다. 줌 · 광각은 파일에 적힌 35mm 환산값으로 알리고 분석 서버에 `lens: 'zoom'` 을 넘겨 1배 초점 사전을 끈다. 그 값을 못 읽으면 못 봤다고 알린다. 초당 60장 안팎의 파일이 슬로 모션을 구운 것인지는 파일 사실로 못 가른다. 시간 지표를 빼지 않고 그 한계만 알린다.
- **결과 바꿔치기 막기**: 결과 올리기 주소는 재시도 때문에 덮어쓰기가 켜져 있어 살아 있는 동안 파일이 바뀔 수 있다. 끝날 때 잰 SHA-256 을 `resultMeta` 에 두고 공개 · 공개 보기 때마다 다시 맞춘다. 다르면 내보내지 않는다.
- **공개 판**: 설명을 고치면 새 판이다(승인 내용이 말없이 바뀌지 않게). 같은 실행 · 같은 설명은 판이 안 는다. 다른 실행을 승인하면 앞 공개를 닫고 새 판을 준다.
- **동시 관리자**: 공개 · 내리기는 화면이 알던 공개(`expectedActivePublicationId`, 없으면 null)를 잠금 안에서 맞춰 보고, 다르면 `stale_publication` 으로 막는다. 값을 안 보낸 요청은 받지 않는다. 지금 판과 다른 영상의 실행은 `allowOlderRevision` 을 분명히 넘겨야 공개된다(`run_not_current`).
- **공개 이름**: 결과 · 설명은 승인한 판 그대로지만, 선수 이름은 지금 판에서 읽는다. 이름은 승인한 분석 내용이 아니라 신원 표시이고, 관리자가 요청한 고침으로만 바뀐다. 공개 때 사본을 두면 오타 하나에 재공개가 필요하고 표 칸도 하나 더 든다.
- **철회**: 필수 동의를 거두면 공개 칸이 남아 있어도 공개 API 가 내보내지 않는다. 받는 사람의 철회 요청은 담당자가 기록한다(`withdrawIntakeConsent`). 철회 뒤에는 새 분석 · 공개 · 원본 주소 · 미리보기 · 결과 열기가 모두 막힌다.
- **철회 때 이미 돌던 실행**: 분석 서버에는 멈추는 길이 없어 멈출 수 없다. 다음 상태 묻기에서 결과를 읽지 않고 실패(`withdrawn`)로 닫는다. 그래서 그 실행은 공개될 수 없다. 뒤늦게 결과 파일이 올라와도 아무도 안 읽고, 지우지는 않는다(분석 결과의 보유 기간은 아직 안 정했다). 분석 서버가 이미 받은 읽기 주소는 수명(한 시간)까지 산다. 철회 · 폐기가 GPU 전송 직전이면 보내지 않고 닫는다.
- **폐기**: 새 토큰 · 완료 · 결과 보기를 막고, 새 분석도 막는다(원본을 국외 서버로 새로 보내지 않게). 이미 돌던 실행은 끝까지 받되 폐기된 초대에는 공개할 수 없다. 원본 내려받기는 막지 않는다 — 폐기는 동의 철회가 아니라서, 철회는 따로 기록해야 원본이 잠긴다.
- **읽기 주소 수명**: 분석 서버용 서명 읽기 주소는 한 시간이다(실험실과 같다). 폐기해도 그 시간까지 산다. 관리자 내려받기는 5분이다.
- **동의 판이 바뀌면**: `ANALYSIS_CONSENT` 가 확정되면 글이 바뀌어 예전 동의는 '지금 판'이 아니다. 그 접수는 GPU 가 `analysis_consent_missing` 으로 막히고, 받는 사람이 링크를 열면 `ReconsentStep` 이 바뀐 글만 다시 받는다. 알림은 없어서 링크를 다시 열어야 한다.
- **보내는 사람의 관계**: 동의는 누구의 자격으로 했는지까지가 기록이다. 관계가 바뀌면 같은 답이어도 새 줄이고, 다시 받기 전에는 필수 동의가 없는 것으로 본다. 고침 화면은 관계를 바꾸면 체크를 비우고 필수 동의만 다시 받는다. 옛 관계의 모델 동의는 '안 함'으로 적지 않고 쓰이지 않는 채로 둔다. 누가 대신 동의할 수 있는지는 정하지 않았다.
- **접근 코드**: 6자 이상. 시도 자리를 코드 대조 전에 DB 가 세고, 맞으면 돌려준다. 창마다 8번, 틀린 횟수가 쌓여 10번이면 관리자가 풀 때까지 잠근다. 틀린 시도는 감사 기록에 남기고 코드 글은 안 남긴다. 코드는 화면 메모리에만 있어 새로고침하면 다시 적는다.
- **감사 기록 보기**: 받는 사람이 만든 줄은 따로 60줄까지만 보인다. 링크를 쥔 사람이 동의를 뒤집어 관리자 · 일꾼의 기록을 화면 밖으로 밀지 못하게 한다. 줄 자체는 지우지 않고, 쓰기는 초대별 한도로 묶는다.
- **같은 투구 확인**: 짝이 달라지면 지운다(칸 교체 · 한쪽이 있는데 빈 칸 채우기 · 정리가 칸을 비울 때). 방금 이 짝을 확인하고 보내는 전송은 `pairConfirmed` 로 알려 지우지 않는다.
- **이름이 지워진 초안**: 만 14세 미만을 골랐다가 되돌리면 파일이 다 왔어도 이름부터 다시 받는다. 올리기 기간이 끝났으면 저장할 수 없어 기간 끝 화면이고, 관리자가 늘리면 이어 간다.
- **촬영 길이**: 분석 서버는 영상 앞 20초만 읽는다(`pipeline.py MAX_VIDEO_SEC`). 원본은 잘라 받지 않으므로 투구가 그 뒤에 있으면 실패한다.
- **크론**: 5분 일정은 Vercel Pro 이상이어야 한다. `CRON_SECRET` 이 없으면 401 로 아무것도 안 한다.

## 원본 보유 기간(2026-11-06 금윤호 결정)
규칙은 `lib/intake/retention.ts` 한 곳이고, 지우는 일은 `lib/intake/purge.ts`, 판에 오르지 못한 파일은 `cleanupStaleUploads` 다.

**사람이 정한 것**
1. 원본은 90일 보유한다. 시계는 그 접수의 가장 늦은 공개일에서 시작한다. 뒤에 다시 내거나 다시 공개하면 새로 돌고, 공개를 내려도 안 돈다.
2. 공개한 적이 없으면 철회한 접수는 철회한 날, 그 밖에는 마지막으로 낸 날부터다. 철회는 공개한 적 있는 접수의 시계를 늦추지 않는다.
3. 모델 개발 동의는 예외가 아니다. 그 원본도 90일에 지운다.
4. 필수 동의를 철회해도 모델 개발 동의는 따로 남는다. 동의 글이 그렇게 말한다.
5. 철회한 접수에서 판에 오르지 못한 파일은 철회한 날부터 7일 유예 뒤 지운다.
6. 분석 전 미리보기는 만들지 않는다. 범위 제외 결정이고, 못 끝낸 일이 아니다.

**구현하며 정한 것(사람이 뒤집을 수 있다)**
- **'다시 내면 새로 돈다'의 뜻**: 공개한 접수를 뒤에 다시 냈으면 공개일과 낸 날 가운데 늦은 날을 쓴다(`resubmitted`). 재공개가 없어도 그렇다. 방금 받은 파일이 며칠 만에 지워지지 않게 한 쪽이다.
- **열린 고침**: 받는 사람이 고칠 수 있는 동안(초대가 살아 있고 올리기 기간 안) 삭제를 기다린다. 다시 내면 시계가 새로 돌고, 거두면 다음 크론이 지운다. 기다림은 지울 날부터 14일(`INTAKE_CORRECTION_HOLD_DAYS`)까지다. 관리자가 기간을 거듭 늘려 삭제가 끝없이 밀리지 않게 했다. 상한이 되면 얼린 원본만 지우고, 고침 중 새로 고른 파일은 남기며, 지운 칸을 고침 요청에 넣는다. 관리자 상세는 기다리는 중이라고 보이고, 동의 글도 이 규칙을 말한다.
- **분석**: 실행이 대기 · 실행 중이거나 시작 응답을 못 받았으면 기다린다. 끝난 뒤에도 한 시간 기다린다(분석 서버 읽기 주소 수명과 같다). 뒤늦은 미리보기 파일이 삭제 뒤에 남지 않게 줄이려는 것이다.
- **새 분석**: 지울 날이 지나면 지우기 전이어도 `original_purged` 로 막는다. 삭제가 도는 파일을 분석 서버로 보내지 않고, 기다리는 사이 새 실행이 끼어들지 못한다.
- **지운 뒤 고침**: 지운 칸은 언제나 고침 요청에 들어간다. 글만 요청해도 그렇다. 지운 파일로는 판을 얼릴 수 없어서 안 넣으면 받는 사람이 끝낼 수 없다. 같은 파일을 다시 골라도 새 자산이다.
- **삭제 확인**: 저장소의 답만 믿지 않고 `stat` 으로 없어진 것을 본 뒤 'purged' 로 적는다.
- **포기 없음**: 삭제 일감은 시도를 다 써도 6시간마다 다시 건다. 멈춘 동안은 상세의 '멈춘 일감'에 보인다.
- **표 칸**: `IntakeSubmission.withdrawnAt` 을 더했다. 동의 줄의 시각은 철회할 동의 줄이 없는 접수에 없어서 쓸 수 없다.

**남는 위험**
- 분석 서버는 멈출 수 없어서, 닫힌 실행의 미리보기가 삭제 뒤에 올라오면 남는다. 한 시간 기다림으로 줄였을 뿐이고 없애지는 못했다.
- 분석 서버가 이미 받은 읽기 주소는 수명까지 살고, 지운 뒤에는 읽을 파일이 없다.
- 관리자가 내려받은 사본은 이 삭제가 닿지 않는다. 분석 서버 쪽 사본의 보유 기간은 `ANALYSIS_CONSENT` PENDING 그대로다.
- 검증이 끝내 멈춘 판은 삭제 뒤에도 'pending' 으로 남는다.

## 실제 버킷 없이는 모르는 것
- 호스팅 저장소가 `apikey` 없이 받는지, 토큰 만료 응답의 정확한 상태 · 글(시험은 소스대로 400 + 'signature' 로 흉내), 끝난 업로드에 대한 HEAD 응답.
- 프로젝트 전체 파일 한도가 1GiB 이상인가.
- 호스팅 저장소의 `remove` 가 없는 객체에 오류 없이 답하는지, 지운 객체의 서명 주소를 `not found` 로 거절하는지. 삭제 재시도와 삭제 확인이 여기에 기댄다. 시험은 가짜 저장소로만 봤다.
- 1GiB 해시를 서버 함수 한 번에 끝낼 수 있나 — 스트리밍이라 메모리는 안 늘지만 시간 제한이 있다. 라우트 · 크론의 `maxDuration` 은 300초로 두었고, 끝나는지는 실제 파일로 재 봐야 한다.

요구 · 구현 · 검증 대조표는 `external-intake-verification.md`.
