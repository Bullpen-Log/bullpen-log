# 싱커 × 덕아웃 팀·레슨 통합 설계

작성: 2026-11-01. 상태: 설계 제안. 이번 작업은 문서 작성이며 앱·서버·DB·출시 설정은 변경하지 않았다.

## 1. 제품의 경계

싱커는 **선수의 운동 실행과 개인 기록**, 덕아웃은 **사람·조직·예약·소통의 관리**를 담당한다. 두 앱은 같은 계정·회원 관계·훈련 원본을 사용한다. 화면의 책임을 옮기며 데이터나 계정을 복제하지 않는다.

| 업무 | 싱커 | 덕아웃 |
|---|---|---|
| 개인 투구·구속·분석·트레이닝 | 실행·기록·개인 이력 관리 | 공유에 동의한 범위만 관리자가 조회 |
| 팀 가입·초대·승인·탈퇴·관리자 임명 | 소속 및 다음 훈련 확인 | 관리의 원본 화면 |
| 팀 훈련 | 배정 계획 확인·운동·기록·정정 요청 | 계획 배정·현황·피드백·예외 확인 |
| 레슨 | 본인 레슨 화면·숙제·실제 촬영/분석·개인 성장 | 코치 탐색·예약·변경·회원·이용권·계획·소통 |
| 코치의 현장 지도 | 권한 있는 회원의 촬영·측정·분석 도구 | 회원 선택·레슨 운영·기록 검토·발행 |
| 팀 일정·대회·공지·단체 채팅 | 운동에 필요한 일정 요약과 이동 링크 | 작성·관리·소통 |
| 학부모 | 기본 진입처로 삼지 않음 | 자녀 기록·일정·공지·예약·연락 |

좌측 상단의 공간 전환을 유지한다. `내 훈련 / A팀 훈련 / B코치 레슨`처럼 선수에게 이해되는 이름을 사용한다. 선택한 공간은 화면 문맥일 뿐 권한이 아니다. 계정을 바꾸거나 기존 개인 운동을 재설정하지 않는다. 진행 중 운동은 시작할 때의 선수·조직·일정에 귀속하며, 도중 공간을 바꿔도 귀속을 바꾸지 않는다.

## 2. 현행 코드 확인과 재사용 지점

다음은 이번 코드 열람으로 확인한 사항이다. 기능의 전체 동작을 실행 검증했다는 뜻은 아니다.

- `prisma/schema.prisma`: Org, OrgMember, ShareConsent, OrgEvent, OrgPlan, OrgEventAttendee, OrgAssignment, LessonNote, LessonPass, LessonBooking, OrgComment, OrgNotice/Read, GuardianReport가 존재한다.
- `native/src/app/org/`, `native/src/org/`: 조직·선수·코치 화면과 공간 전환이 이미 존재한다. 과거 설계 문서의 ‘네이티브 조직 화면 없음’은 현재 상태와 다르다.
- `lib/org/space-nav.ts`: 개인/조직 공간, 딥링크, 조직 탈퇴 시 대체 경로를 공유한다.
- `lib/org/team-work-store.ts`: 조직 훈련을 기존 선수 운동 판에 쓰며 작성자와 orgEventId를 구분한다. 기존 하루 단위 TrainingSession 구조를 무시하고 별도 세션 체계를 만들지 않는다.
- `app/actions/lessons.ts`: 예약 확정 시 회원·일정을 연결하며 공유 동의를 자동 생성하지 않는다. 이 원칙을 유지한다.
- 같은 파일의 완료 처리: 트랜잭션 전 상태 확인 후 이용권 used 증가 구조여서 동시 요청의 중복 차감 방지가 필요하다.
- 같은 파일의 취소 처리: 연결 일정 삭제 경로가 있어 기록이 있는 일정의 취소 보존 정책이 필요하다.
- `lib/org/app-access.ts`: 현재 코치 접근에 accountType MASTER 또는 전역 관리자 조건이 있다. 일반 학부모를 총무로 임명하려면 조직 권한만으로 해당 업무를 수행할 수 있게 분리해야 한다.
- `GuardianReport`는 토큰/코드 기반 보고서다. 로그인한 학부모-자녀 관계를 대체하지 못한다.
- 현재 Conversation/Message는 장터 buyer/seller 1:1 구조다. 팀 단체방을 여기에 억지로 넣지 않는다.
- `OrgEventAttendee.reply/attended`는 현재 주석상 사용 중단 상태다. 참석 응답을 재도입할 때 기존 수행 확인과 섞지 않는다.
- `lib/release-access.ts`: restricted_beta가 기본이고 비대표관리자는 투구 3D 중심으로 제한된다. 팀·레슨 개발과 공개는 별개다. 기존 베타 정책을 자동 해제하지 않는다.

## 3. 사용 흐름

### 팀 선수
1. 덕아웃에서 팀을 찾아 가입 요청하거나 만료되는 초대 링크를 사용한다.
2. 감독/권한자가 승인한다. 기존 계정과 정확히 연결하며 이름이 같다는 이유로 합치지 않는다.
3. 어떤 훈련 데이터를 팀에 공유하는지 설명하고 동의를 받는다. 가입과 동의는 별개의 상태다.
4. 싱커를 열거나 앞으로 가져오면 소속을 갱신한다. A팀 훈련 공간이 생기고 개인 훈련도 남는다.
5. 팀 계획을 선택해 운동하면 기존 운동 원본에 기록한다. 덕아웃이 같은 기록을 읽는다.
6. 감독은 완료/일부 수행/미수신/공유 안 함/정정 필요를 구분한다. 미수신을 미훈련으로 표시하지 않는다.

### 레슨 회원
1. 덕아웃에서 지역·종목/전문 분야·대상·시간·가격·코치 프로필로 탐색한다.
2. 실제 예약 가능한 시간을 선택하고 체험/정규, 예약자/실제 수강자를 구분한다.
3. 예약 확정과 회원 자격 활성화 규칙을 적용한다. 첫 신청만으로 무제한 회원 권한을 주지 않는다.
4. 싱커 좌측 상단에 해당 레슨 공간이 추가된다. 다음 레슨·배정 숙제·본인 피드백을 확인한다.
5. 현장 운동·촬영·분석은 싱커, 예약 변경·코치 문의·이용권·회원 관리는 덕아웃에서 한다.
6. 개인 화면에서는 원래와 동일하게 개인 운동을 한다. 공유된 레슨 기록도 개인 이력과 연결한다.
7. 진행 횟수, 날짜별 실제 수행, 코치가 발행한 피드백, 비교 가능한 지표 변화, 다음 목표를 본다. 같은 코치의 다른 회원 기록은 볼 수 없다.

### 감독·코치
- 덕아웃 오늘 화면: 오늘 일정 → 확인 필요한 훈련/질문 → 선수/회원 현황 순서.
- 팀 계획은 전체 → 투수조/야수조 등 묶음 → 개인 예외 방식. 30명을 매번 한 명씩 입력시키지 않는다.
- 현장 입력이 필요하면 명확히 ‘코치가 기록’으로 남기고 선수 직접 기록과 정합성을 검토한다.
- 레슨 완료, 출석, 노트 발행, 이용권 차감은 별개 개념이다. 정해진 완료 처리에서만 이용권을 한 번 차감한다.
- 회원을 선택하고 싱커 촬영·분석으로 이동할 수 있다. 화면에 대상 선수를 계속 표시한다. 감독 계정의 개인 기록으로 저장하면 안 된다.

### 학부모·총무
- 인증된 자녀 관계에 따라 자녀 선택, 다음 일정, 최근 공유 훈련, 코치 피드백, 공지, 예약을 확인한다.
- 여러 자녀·복수 보호자·관계 해제·초대 만료·분쟁 중 접근 중단을 다룬다. 이름/학년/전화번호 입력만으로 관계를 승인하지 않는다.
- 감독이 총무로 임명하면 일정/공지 등 지정한 운영 업무가 추가된다. 학부모라는 이유로 다른 선수의 훈련이나 영상을 볼 수 없다.
- 별도로 코치 업무까지 위임할 경우 대상 선수 범위와 데이터 공유 권한을 다시 판정한다. 직함 변경이 모든 데이터 공개로 이어져서는 안 된다.

## 4. 권한 설계

네 층을 분리한다: 전역 서비스 역할 → 조직 소속/업무 권한 → 보호자 관계 → 기록 공유 범위. 출시 단계 제한도 별도로 적용한다.

| 기본 역할 묶음 | 기본 접근 |
|---|---|
| 감독/조직 소유자 | 조직 설정·임명·팀 운영. 개인 공유 동의를 우회할 수 없음 |
| 코치 | 배정 선수의 허용된 훈련·레슨·피드백 |
| 운영 담당/총무 | 위임받은 일정·공지·명단 최소 정보·선택적 회계 |
| 선수/레슨 회원 | 자신의 기록·배정·예약·공지·허용된 대화 |
| 학부모 | 연결된 자녀의 허용 기록·예약, 팀 일정·공지·허용된 대화 |

권한 예: roster.read/manage, schedule.read/manage, training.assign, training.read, training.recordForAthlete, lesson.manage, booking.manage, notice.publish, chat.moderate, finance.manage, permission.manage, export.data. 기능 권한에 `self / linked_children / assigned_players / explicit_group / organization` 범위를 붙인다. 이는 제안 명칭이며 실제 구현은 기존 규칙과 맞춘다.

- 기본 거부, 서버에서 매번 확인. 조회 목록·상세·검색·첨부·다운로드·푸시·실시간 구독까지 동일한 판정.
- 감독은 조직의 업무 권한을 설정하지만 서비스 ADMIN/MANAGER를 임명하지 않는다.
- 민감 정보는 업무 권한과 동의의 교집합만 공개한다. 식단·체중 등의 기존 비공개 기본값 유지.
- 소유권 이전은 확인과 감사 기록, 마지막 소유자 제거 금지. 임명/회수/기록 정정은 누가 언제 했는지 남긴다.
- 로그아웃·자녀 변경·조직 탈퇴·권한 회수 시 이전 화면 캐시와 구독을 제거한다.
- 기관 이름이나 조직 ID, 프런트엔드에서 보낸 역할을 권한 근거로 믿지 않는다.

## 5. 기록 연결과 동기화

**싱커 원본 기록 → 조직과의 연결 → 권한별 덕아웃 조회** 구조를 사용한다. 분석 결과나 운동 합계를 앱별로 복제하지 않는다.

- 원본은 선수 식별자, 작성자, 작성 경로, 조직/일정/숙제 연결, 발생 시각과 서버 수신 시각, 수정 버전, 재시도 키를 추적한다. 기존 데이터 구조로 표현 가능한 부분은 재사용한다.
- 개인 운동은 개인 소유다. 조직 가입으로 과거 전체 기록을 소급 공유하지 않는다. 기간·종류·대상 조직을 구체적으로 정한다.
- 한 운동이 팀과 레슨 양쪽 계획을 충족해도 원본은 한 번만 집계한다. 조직별 연결과 열람 권한은 각각 다르다.
- 계획, 참석 응답, 실제 출석, 운동 수행, 코치 확인, 예약 완료, 이용권 차감을 독립된 상태로 유지한다.
- 코치 입력과 선수 입력이 충돌하면 원본을 덮어쓰지 말고 확인 대상으로 만든다. 기존 팀 수행 조정 코드와 합계 재계산을 검증한다.
- 저장 성공 후 갱신 이벤트를 유실하지 않도록 기존 인프라에 맞는 영속 이벤트/트랜잭셔널 아웃박스 방식을 사용한다. 별도 마이크로서비스는 필요 없다.
- 실시간 신호는 새 조회를 유도할 뿐 권한을 우회하거나 데이터 원본이 되지 않는다. 재접속·앱 복귀·누락 시 재조회한다.
- 제안 목표: 온라인 저장 확정 이후 활성 덕아웃 화면에 p95 5초 내 반영. 이는 측정 전 목표이며 보장/실측 수치가 아니다.
- 오프라인은 ‘기기에 저장/전송 대기/서버 반영’을 구분한다. 재시도 중복 방지, 서버 동의 재검사, 로그아웃 시 다른 계정으로 대기 기록 전송 금지.
- 업로드 중 탈퇴했으면 개인 기록 보존과 조직 연결 거절을 분리한다. 실패했다고 개인 운동을 버리지 않는다.
- 공유 철회는 새 조회·내보내기·첨부 URL·캐시·구독에 반영한다. 영구 공개 미디어 URL 금지. 이미 외부로 내려받은 사본을 원격 회수할 수 있다고 약속하지 않는다.

## 6. 팀 운영 기능

첫 팀 출시 범위:
- 가입/초대/승인/탈퇴, 감독·코치·선수·보호자 연결, 업무 위임.
- 오늘/주간 일정, 반복 일정과 특정 회차 변경·취소, 훈련 장소·준비물·집합 시간·대회 일정.
- 전체/조/개인 계획, 배정 당시 대상 명단 보존, 수행 현황, 예외와 정정.
- 참석 예정 응답과 실제 출석을 운동량과 별개로 재도입. 기존 비활성 칸을 검토 없이 활성화하지 않는다.
- 공지 고정·대상·확인 버튼·확인 기한·미확인자 알림. 단순 페이지 노출과 ‘확인했어요’를 구분한다.
- 단체 채팅과 운영진 전용 방, 필요한 경우 조별 방. 민감한 개인 훈련은 팀방에 자동 게시하지 않는다.
- 일정 변경 알림은 바뀐 시간/장소를 명확히 보여주고 중복 발송을 막는다.

후속 편의 기능:
- 훈련/주간 일정 템플릿, 선수 일괄 등록의 미리보기와 중복 확인.
- 대회 준비 체크리스트·원정 집합·업무 분담, 공유 장비 대여/반납.
- 보호자 희망자 중심 이동 지원/차량 배정. 자택 주소와 연락처를 전체 공개하지 않는다.
- 권한 범위 내 캘린더 구독/내보내기. 취소할 수 있는 링크와 최소 정보만 포함.
- 총무 회계 장부·회비 현황은 별도 단계. 결제·정산·영수증·환불을 현재 구현된 것처럼 제시하지 않는다.

## 7. 레슨 예약·회원 관리

- 여러 코치가 있는 레슨장을 지원할 수 있도록 조직/코치/레슨 상품/시간/장소·장비 자원을 구분한다.
- 예약 요청→확정→완료, 거절/취소/노쇼를 명시한다. 변경 요청은 기존 확정 시간과 별도이며 수락 전 기존 예약을 보존한다.
- 코치 시간·수강자 시간·시설 수용량을 서버에서 원자적으로 검사한다. 동시에 두 사람이 눌러도 마지막 한 자리가 두 번 확정되지 않아야 한다.
- 요청 시간은 확정과 구분해서 표시한다. 확정/보류 방식에 따라 자리 확보 정책을 명시하고, 만료되는 보류를 쓰면 만료 처리도 구현한다.
- 지역 시각과 타임존, 날짜 경계, 반복 회차를 명확히 한다. 기존 Date와 HH:MM 구조는 호환되는 추가 확장으로 이전한다.
- 예약자와 실제 수강자를 구분한다. 부모 예약은 자녀의 기록과 이용권에 연결하고 부모 계정의 운동으로 저장하지 않는다.
- 취소해도 이미 발생한 운동/피드백은 지우지 않는다. 이용권 복원/차감은 정책과 원장으로 한 번만 처리한다.
- 노트는 초안/회원 공개/코치 내부 메모 구분. 학생 공개 피드백과 내부 관리 메모를 같은 응답에 섞지 않는다.
- 진도는 완료한 레슨 수·수행 내용·숙제·다음 목표를 중심으로 한다. 다른 측정 조건의 구속/분석 수치를 무조건 비교하거나 의학적 진단을 표시하지 않는다.
- 기존 payMethod 저장만으로 실제 결제가 구현됐다고 표시하면 안 된다. 결제 수단 연동은 별도 설계와 출시 과제다.

## 8. 채팅·알림

장터 1:1 채팅은 보존하고 조직 방·방 참여자·메시지·개인별 읽음 위치를 추가하거나 기존 기반을 호환 확장한다.

팀 전체 / 운영진 / 조별 / 코치-회원(필요시 인증 보호자 참여)을 구분한다. 레슨회원 전체가 서로의 진도·영상·예약 상세를 보지 못하게 한다. 새 참여자는 기본적으로 가입 이후 대화만 보며, 현재 공지는 별도 공지 기능으로 제공한다. 과거 공개 범위를 넓히려면 명시적인 정책과 검증이 필요하다.

대상자 검증, 메시지 재전송 중복 방지, 순서, 페이지 조회, 신고/숨김/관리 기록, 음소거, 첨부 검증, 탈퇴 즉시 구독 해제, 푸시 잠금화면의 민감 내용 최소화를 포함한다. 미성년 회원의 코치 대화는 허용된 보호자 동반 참여 정책을 제공하되, 정확한 적용 기준은 출시 설정으로 확정한다.

## 9. 화면 구성

덕아웃 기존 브랜드·내비게이션 틀을 유지한다. 팀 기능을 위해 홈 전체를 새로 설계하거나 커다란 홍보 배너를 추가하지 않는다.

- 팀 PC: 조직 선택 → 요약/선수단/훈련/일정/공지/대화/설정. 오늘 일정, 확인할 일, 행 단위 선수 현황을 먼저 보인다. 선수 선택 시 옆 패널로 상세.
- 레슨 코치 PC: 오늘 수업·변경 요청·미응답 질문 중심. 캘린더와 회원 목록을 오가며 동일 회원 문맥 유지.
- 보호자: 자녀 선택 → 다음 일정 → 최근 훈련/피드백 → 공지/예약. 다른 선수 통계 순위 불필요.
- 싱커: 기존 상단 공간 전환, 오늘 할 운동, 이어 하기, 최근 피드백. 팀 운영 폼이나 예약 관리 표를 억지로 넣지 않는다.
- 휴대폰 정식 구현은 native/이며 mobile/을 다시 개발하지 않는다. 긴 표는 핵심 항목 리스트와 상세 화면으로 전환한다.
- 모바일 safe-area·키보드·큰 글씨·접근성 라벨을 확인한다. PC 1280/1440/1920, 모바일 360/390/430 논리 폭 기준으로 잘림을 검증한다. 모든 정보를 한 화면에 쑤셔 넣는 것을 목표로 하지 않는다.
- 앱 간 이동은 현재 검증된 앱 식별자·도메인·링크 체계를 사용한다. 인증 토큰을 URL에 넣지 않는다. 미설치/구버전/권한 없음에 대한 복귀 경로를 제공한다.

## 10. 구현 단계와 완료 조건

0. 현행 조사/계약: 화면·동작·데이터 원본·권한·출시 잠금·기존 문서 충돌 목록과 요구사항 대응표. 이전 문서의 바뀌는 결정은 폐기 표시.
1. 기반: 조직별 권한, 보호자 관계, 원본 연결, 동의, 멱등성, 감사 기록, 호환 API. 먼저 부정 접근 테스트.
2. 팀 수직 흐름: 가입→싱커 공간→계획→수행→덕아웃 확인→자녀 조회까지 연결. 운영 화면을 덕아웃으로 이동.
3. 레슨 수직 흐름: 코치 찾기→예약→회원 연결→싱커 수행→피드백→다음 계획. 경쟁 예약·중복 차감·취소 보존 포함.
4. 소통/편의: 팀 단체방, 레슨 대화, 공지 확인, 일정 변경, 반복 일정과 참석. 기존 출시 기능 회귀 검증.
5. 출시: 구버전 앱 호환·관찰·단계적 공개·되돌리기. 현재 투구 3D 베타 해제는 별도 제품 결정으로만 진행.

기반 및 각 단계에 실제 완료/미완료를 표시한다. 단순 UI 시제품을 전체 완료로 보고하지 않는다. 모든 원래 요청은 최종 범위에 남기며 후속 단계라는 이유로 삭제하지 않는다.

필수 검증: 두 팀 동시 소속, 학부모 두 자녀, 타 자녀 직접 URL 차단, 학부모 총무 임명/회수, 별도 코치 권한, 탈퇴/공유 철회/재가입, 개인+팀+레슨 같은 날 기록, 코치와 선수 중복 입력, 재전송/오프라인/역순 갱신, 마지막 자리 동시 예약, 동시 완료 이용권 1회 차감, 취소 후 기록 보존, 방 권한 회수, 실제 두 앱 이동, 구버전 클라이언트, 베타 차단 유지.

## 11. DB·배포·인수인계

필요한 새 모델의 후보: 보호자 관계, 조직 권한 부여, 강사/자원 가용시간, 예약 변경, 이용권 원장, 채팅방 참여, 감사 이벤트, 영속 갱신 이벤트. 모두 **제안**이며 기존 모델로 충분하면 재사용한다.

공유 DB가 운영 DB이므로 이번 설계에서는 변경하지 않는다. 구현자는 AGENTS.md에 따라 상대 개발자와 사전 조율·백업 후 nullable/default 추가 마이그레이션을 준비한다. migrate dev/db push/reset 금지. 기존 데이터 중복/모호한 회원은 자동 합치지 않는다. 백필은 dry-run·건수 검증·재실행 안전성을 갖춘다.

서버 호환 확장→앱 업데이트→이용 확인→옛 관리 진입 전환→충분한 호환 기간 뒤 정리 순서. 앱 OTA와 웹 배포가 같은 시각에 도달한다고 가정하지 않는다. 운영 공개 전에 필요한 승인만 최종 단계에서 받는다. Seoul icn1, 기존 다른 작업 변경, 정식 native 구조를 보존한다. 받은 사람이 할 일은 HANDOFF.md에 남긴다.
