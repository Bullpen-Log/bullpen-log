## G01 · P1 · 웹에서 유효한 STAFF 초대를 수락할 수 없다

근거: `components/org/join-view.tsx:90–103,119`는 usable을 `invite.role === 'PLAYER'`일 때만 true로 한다. STAFF 코드는 정상 코드여도 수락 폼이 나오지 않으며 ‘맞지 않거나 기한이 지난 코드’처럼 안내한다. `lib/org/join.ts`는 이제 일반 계정의 STAFF 코드를 허용하지만 웹 화면이 그 함수를 부를 길을 제공하지 않는다. 새 `/teams/join`과 옛 `/join`이 이 본문을 같이 쓰므로 둘 다 영향을 받는다. 소스 제어 흐름으로 확인했고 실제 로그인 브라우저에서 실행하지는 않았다.

수정 설계:
- 서버가 PLAYER/STAFF 초대의 유효성과 수락 가능 이유를 공통 규칙으로 판정한다. 프런트와 액션이 서로 다른 역할 조건을 유지하지 않게 한다.
- PLAYER는 선수 가입·개인 기록 공유 설정, STAFF는 ‘이 조직의 코치 업무 초대’로 명확히 구분해 수락한다. STAFF 수락을 선수 기록 공유 동의로 처리하지 않는다.
- ‘코드 만료/사용됨/역할 충돌/권한 없음/이미 참여’를 구분한다. 실제 코드의 조직과 역할을 보여주고 수락 후 덕아웃 관리 진입·싱커 공간 새로고침을 연결한다.
- 기존 PLAYER 회원이 STAFF 초대를 받으면 현재 단일 role 모델의 한계를 명시한다. 조용히 코드를 소비하고 PLAYER로 남긴 뒤 성공이라고 하지 않는다. 다중 책임을 저장할 때까지는 명시적인 충돌/지원 경로를 제공하거나 승인된 역할 전환 규칙을 구현한다.
- CopyJoinLink의 기존 주소와 앱 딥링크도 이 공통 수락 흐름으로 호환시킨다.

## G02 · P1 · 선수용 재가입으로 회수된 STAFF 권한이 살아난다

근거: `lib/org/join.ts:39–50`은 기존 회원의 role을 조회하지 않고, status가 LEFT이면 ACTIVE로 바꾼다. 따라서 USER/PLAYER 계정의 기존 회원이 `{role:STAFF,status:LEFT}`일 때 PLAYER 코드를 사용하면 STAFF는 그대로인 채 ACTIVE가 된다. `orgsFor`/requireOperator/coachOrgCan은 이를 다시 운영자로 인정한다.

실제 joinWithCode를 모의 Prisma와 실행한 결과:

```text
before: role=STAFF, status=LEFT
input: invite.role=PLAYER, accountType=PLAYER
result: ok=true
after: role=STAFF, status=ACTIVE
```

이는 일반 선수 재가입이 코치 권한 복원으로 이어지는 경로다. 현재 베타에서 해당 사용자에게 org 기능이 잠겨 있다면 그 출시 제한은 별도로 적용된다. 운영에서 악용됐다고 확인한 것은 아니다.

`lib/org/booking-transitions.ts:74–81`의 레슨 예약 확정도 기존 role을 보지 않고 같은 ACTIVE 갱신을 한다. 선수 등록을 통해 운영 권한이 복원되는 동일한 불변식 위반이다.

수정 설계:
- ‘선수 등록/재가입’과 ‘운영 권한 임명/복원’을 다른 명령으로 구분한다.
- 기존 role/status를 트랜잭션 안에서 읽고, 명시적인 전이 표로 허용한다. PLAYER 초대·레슨 등록은 LEFT STAFF/MASTER를 ACTIVE STAFF/MASTER로 만들 수 없어야 한다.
- ACTIVE STAFF/MASTER를 자동 PLAYER로 낮추는 임시 수정도 하지 않는다. role이 충돌하면 실패하거나 명시적으로 승인된 책임 전환을 수행한다.
- 코치 재임명은 감독이 발급한 유효한 STAFF 초대 또는 별도 임명 동작으로만 처리한다. 과거 개인 기록과 수신 레슨 기록은 보존한다.
- LEFT/INVITED/ACTIVE와 각 role의 교차 조합을 웹·앱·예약 등록에 동일하게 시험한다. 가입 자체가 권한 회수를 무효화하지 않도록 한다.

## G03 · P1 · 1회용 STAFF 초대를 두 사람이 동시에 사용할 수 있다

근거: `lib/org/join.ts:20–30`의 사용 여부/만료 검사는 트랜잭션 밖이고, 95–98행은 마지막에 id만 조건으로 usedAt을 쓴다. 두 사용자가 둘 다 미사용 상태를 읽으면 각각 STAFF 회원을 만든다.

실제 joinWithCode에 두 사용자의 초대 조회를 같은 시점에 완료하도록 한 모의 실행에서 **두 요청 모두 ok, STAFF 회원 2개**가 생성됐다. PostgreSQL 실서버 경쟁 검증은 아니다. 단일 사용 선점 조건이 없다는 실제 소스와 결합한 결정적 제어 흐름 재현이다.

수정 설계:
- STAFF 및 특정 placeholder에 연결된 1회용 초대는 트랜잭션 안에서 `usedAt is null`, 미만료, 정확한 org/role 조건으로 한 요청만 선점한다. 영향받은 행 수를 확인한다.
- 회원 생성·역할 전이·초대 소비는 같은 트랜잭션이다. 뒤 단계 실패 시 초대 소비도 롤백한다.
- 같은 사용자 재시도는 타인의 권한을 넓히지 않는 일관된 결과로 처리한다. 다중 사용 PLAYER 코드는 별도 정책을 유지한다.
- placeholder 연결도 `userId is null`을 갱신 조건으로 선점한다. 선점 실패 시 다른 계정의 자리를 덮거나 새 권한을 임의 생성하지 않는다.
- 단순 ‘트랜잭션으로 감쌈’이나 선조회만으로 동시성 문제가 해결됐다고 보지 않는다.

## G04 · P1 · 새 운동 연결 대기열도 재시작/전송 순서에서 연결을 잃는다

근거:
- `native/src/org/space-store.ts:132–140`: 활성 event 귀속은 여전히 orgReturn 메모리에만 있으며 consumeOrgReturn 때만 links로 옮긴다.
- 163–175행: RPC가 반환되면 linked=0이어도 links에서 즉시 제거한다.
- `app/actions/app-team.ts:984–999`: 현재 서버에 존재하는 세트만 updateMany하고 0개여도 `{ok:true,linked:0}`을 반환한다.
- 운동 세트는 별도 `native/src/workout/outbox.ts`로 전송한다. links에는 그 세트의 저장 확인을 기다리는 의존 관계가 없다.
- 저장도 fire-and-forget persist이고 saveJson은 실패를 삼킨다. ‘폰에 안전하게 남음’을 보장하는 방식이 아니다.

실제 space-store 모듈을 모의 저장소/RPC로 실행한 두 재현:

```text
setOrgReturn(event) → 모듈 재시작 → consumeOrgReturn
결과: pending=0, link RPC=0 (활성 귀속이 저장되지 않음)

consumeOrgReturn → 세트 도착 전 link RPC가 ok:true,linked:0
결과: pending=0 (뒤늦게 세트가 도착해도 다시 연결하지 않음)
```

수정 설계:
- 운동 시작 때부터 계정/선수/조직/회원/일정/원본 세션과 세트 식별자를 내구성 있게 저장한다. 복귀 화면 정보와 귀속은 분리한다.
- 세트 저장 성공 → 정확한 세트 연결 요청 → 연결 확인의 순서를 보장한다. 단순 since 시각의 하한만으로 다른 개인 운동까지 붙이지 않는다.
- 연결 RPC에 예상한 원본 식별자를 전달하고 성공/저장 대기/최종 거절/복구 가능 실패를 구분한다. 정상적인 빈 운동과 아직 도착하지 않은 세트를 구분한다.
- 서버가 확정한 원본 수를 확인한 뒤에만 대기열을 지운다. 재시도는 동일 키에 대해 멱등하게 한다.
- 저장 실패 상태와 아직 미연결인 상태를 실제 화면에 표시한다. pendingLinkCount는 정의만 있고 사용처가 없다.
- 저장 쓰기를 직렬화하고, 시작/재시작/로그아웃/다른 계정/권한 회수/응답 유실을 검증한다. 개인 운동은 조직 연결 실패와 관계없이 보존한다.

## G05 · P2 · 일부 선수만 보는 렌즈에서 다른 선수 체크인과 전체 통계가 남는다

근거: `lib/org/dto-scope.ts`의 training/checkin은 전역 boolean이고 trainingMembers는 일부 분기에서만 확인한다.

실제 lensOf/redact 함수를 아래 조건으로 실행했다:

```text
roster.read = organization
training.read = explicit_group [m1]

redactEventDetail(m2): values는 비지만 outingNote="m2 private check-in"은 남음
redactToday(memberId=null): recorded=17, selfRecorded=5, issues=3이 남음
memberId=null인 전체 팀 브리핑도 남음
```

또 redactToday는 counts를 바꾸지 않으며, redactEventDetail은 plans/targets/memberIds/names/tags 등 원본을 펼쳐 반환한다. 허용 집합이 좁으면 연결된 메타데이터·집계도 별도로 판단해야 한다.

현재 orgAuthz의 grants는 빈 배열이므로 이 좁은 grant가 실제 사용자에게 저장돼 운영에서 유출됐다고 주장하지 않는다. **새 순수 가리기 규칙을 실제 좁은 위임에 연결하기 전 수정할 결함**이다.

UI도 hidden을 소비하지 않는다. 예를 들어 `native/src/org/coach.tsx`는 가려져 사라진 recorded를 `?? 0`으로 바꾸어 ‘기록 0’처럼 표시할 수 있다. 새 optional 필드만 추가하면 구버전/현재 UI의 동작이 안전해진다는 가정은 성립하지 않는다.

수정 설계:
- training/checkin/video/finance별 대상 집합을 명시하고, 대상별 판정 함수를 일관되게 적용한다. self는 실제 현재 회원 id로 해석한다.
- memberId=null인 팀 전체 집계/브리핑은 모든 대상 접근이 가능할 때만 원본을 제공한다. 아니면 허용 대상에서 다시 계산하거나 감춘다.
- 계획의 대상 id·실제 수행·태그·이름 사전·멤버 수·개별 메모까지 DTO 필드 목록으로 관리한다. `...원본`으로 새 민감 필드가 자동 통과하지 않게 한다.
- 조회 쿼리부터 대상을 좁히고 반환 직전에도 최소 DTO를 확인한다. 이 규칙을 나머지 노트/영상/웹 관리/검색/알림/내보내기에 연결한다.
- UI는 비공개/권한 없음/동기화 대기/실제 0을 구분한다. 기존 앱 응답 호환은 버전별로 검증하고 준비되지 않은 좁은 위임을 켜지 않는다.

- 추가로 실제 설치된 Prisma에 가짜 드라이버를 연결해 `updateMany(data:{})` SQL을 관찰했다. 해당 호출은 SELECT만 생성했고 UPDATE나 FOR UPDATE를 만들지 않았다. finishBookingTx의 이 호출을 행 잠금이라고 설명하면 안 된다. 뒤의 CONFIRMED→DONE 조건부 UPDATE가 핵심 보호이며, 빈 갱신 자체가 완료를 실패시킨다는 주장은 하지 않는다.

## 전체 설계의 남은 범위

인증된 학부모-자녀 관계, 실제 세부 위임 저장·설정 UI, 팀 단체 채팅/코치 대화, 관리 기능의 완전한 덕아웃 이전, 원자적 슬롯 용량/예약 변경, 이용권 원장, 초안/공개/내부 노트, 반복 일정/참석/공지 확인, 안정적 변경 전달과 실측은 여전히 별도 진행이 필요하다. DB 무변경 범위의 수정과 이 전체 기능 완료를 혼동하지 않는다.

다음 순서: G02/G03 권한·초대 불변식 → G01 실제 수락 화면 → G04 내구성 있는 정확한 귀속 → G05 전 조회·화면 적용 → R01~R14의 검증 가능한 수직 흐름. 공유 DB 변경은 사전 조율·백업을 따르며, 현재 진행 중인 다른 세션의 베타/배포 작업은 되돌리지 않는다.

영어 실행 지시: `sinker-dugout-team-lesson-platform-remediation2-claude-prompt.md`.
