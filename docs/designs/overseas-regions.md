# 해외 출시 때 서버 · DB 배치 — 지역별 Supabase 둘(한국 · 미국 동부)

2026-10-13 · 김민(Claude)과 정함. **해외 출시 이야기를 꺼내면 이 문서대로 한다.** 지금(한국 출시)은 서울 하나 그대로 두고, 아래 '지금 해 둘 것'만 한다.

## 왜 — 사용자 기준

김민: "북미 · 남미 사용자도 내가 지금 서울에서 쓰는 것처럼 빠르고 편해야 한다." 김민이 미국에서 써 보니 너무 느렸다 —
서버 · DB 가 서울이라 요청마다 태평양 왕복(약 0.15~0.2초)이 화면 하나에 여러 번 쌓였다.

## 고른 길과 버린 길

| 길 | 판단 |
|---|---|
| 서버만 미국에 추가(DB 는 서울) | 버림 — 미국 서버가 서울 DB 를 여러 번 오가 더 느려진다(AGENTS.md 5번의 경험) |
| B. 서울 원본 + 미국 읽기 복제본 | 버림 — 저장(쓰기)이 늘 서울로 가서 기준에 못 미친다. 한국 사용자 데이터 전체가 미국에 복제되는 법적 부담도 생긴다 |
| Aurora DSQL(분산 DB) | 버림 — 여러 지역을 묶으면 **커밋마다 다른 지역과 왕복 두 번**(AWS 블로그). 서울 + 미국 동부를 묶으면 한국 사용자 저장까지 느려진다. 트랜잭션 3,000줄 · DDL 한 개 제약, JSON · 배열 칸 지원 미확인 |
| CockroachDB(행 단위 지역 고정) | 보류 — 기능은 가장 잘 맞지만 2지역 월 약 $260 이상, DB 이전 공사 |
| **A. 지역별 Supabase 둘** | **고름** — 추가 비용이 작고(프로젝트 하나 = 서버 크기만큼, 작은 크기 월 약 $10부터 — 확인 필요) 읽기 · 쓰기 모두 현지 |

## 구조

- **Supabase 프로젝트 둘**: 서울(지금 것) · 미국 동부(새로). 같은 조직 안.
- **개인 데이터는 사용자 홈 지역 DB 에만**(체크인, 운동 · 영양 · 투구 기록, 구속 세션 …). 한국 · 일본 · 대만 → 서울, 미국 · 멕시코 · 카리브 · 베네수엘라 → 미국 동부.
- **공통 콘텐츠는 서울 하나에만**(운동 · 드릴 · 자료실 · 패치노트). 미국 서버는 콘텐츠를 서울에서 한 번 읽어 캐시한다(`lib/library-cache.ts`, 캐시면 0ms) — 미국 DB 로 복사 · 동기화하지 않는다.
- **이메일 → 지역 목록은 서울 DB** — 로그인 때 어느 DB 인지 찾고, 가입 때 양쪽 이메일 중복을 막는다.
- **Vercel 프로젝트 하나에 리전 둘**(`icn1` + 미국 동부). 주소는 하나 그대로 — 아이폰 앱은 다시 굽지 않는다. 로그인한 사용자의 지역(쿠키)을 보고 그 지역 DB 를 쓴다.
- 3D 분석(Modal)은 지역 지정이 없어 대개 미국에서 돈다 — 북미 사용자에게는 오히려 가깝다.
- 구속 측정은 폰 안에서 계산해 어디서든 같다.

## 사용자가 느끼는 것

- 미국 동부 근처: 화면 이동 · 기록 · 저장이 서울과 같다.
- 미국 서부 · 멕시코 · 카리브: 요청마다 40~80ms 더해진다(추정) — 대부분 못 느낀다. 서부 사용자가 많아지면 서부 지역을 더한다.
- 로그인 한 번은 이메일 목록이 서울이라 0.2초쯤 느리다.
- 운동 · 드릴 목록은 미국 서버 캐시가 처음 찰 때 · 콘텐츠를 고친 뒤 한 번 느리다. **고친 콘텐츠가 미국 캐시에 반영되는 방식은 확인할 것.**
- 운동 · 드릴 영상은 서울 저장소라 첫 재생이 느릴 수 있다 — CDN 이 받아 두면 두 번째부터 빠르다. **확인하고, 부족하면 미국 저장소에 복사본.**
- 여행 중인 사용자는 홈 지역 DB 라 조금 느리다. 이사한 경우만 지역을 옮긴다.

## 평소 작업은 그대로

고치기 → 커밋 → push 한 번이면 두 리전에 함께 배포된다.
- DB 구조(마이그레이션): 빌드가 서울 → 미국 순서로 둘 다 적용, **한쪽이 실패하면 배포를 멈춘다**.
- 콘텐츠: 서울만 고치면 된다.
- 새 환경변수만 지역별 값 두 개.
- 특정 사용자 데이터를 고치는 스크립트는 그 사용자의 지역 DB 에서 돌린다.

## 지금 해 둘 것(한국 출시 단계 — 어느 길이든 필요)

1. 사용자 국가 · 지역 칸(DB) — 국가별 기능 · 요금 · 동의 설정에도 쓴다.
2. DB 접근을 한 함수 뒤로 모으기(`prisma` 를 직접 부르는 곳을 줄인다).
3. 저장하면 화면부터 바뀌게(즉시 반영) — 어디서든 체감이 빨라진다.
4. 새 코드는 사용자 기록과 운동 정보를 DB 에서 엮어 읽지 말고 캐시에서 찾는다.

## 해외 출시 때 할 일

**한 번**: 미국 Supabase 만들기(마이그레이션 85개 + 저장소 버킷 설정 — 비공개 · 50MB · `application/json` 허용) · 이메일 → 지역 목록 · DB 고르는
함수 · Vercel 미국 리전 · 지역별 환경변수 · 스크립트(백업 · 복구 · 패치노트 · 구속 실험 도구)가 지역을 골라 돌게 · 관리자 화면 지역 탭 ·
사용자 기록과 운동 정보를 엮어 읽는 약 11개 파일을 캐시 조회로 · 개인정보 방침에 보관 위치.

**계속**: 마이그레이션 두 번(자동) · 백업 둘(`npm run backup` 이 둘 다) · 전체 통계는 두 DB 합산 화면 · 지역 이동 요청은 옮기는 스크립트
(외래키가 없어 비교적 쉽다) · Supabase 알림 두 프로젝트 · 시험 계정 지역별 하나 · AGENTS.md DB 규칙을 두 DB 기준으로.

**남는 숙제**: 코치(한국) ↔ 선수(미국) 팀 기능은 두 DB 를 가로질러 읽는다 — 팀 기능을 만들 때 설계.

## 같이 정한 것(해외 출시 관련)

- 쿠바는 미국 제재로 앱스토어 · 구글 플레이 배포 · 결제가 막혀 있어 제외(확인 필요).
- 나라마다 기능 · 요금 · 동의를 다르게 — DB 를 나누지 않고 '국가 설정 한 곳'으로. 가격은 앱스토어에서 나라별로.
- 영양은 식약처 DB · 한식 식단 틀이라 나라별 식품 DB(미국 USDA, 일본 식품성분표, 대만 TFDA)와 식단 틀이 따로 필요하다.
- 출시 전에 나라별 법률 자문(미성년자 동의 — 한국은 만 14세 미만 법정대리인 동의로 알고 있어 지금 '만 13세부터'와 부딪힐 수 있다, 건강정보 민감정보, 자동결제 고지, 의료 · 건강 효능 표현).
