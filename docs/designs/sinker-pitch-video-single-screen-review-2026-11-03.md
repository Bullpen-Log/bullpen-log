# 싱커 투구 영상 비교 한 화면 검토와 개선 계획

검토일 2026-11-03. 기준 커밋 `a7bbda63`, 한 화면 구현 `dc0cc1aa`. 원격 `origin/main`과 앞섬·뒤처짐 0/0을 확인했다. 기존 다른 세션의 변경은 보존했다.

**영상 중심의 한 화면 구조는 반영됐지만, 모든 도구를 스크롤 없이 편하게 쓸 수 있다는 완료 기준은 아직 충족하지 못한다.** 기능을 더 추가하기 전에 작은 화면의 도구 경계, 긴 메모, 키보드, 개별 재생의 중단 처리를 고쳐야 한다.

이번 작업은 검토와 계획이다. 앱 동작 코드는 바꾸지 않았고 커밋·푸시·배포도 하지 않았다. 사용자 지시에 따라 시뮬레이터·Metro를 실행하지 않았다. 아래 재현은 소스 실행을 이용한 모의 검사와 치수 계산이며 실제 아이폰의 화면·터치·키보드·디코더 검증과 구분한다.

## 잘 반영된 부분

1. 비교 화면의 긴 ScrollView를 없애고 영상 무대, 타임라인, 재생 줄, 상황별 도구를 같은 작업 화면에 배치했다.
2. 고정된 창 높이 비율 대신 남는 무대 공간을 쓰고, 원본 영상 비율별로 나란히·위아래 후보를 비교한다. 집중 보기와 수동 배치도 남아 있다.
3. 맞추기·그리기·장면·메모를 한 번에 모두 펼치지 않고 문맥별 도구로 바꾼다. 팝업은 하나씩 열고 뒤로 닫는 순서가 있다.
4. 타임라인, 장면 이동, 반복 구간, 주석 편집, 원본 좌표 유지에 관한 기반이 있다. 배치를 바꿀 때 Pane의 소스 키를 유지하는 회귀 검사도 통과한다.
5. 투구 탭에 3D·영상 비교·구속·ABS의 2×2 진입점이 있다. 기능 공개 정책과 기존 잠금을 임의로 바꾸지 않았다.
6. 문서 저장·복원·버퍼링 등 이전 교정의 회귀 검사가 계속 통과한다. 다만 검사 통과를 실제 기기 동기화 정확성으로 해석할 수는 없다.

## 우선 고칠 문제

P1은 일상적인 핵심 사용 흐름을 막을 수 있어 다음 구현에서 먼저 고칠 항목이다. P2는 조작의 일관성과 접근성을 개선할 항목이다.

### SS01 작은 세로 화면에서 그리기 버튼 줄이 폭을 초과한다

**P1 · 소스와 모의 컴포넌트 검사로 확인.**

근거: `workbench.tsx:1548`, `:1580`, `:2109`와 `workspace-parts.tsx:208` 부근.

두 영상의 그리기 첫 줄에는 A/B 전환, 빠른 도구 네 개, 선택·이동, 도구 전체로 총 일곱 버튼이 나온다. 각 버튼은 44pt이며 간격은 4pt, 부모 좌우 패딩은 합계 16pt다.

`7 × 44 + 6 × 4 + 16 = 348pt`

320pt 화면에서는 최소 필요 폭이 28pt 초과한다. 세로 화면에는 줄바꿈이나 페이지 분할도 없다. 실제 Workbench가 생성하는 버튼 일곱 개와 행 스타일을 추가 검사에서 확인했다. 실제 기기에서 어느 버튼이 얼마나 잘리는지는 미측정이다.

둘째 줄 역시 색·굵기·설정·undo·redo·선택 삭제·완료를 모으면 선택 상태에서 더 넓어진다. 단순히 줄바꿈하면 영상 공간이 줄어들어 원래 불편이 돌아온다.

**개선:** 좁은 폭에서는 `A/B · 현재 도구 · 스타일 · 되돌리기 · 완료`를 고정한다. 현재 도구를 누르면 선·각도·자유선·점과 전체 도구를 페이지형 선택창에서 고른다. redo·삭제는 선택 상태 메뉴로 옮기고 위치를 일관되게 유지한다. 넓은 폭에만 빠른 도구를 추가 노출한다. 기존 도구는 없애지 않는다.

**통과 기준:** 320pt, 375pt, 큰 글씨, 선택 도형 있음/없음에서 모든 버튼 경계가 부모 안에 있고 완료·undo가 계속 보인다. 추가 도구에 접근하려고 화면을 스크롤하지 않는다.

### SS02 팝업의 한 행이 너무 크면 페이지 분할로도 해결되지 않는다

**P1 · 실제 Inspector와 순수 페이지 함수의 조합으로 확인.**

근거: `workspace-parts.tsx:115` 이후, `workspace-layout.ts:239`, `workbench.tsx:1194`, `:1335`, `:1819`.

Inspector는 행을 묶어서 페이지로 나누지만 큰 행 자체를 쪼개지는 않는다. 팝업 높이 160pt에서 본문 예산은 96pt다. 겹쳐 보기의 여덟 동작을 폭 232pt에 넣은 행의 현재 추정 높이는 144pt다. 측정 높이를 반영해도 `packRows([144], 96)`은 같은 행을 한 페이지에 그대로 둔다. 컨테이너에는 `maxHeight:160`과 `overflow:'hidden'`이 있다.

여섯 투구 장면을 한 Wrap에 넣는 경우, 긴 메모 조각, A/B 장면 그림을 세로로 쌓는 장면 모음도 같은 구조를 사용한다. 이 모두가 실제 기기에서 잘렸다고 단정하지는 않지만, 초과 행을 해결할 경로가 없다는 것은 확인했다.

또 `inspAvail = stageHeight - 12`라 도구창이 영상 무대 대부분을 차지할 수 있다. 영상과 조작을 함께 보려는 목적에 맞지 않는다.

**개선:** 페이지 단위를 큰 Wrap이 아닌 개별 버튼·짧은 항목으로 바꾼다. 공간 맞춤은 방향 패드, 크기 조정, 초기화를 구분한다. 사건 선택은 화면에 맞는 수만큼 나눈다. 장면 모음은 짧은 가로 화면에서 A/B를 좌우로 두거나 한 사건씩 전환한다. 본문보다 큰 항목은 개발 검사에서 실패로 처리하고 재분할한다.

팝업의 영상 가림 비율도 관리한다. 기본 목표는 무대의 약 1/3 이내다. 불가능한 짧은 화면에서는 상황 도크의 페이지를 바꾸거나, 최소 영상 미리보기를 남기는 명시적인 편집 모드로 전환한다. 글씨·터치를 줄이거나 내용을 숨겨 목표를 맞추지 않는다.

**통과 기준:** 모든 페이지의 실제 자식 높이 합이 가용 본문 높이 이하이고, 첫 페이지부터 마지막 페이지까지 모든 기존 명령에 도달한다. 팝업을 열어도 타임라인·재생·닫기가 가려지지 않는다.

### SS03 짧은 가로 화면에서 키보드 편집 공간이 부족하다

**P1 · 소스 치수에 따른 하한 계산. 실제 iOS 키보드 재현은 아님.**

근거: `workbench.tsx:1667`, `:1824`, `note-editor.tsx:29`, `:100`.

입력 줄 수를 최소 두 줄로 강제한다. 기본 글씨에서는 머리 44 + 입력칸 60 + 동작 줄 최소44 + 간격12로 편집기만 최소160pt다. 여기에 키보드 높이만큼 하단 패딩을 따로 둔다.

가정한 창 높이 390pt, 키보드 216pt, 위 안전영역 0인 경우:

`화면 머리44 + 편집기160 + 키보드 패딩220 = 최소424pt`

영상 높이를 0으로 줄여도 34pt가 초과한다. 안내 문구가 생기면 더 커진다. 이 계산은 가능한 입력값에서 구조가 성립하지 않는다는 증거이며 특정 아이폰 키보드가 반드시 216pt라는 주장은 아니다.

**개선:** 키보드와 작업 영역의 실제 교차 높이를 한 번만 뺀다. 키보드 프레임 변경·회전도 반영한다. 편집 모드에서는 중복 제목 줄을 합치고 취소·저장을 하나의 고정 동작 줄에 둔다. 아주 짧은 화면은 한 줄 입력 페이지와 작은 정지 미리보기로 전환한다. 저장·취소와 현재 입력 문장을 먼저 보장한다. 일반 분석 모드의 타임라인은 저장 후 같은 위치로 복원한다.

**통과 기준:** 가로·세로·키보드 높이 변경·예측 입력 켜짐·160/200% 글씨에서 저장·취소·입력 중 문장이 키보드와 겹치지 않는다. 회전 전후 초안과 커서 위치가 유지된다.

### SS04 여러 줄 붙여넣기는 스크롤 없는 메모 칸 밖으로 쌓인다

**P1 · 실제 NoteEditor를 모의 훅에 연결해 재현.**

근거: `note-editor.tsx:31`, `:45`, `:72`, `workspace-layout.ts:164`, `:191`.

초기 페이지 분할은 글자 수를 기준으로 하고 줄바꿈의 높이를 충분히 계산하지 않는다. 입력 중 `onChangeText`는 새 문자열을 그대로 현재 페이지에 넣는다. 입력칸은 `scrollEnabled:false`다. 넘침을 감지하면 `maxLength`만 현재 길이로 바꾼다.

검사에서 높이60pt의 두 줄 입력칸에 12줄을 붙여넣었다. 값은 12줄 그대로지만 페이지 수는1, 내부 스크롤은 꺼짐, maxLength는38이었다. 글자 자체는 초안에 남지만 뒤쪽 내용을 페이지를 넘겨 확인·고칠 수 있게 분배하지 않는다. 새 페이지 추가도 넘친 글을 옮기지 않는다.

**개선:** 초안 원문을 하나로 보관하고 페이지는 원문 구간으로 관리한다. 줄바꿈·폭·실제 텍스트 높이를 고려해 분할한다. 붙여넣기와 편집 완료 시 넘친 내용을 다음 페이지로 보존한다. 한글 조합 중에는 분할을 확정하지 않고 조합 완료 시 처리한다. 전역 커서 위치를 저장하고 현재 편집 위치가 포함된 페이지를 유지한다. 글자 수 제한은 전체 원문에 적용한다.

**통과 기준:** 12줄, 빈 줄 다수, 긴 한글 문장, 이모지, 기존 페이지 중간 삽입·삭제·붙여넣기에서 글자·줄바꿈이 보존되고 모든 부분에 접근한다. 페이지 합치기가 원문과 같고 숨겨진 입력 내용이 없다.

### SS05 맞추기 중 개별 재생이 백그라운드 중단 처리 밖에 있다

**P1 · 실제 Workbench와 transport-hook을 함께 실행한 모의 재생기 검사로 재현.**

근거: `workbench.tsx:217`, `:800`, `:854`, `transport-hook.ts:311`.

맞추기 단계의 A/B 단독 재생은 공통 재생 상태 기계 밖에서 직접 `player.play()`를 호출한다. transport의 백그라운드 처리는 상태가 idle이 아닐 때만 중단을 보낸다. Workbench의 별도 AppState 처리는 저장 flush만 한다.

검사 순서는 `맞추기 → A 재생 → AppState background`다. 실제 소스의 두 AppState 리스너를 호출했지만 가짜 A 플레이어는 `playing:true → true`로 남았다. 실제 iOS에서 OS가 재생을 막는지는 별도이며, 앱 코드가 명시적인 중단을 보장하지 않는 문제다.

**개선:** 함께/A/B 재생 모두 같은 생명주기 정책에 포함한다. 백그라운드·화면 이탈·소스 교체·원본 오류·권한 변경 시 양쪽 재생을 중단하고 오래된 탐색·재개 의도를 무효화한다. 돌아와도 자동으로 틀지 않는다. 단순히 interval만 지우는 방식으로 끝내지 않는다.

**통과 기준:** 함께·A만·B만, 맞추기·일반 비교 각각에서 background/blur/unmount 후 둘 다 정지한다. 복귀 시 마지막 위치를 유지하고 사용자가 누르기 전에는 재생하지 않는다.

### SS06 A와 B 선택의 의미가 조작마다 다르다

**P2 · 소스 분기로 확인.**

근거: `workbench.tsx:824`, `:846`, `:854`, `:870`.

일반 비교에서 A를 선택하면 탐색과 한 장면 이동은 A만 바뀌지만, 재생을 누르면 대상이 함께로 바뀐다. 접근성 이름은 '함께 재생'이라 상황을 일부 설명하지만 사용자가 보는 재생 아이콘만으로는 동작을 예측하기 어렵다. 원래 R06의 독립·연동 재생 취지와도 차이가 있다.

**개선:** `함께/A/B`는 탐색·장면 이동·재생 전부 같은 대상을 뜻하게 한다. 독립 재생 뒤 함께로 복귀할 때 어느 시점을 기준으로 다시 붙일지 정하고 화면에 짧게 알린다. 좁은 화면에서는 누를 때마다 순환시키기보다 세 대상을 한 번에 보여주는 작은 선택창을 쓴다. 사건 분석의 실제 시간 비교와 동작 길이 정규화 모드는 계속 구분한다.

**통과 기준:** A 선택→재생은 A만, B 선택→재생은 B만 동작한다. 함께 복귀 기준·반복·오류·버퍼링 정책이 시험과 UI 설명에서 일치한다.

### SS07 큰 글씨 대응을 배율 상한으로 대신한 부분이 있다

**P2 · 명세와 소스의 불일치.**

근거: `workspace-parts.tsx:62`, `:88`, `note-editor.tsx:28`, `workbench.tsx`의 도크·제목.

단추는 주로1.3~1.4배, 입력칸은2배로 제한한다. 기존 화면 계산 시험도 이 상한을 반영한다. 따라서 '200% 설정 조합 시험 통과'가 모든 글자가200%로 표시돼도 사용 가능하다는 뜻은 아니다. 명세의 배율을 막지 말라는 요구는 충족하지 못한다.

**개선:** 이 기능의 핵심 글자부터 시스템 배율을 따르게 하고 실제 높이로 페이지 항목 수를 줄인다. 접근성 모드에서는 세부 설명·보조 버튼을 다른 페이지로 옮기되 주요 동작·현재 대상·선택 도구는 이름을 확인할 수 있어야 한다. 앱 전체 상한을 한 번에 제거하지 않는다.

**통과 기준:** 배율 상한을 적용한 계산과 실제200% 텍스트 검사를 구분한다. 버튼의44pt 이상 타깃, 읽을 수 있는 이름, 포커스 표시, 선택 상태를 유지한다. VoiceOver로 닫기·다음 쪽·저장까지 화면 이동 없이 도달한다.

## 사용자 편의를 높이는 작업 흐름

### 처음 비교를 시작할 때

- 투구 탭의 영상 비교를 누르면 최근 비교를 이어 보거나 새 영상을 고르는 목적을 바로 구분한다. 현재 공개 정책의 잠금은 별도로 유지한다.
- 선택 화면에는 A/B에 넣은 영상과 촬영일·출처를 작게 표시한다. 영상을 둘 고르면 바로 맞추기로 이동하며 추가 설명 화면을 끼우지 않는다.
- 기본 기준은 앞발 착지로 하되 다른 사건·직접 기준을 선택할 수 있게 한다. A 지정 후 B를 강조하고 완료 후 공통 기준 시점에서 멈춘 채 보여준다. 지정 되돌리기·맞추기 취소는 보존한다.
- '자동으로 정확히 맞췄다'는 표현은 실제 자동 탐지와 검증이 없으면 사용하지 않는다.

### 매일 반복해서 비교할 때

- 최근 비교를 한 번 눌러 열고, 이전 위치·속도·기준·그림을 복원한다. 재생은 사용자가 누른다.
- A 고정·B 차례로 보기에서는 이전/다음 B를 같은 위치에 둔다. 짝별 기준·메모가 섞이지 않아야 한다.
- 현재 도구를 잊지 않게 선택 상태와 작은 이름을 표시한다. 불투명한 그림 버튼만 늘리지 않는다.
- 오류는 실제 영상의 어느 쪽인지 표시한다. 새 영상 연결·재시도·취소가 같은 화면에서 가능해야 한다.

### 도구를 사용할 때

- 재생·멈춤, 이전/다음 장면, 대상, 속도는 위치를 유지한다. 기능별 긴 도움말을 상시 노출하지 않는다.
- 좁은 그리기 도크는 현재 도구 중심으로 구성한다. 색·굵기는 스타일 하나로 묶고 선택창에서 미리 결과를 보여준다.
- 팝업을 열어도 사람의 몸·릴리스 지점·타임라인을 동시에 확인할 수 있게 배치한다. 가용 공간이 없으면 명시적인 작은 편집 페이지로 전환한다.
- 자주 쓰는 기능은 첫 단계에 둔다. 사용 빈도는 아직 측정하지 않았으므로 '선·각도·선택'의 우선 노출은 초기 제안이며 실제 사용 후 조정한다.

### 메모를 남기고 돌아올 때

- 사용자에게 페이지 분할 자체를 관리하게 하지 않고 입력·붙여넣기 결과를 안전하게 다음 쪽으로 이어 준다.
- 저장·닫기·초안 버리기의 뜻을 구분한다. 현재 초안은 Workbench 메모리 Map에 있어 앱 재시작까지 보존한다고 설명하면 안 된다.
- 개선 시 계정·문서·영상·시점에 연결한 로컬 초안을 별도로 보관하고 복구를 제공한다. 명시적인 버리기만 삭제하며 로그아웃·다른 계정 접근은 격리한다. 이 기능에 서버 동기화를 추가하지 않는다.

## 검증 계획

1. 치수: 320×568, 375×667, 390×844, 430×932pt와 각각 가로, iPad·좁은 분할창. 기본·160%·200% 글씨, 세 가지 테마.
2. 상태: 무영상/한 영상/두 영상, 세로/가로/혼합, 긴 제목, 원본 없음, 로딩, 실패, 저장 실패, 팝업 각 페이지, 도형 선택 유무.
3. 메모: 빈 글/긴 글/줄바꿈12개 이상/이모지/한글 조합/붙여넣기/가운데 수정/회전/키보드 높이 변경. 원문·커서·초안 복구를 확인한다.
4. 재생: 함께/A/B × 보기/맞추기 × 재생/탐색/버퍼링/반복 × background/blur/복귀/소스 교체. 단독 재생도 같은 시험에 넣는다.
5. 경계: 실제 페이지 안의 자식·버튼 경계와 키보드 교차를 측정한다. `ScrollView가 없다` 또는 stage 계산이 맞는다는 조건만으로 통과시키지 않는다.
6. 사용 흐름 목표: 최근 비교 열기1회, 그리기 진입1회, 그리기 완료1회, 주요 사건 이동1~2회, 부가 스타일 선택2회 이내를 시작 목표로 둔다. 영상 선택·사건 찾기의 실제 소요 시간은 자료와 사용자에 따라 달라 따로 기록한다.
7. 가능한 비시뮬레이터 자동 검사를 먼저 한다. 실기기가 없으면 실제 화면·디코더 동기화·루페·제스처·키보드·VoiceOver·발열은 미검증으로 남긴다. 기기 사용성 확인 전 '전부 완료'로 올리지 않는다.

## 원래 전체 기능과 구분할 것

한 화면 개편이 원래 Dartfish 수준의 모든 기능 구현 완료를 뜻하지 않는다. 현재 대장에는 음성 메모·해설 녹화, 주석을 합성한 정지/동영상 파일 출력, 공유·클라우드 동기화, 실제 프레임 PTS 읽기 등이 미완료 또는 차단으로 남아 있다. 수동2D 값은 실제3D 관절값이나 의학적 판단으로 표현하지 않는다.

지금 권장하는 순서는 **한 화면 핵심 사용성과 재생 안정화 → 정밀 시간/출력 네이티브 기능 → 공유·코치 검토**다. 미완료 출력 기능을 주요 동작처럼 노출하기보다 실제 사용할 수 있는 비교·그리기·장면·글 메모에 초점을 맞추는 편이 사용자 목적에 맞는다.
