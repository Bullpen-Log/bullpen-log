## 1. [high] 지운 뒤에도 공개 영수증이 분석과 결과를 약속한다

- 자리: `components/intake/status-steps.tsx:101`
- 재현: PGlite로 확인. 검증까지 끝나고 분석 · 공개를 안 한 접수를 90일에 지우면 loadPublicState 값은 screen 'receipt', analysis 'ready', statusText '파일을 확인했어요. 분석을 기다리고 있어요'다. 화면 머리는 '영상이 잘 도착했어요 / 분석 결과가 준비되고 공개되면 이 링크에서 확인할 수 있어요.'이고, 같은 화면의 줄은 '원본 지운 날'과 '보유 기간이 지나 원본을 지웠어요'다. 그런데 새 분석은 original_purged로 막혀 있어서 고침을 받기 전에는 결과가 나올 수 없다. 같은 뿌리의 경우가 셋 더 있다. analysisStatus 'failed'면 '담당자가 영상을 다시 확인하고 있어요'(lib/intake/state.ts:270, 볼 영상이 없다). 고침이 기간 끝난 채 지워지면 머리가 '접수된 내용은 그대로 있어요.'(status-steps.tsx:106). 고침을 거두면 다시 '분석을 기다리고 있어요'로 돌아간다.
- 고칠 방향: 상태에 '원본을 다 지웠다'를 입력으로 넣어 publicStatusText와 HEADS가 다른 글을 고르게 한다. 분석 성공 없이 지운 접수는 '보유 기간이 끝나 원본을 지웠어요. 분석이 필요하면 링크를 보내 준 분에게 문의해 주세요' 쪽으로, correction_closed 글도 지운 경우에는 '그대로 있어요'를 빼고, 시험에 지운 뒤 글 격자를 더한다.

## 2. [high] 삭제 시작 표시가 없어, 시계가 다시 돌아도 원본이 지워지거나 지워진 파일이 '있음'으로 남음

- 고칠 방향: remove 전에 같은 잠금 트랜잭션에서 삭제 시작 표시를 남깁니다(예: IntakeSubmission.purgeStartedAt이나 자산 'purging' 상태). 표시가 있으면 publishRun · finalizeSubmission · requestCorrection · startIntakeAnalysis를 막고, 다시 돌 때는 not_due로 끝내지 않고 끝까지 지워 'purged'로 적습니다. 시계를 다시 돌리고 싶으면 표시를 건 뒤에는 그 접수의 고침으로 새 파일을 받게 합니다.

   - 상한이 되면 얼린 원본만 지우고, 고침 중 고른 새 파일은 남기며, 지운 칸을 요청에 넣습니다.
   - 이 값은 사용자가 정한 90일을 넘길 수 있어서 동의 글에 적었습니다. 확인이 필요합니다.
3. **실행이 끝난 뒤에도 1시간 기다립니다.** 분석 서버가 미리보기를 늦게 쓸 수 있어서입니다.
4. **지울 날이 지나면 지우기 전이어도 새 분석을 막습니다.** 삭제와 새 실행이 부딪히지 않게 한 것입니다.
5. **지운 뒤 글만 고치라고 요청해도 지운 칸이 저절로 들어갑니다.** 지운 파일로는 판을 얼릴 수 없어서입니다.
6. **`withdrawnAt` 칸을 새로 뒀습니다.** 철회할 동의 줄이 없는 접수가 있어 동의 줄 시각을 쓸 수 없었습니다.
7. **삭제 일감은 시도를 다 써도 6시간마다 다시 겁니다.** 멈춘 동안은 상세의 '멈춘 일감'에 보입니다. 경로 모양이 어긋나면 아무것도 안 지우고 던집니다.
8. **`reserveAsset`에서 지운 자산은 없는 것으로 봅니다.** 같은 파일 판정, 합계 한도, 자산 개수에서 모두 뺍니다.
9. **동의 글에 규칙을 더 적었습니다.** 요청하신 문장 외에 공개한 접수의 철회, 시계 다시 돌기, 고침 기다림, 7일 유예, 미리보기 삭제를 사실대로 넣었습니다.
10. **철회 화면에는 날짜를 안 넣었습니다.** 날짜는 영수증에만 보입니다.

# 안 본 것과 남는 위험

- 호스팅 Supabase의 `remove` · `stat` 동작과 Vercel 크론은 가짜 저장소로만 봤습니다.
- 격리 브라우저 시험은 다시 안 돌렸습니다. 이번 화면 변경은 코드와 정적 그리기까지만 봤습니다.
- 닫힌 실행의 미리보기가 삭제 뒤에 늦게 올라오면 남습니다. 1시간 기다림은 이 위험을 줄일 뿐입니다.
- 관리자가 내려받은 사본과 분석 서버 쪽 사본에는 이 삭제가 닿지 않습니다.
- 임시 파일 정리가 지운 뒤 답이 끊기면, 판에 오른 적 없는 그 파일은 다음 정리까지 `replaced` · `abandoned`로 남아 관리자 화면이 있다고 말합니다. 다음 정리가 없어진 것을 보고 끝내서 저절로 풀립니다. 여기에 `purging`을 쓰면 보유 삭제가 판 파일만 다룬다는 약속을 갈라야 해서 표시를 두지 않았습니다.
- 임시 파일 정리는 지우기 직전에 접수를 다시 보지만, 그 뒤 저장소를 부르는 사이의 철회는 못 잡습니다. 철회 앞에 정한 지우기로 칩니다. 판에 오른 적 없고 이미 여유가 지난 파일뿐입니다.

`intake:public-test` 는 전체를 잇달아 돌릴 때 한 번 끝 코드 1(finalize 의 Prisma 오류)로 끝났고 다시 돌리면 통과했다. PGlite 트랜잭션 5초 초과로 짐작하지만 확인하지 못했다.
