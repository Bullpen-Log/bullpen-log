# 앱 화면을 앱 안으로(①안) — 요약

2026-10-16 · 상태: 제안(아직 정하지 않음). 수익 구조 · 서버 비용 이야기에서 나온 세 가지 길(① 껍데기는 두고 화면을 앱 안에 · ② React Native 로 다시 · ③ Swift 로 완전 네이티브) 가운데 ①의 요약이다.

## 1. 무엇을 바꾸나

- **지금**: 아이폰 앱은 껍데기(Capacitor)다. 켜면 `https://bullpen-log.vercel.app/today` 를 불러오고(`mobile/capacitor.config`), 화면은 서버(Vercel)가 그려 보낸다.
- **바꾼 뒤**: 화면 코드(React)를 앱 안에 넣고, 서버는 데이터(API)만 준다. 웹사이트는 같은 코드로 그대로 둔다.
- 카메라(구속 측정 · 촬영) · 영상 폰 저장 · 햅틱 같은 Swift 부품(약 4천 줄)은 그대로 쓴다.

## 2. 왜

| 얻는 것 | 까닭 |
|---|---|
| 빨라진다 | 앱을 켜거나 탭을 옮길 때 서버가 화면을 그려 주길 기다리지 않는다 |
| 서버 계산 비용이 준다 | 앱을 열 때 서버가 탭 넷을 한꺼번에 그리던 일(판 넘기기)이 폰으로 간다. 서버는 데이터만 준다 |
| 오프라인으로 일부 쓸 수 있다 | 5단계(선택)까지 가면 불펜에서 인터넷 없이 기록부터 남긴다 |

**안 바뀌는 것**: DB 조회 수(5단계 전까지) · 앱 내 결제(지금 구조로도 붙일 수 있음) · PC 관리자 화면(웹으로 남긴다).

## 3. 지금 코드 상태

- TypeScript 약 20만 줄: `app` 7.7만 · `components` 3만 · `lib` 9만.
- 화면과 상관없는 계산 약 6.1만 줄(`lib/engine` · `lib/report` · `lib/nutrition` · `lib/program` · `lib/velocity-engine` · `lib/pitch-3d`)은 그대로 가져간다.
- 화면 51개 · 서버 액션 파일 32개 · API 18개. `app` 안에서 DB(`@/lib/prisma`)를 직접 부르는 파일이 55개(서버 액션 29개 포함) — 이 55곳이 바꿀 대상이다.
- **이미 좋은 점**: 대부분 화면이 "서버 `page.tsx` 가 읽고 → 클라이언트 화면에 props 로 넘김" 꼴이다(예: `app/(app)/videos/videos-page.tsx` → `VideosClient`). 클라이언트 화면은 거의 그대로 두고 읽는 부분만 API 로 바꾸면 된다.
- 로그인은 쿠키 세션이다(`lib/session.ts`, `next/headers` 의 `cookies`).

## 4. 단계

0. **정하기(사용자)** — 7절의 넷.
1. **API 층** — 화면마다 지금 쓰는 읽기 함수(`load.ts` 등)를 그대로 부르는 GET API, 서버 액션 32개는 같은 함수를 부르는 POST API. 웹은 지금처럼 서버 액션을 써도 된다.
2. **로그인 토큰** — 앱 안 화면은 출처가 달라(`capacitor://localhost`) 쿠키가 붙지 않는다. 앱은 토큰을 키체인에 두고, 서버는 쿠키 · 토큰 둘 다 받는다.
3. **화면 잇기, 탭 하나씩** — 웹(`page.tsx` 가 서버에서 읽음)과 앱(API 에서 받음)이 같은 클라이언트 화면을 쓴다. 홈 → 투구 기록 → 트레이닝 → 영양 → 하위 화면. 이 단계까지 앱은 여전히 사이트를 불러오므로 **중간에 멈춰도 앱은 돈다.**
4. **앱 전환** — 모든 화면이 API 로 돌면 `server.url` 을 빼고 앱 안 화면을 켠다. 판 넘기기(`app/(app)/@home` 같은 병렬 경로)는 서버가 그리는 구조라 앱 쪽은 따로 짜야 할 수 있다.
5. **(선택) 오프라인 우선** — 폰에 DB(SQLite)를 두고 나중에 서버와 맞춘다. DB 비용까지 줄지만 한 단계 더 큰 일이다.

## 5. 잃는 것 · 조심할 것

- **화면을 고칠 때마다 앱 새 판이 필요하다.** 지금은 Vercel 에 올리면 앱에도 바로 반영된다. 바꾸면 TestFlight · 심사를 거친다. 대안은 화면 파일만 따로 내려받는 라이브 업데이트(유료 서비스가 있다, 애플 규칙 안에서 써야 함).
- 한동안 두 길(웹 = 서버에서 읽기, 앱 = API)을 같이 시험해야 한다.
- 앱 안 화면을 만드는 방식(Next 정적 내보내기 또는 따로 빌드)은 이 저장소의 Next 16.3.6 문서(`node_modules/next/dist/docs/`)로 먼저 확인한다 — `AGENTS.md` 맨 위 규칙.
- DB 구조는 안 바뀐다(`AGENTS.md` 2번 해당 없음).

## 6. 시간(Claude 기준 어림)

| 단계 | 어림 |
|---|---|
| 1 API 층 | 3~5일 |
| 2 로그인 토큰 | 1~2일 |
| 3 탭 넷 | 탭마다 2~4일 |
| 3 하위 화면 | 1~2주 |
| 4 앱 전환 | 2~3일 |
| 합계(1~4) | 4~6주 |

5단계(오프라인)는 따로 잰다. 폰 시험 · 심사 기다림은 사용자 몫이라 빠져 있다.

## 7. 정할 것(사용자)

1. 업데이트 방식: 화면을 고칠 때마다 앱 새 판으로 갈지, 라이브 업데이트를 쓸지.
2. 5단계(오프라인)까지 갈지.
3. 안드로이드를 같이 낼지 — ①은 Capacitor 라 안드로이드 껍데기를 더하면 되지만, Swift 부품(카메라 등)은 Kotlin 으로 다시 짜야 한다.
4. 누가 맡을지 — 앱 틀은 금윤호 영역, 다른 탭도 영역이 나뉘어 있어 HANDOFF 로 맞춘다.
