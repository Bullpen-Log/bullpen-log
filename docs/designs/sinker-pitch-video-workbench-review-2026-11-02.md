# 투구 영상 비교 구현 검토 · 개선 계획

## 판단

설계 방향과 구조 분리는 잘 반영됐다. 투구탭의 2×2 도크, 공통 비교 엔진, 로컬 비교 문서, 주석, 투구 장면, 수동 기준과 정규화 모드가 들어왔다. **다만 아직 전체 명세를 충족한 완성품은 아니며, 기능 추가보다 저장·복원·재생 연결의 결함 교정이 먼저다.**

구현 대장의 자체 분류는 R01–R42 중 `implemented / runtime unverified` 16개, `in progress` 16개, `blocked` 3개, `not started` 7개다. 이는 완료율이 아니다. 일부 '구현됨' 항목에서도 아래 결함을 확인했다. 검토자는 이 상태를 실제 기기 검증으로 올리지 않았다.

이 검토에서는 앱 코드를 수정하지 않았다. 시뮬레이터·Metro·실기기를 실행하지 않았으며, 화면 디자인·실제 디코딩 동기화·터치·발열·배포 완료를 검증했다고 주장하지 않는다. 검사 범위는 현재 소스, 기존 테스트, 메모리 파일 어댑터, 실제 소스를 변환해 실행한 모의 훅 스케줄러다. 후자는 React Native 렌더러/실제 React 커밋 동작과 구분한다.

## 잘 반영된 부분

- 기존 3D·구속·ABS를 남기고 영상 비교를 주요 도구에 배치했다. 베타 잠금을 임의로 풀지 않았다.
- 문서·시간 계산·좌표·주석·저장·재생 상태 기계가 분리됐다. 원본 경로와 서명 URL도 구분한다.
- 한 영상 보기, 수동 기준 맞추기, 시작점 기준, 장면 표시, A 고정 다중 투구 검토의 기반이 있다.
- 원본 비율을 고려한 좌표 변환과 2D 측정, 슬로모션의 실제 시간이 모르면 비워 두는 원칙이 있다.
- 미구현 내보내기/목소리를 성공한 것처럼 표현하지 않고 한계를 명시했다.
- R01–R42 대장이 유지돼 남은 기능을 추적할 수 있다.

## 우선 수정할 결함

우선순위: P1 = 출시/일반 공개 전 교정 권장, P2 = 정확성·복구·핵심 사용성 보강. 아래 '재현'은 운영 자료를 쓰지 않은 로컬 모의 검사다.

### F01 · P1 · 최근 목록 경합이 참조 중인 영상의 삭제 판단으로 이어짐

근거: `native/src/compare/storage.ts:42`, `:66`, `:102`, `:134`, `native/src/compare/store.ts:69`.

문서별 저장은 직렬화하지만 공통 `index.json`의 읽기→수정→쓰기는 문서 간 직렬화되지 않는다. 서로 다른 문서가 동시에 저장되면 둘 다 같은 옛 목록을 읽고 마지막 쓰기가 다른 문서 항목을 지운다. 유효한 JSON이므로 다음 최근 목록 읽기도 자동 복구를 하지 않는다.

더 중요한 것은 삭제가 이 최근 목록만 순회해 자산 참조를 확인한다는 점이다. 목록에서 누락된 문서가 여전히 영상을 사용해도 고아 파일로 분류할 수 있다. `deleteComparison`은 그 결과를 실제 `LocalVideo.remove`에 넘긴다. 사진 앱 원본 삭제가 아니라 **앱 안 비교용 복사본의 잘못된 삭제 위험**이다.

재현:

1. 비어 있는 유효 인덱스를 준비한다.
2. 같은 두 영상 경로를 참조하는 문서 A/B를 병렬 저장한다. A는 참조 사본, B는 영상의 소유 문서로 둔다.
3. 실제 문서 파일 둘이 존재하지만 최근 목록에는 B만 남는다.
4. B 삭제 시 A가 남아 있음에도 두 영상 경로가 `orphanPaths`로 반환됐다.

개선: 계정 단위 인덱스/목록 복구/삭제/자산 정리를 하나의 작업 순서로 조율한다. 최근 목록은 검색용 인덱스이지 자산 소유권의 정답이 아니다. 전체 유효 문서/독립 자산 참조표로 검증하고, 읽기/복구 실패 시 삭제를 보류한다. 인덱스 500개 제한 밖 문서도 참조 검사에 포함한다. 삭제 실패를 성공으로 반환하지 않는다.

통과 기준: 병렬 저장 2개·여러 개에서 모두 조회됨. 인덱스를 일부 누락시키거나 깨뜨려도 참조 중인 영상이 고아로 나오지 않음. 삭제 중 저장·충돌 사본 생성·복구가 겹쳐도 원본/참조 복사본 보존.

### F02 · P1 · 최근 비교를 열면 마지막 상대 위치가 0으로 덮임

근거: `native/src/compare/ui/workbench.tsx:167`, `:242`, `:245`, `:252`.

초기 `times`가 저장된 `pair.rel`이 아니라 기준 장면으로 시작한다. 플레이어가 준비되기 전에도 `keepRel` 효과가 상대 위치 0을 문서에 반영한다. 플레이어가 준비된 뒤 `restoreRel`은 이미 바뀐 값을 보고 복원할 위치가 없다고 처리한다.

모의 훅 스케줄러로 **실제 Workbench 소스**의 효과 순서를 실행했다. A 기준 2초/B 기준 3초/저장 위치 +1.25초인 문서에서 `lastScheduledRel=0`, `restoreSeekCalls=[]`를 확인했다. 기기의 실제 React 렌더링 재현과는 구분한다.

개선: `loading → restoring → ready`의 복원 단계를 둔다. 초기 복원이 완료되기 전 위치 자동 저장 금지. 저장 목표를 변경 가능한 현재 문서와 분리하고, 양쪽 탐색 확인 뒤에만 새 위치 저장을 허용한다. active pair별 복원 키를 사용해 B 교체·A/B 교환·다중 투구 이동에도 적용한다. 한 영상 세션의 재생 위치도 별도로 보존한다.

통과 기준: +1.25초/음수/0초, 준비 순서 A→B/B→A, 재시도, 다른 B로 이동 후 복귀에서 같은 위치로 멈춘 채 복원. 복원 전 디스크의 위치가 바뀌지 않음.

### F03 · P1 · 버퍼링 재개가 현재 위치가 아닌 이전 재생 시작점으로 돌아감

근거: `native/src/compare/ui/transport-hook.ts:127`, `:136`, `:193`, `:199`.

`target.current`는 play를 누를 때 설정되지만 버퍼링이 시작될 때 현재 위치로 갱신되지 않는다. `bothReady` 이후 `seekThenConfirm`이 오래된 target으로 다시 탐색한다.

실제 transport-hook 소스를 가짜 플레이어와 모의 훅 스케줄러에 연결했다. 0초 재생→두 플레이어를 5초로 진행→B loading→ready 순서에서 A/B가 모두 0초로 돌아갔다. 네트워크/실제 디코더 시험은 아니다.

개선: 버퍼링 진입 시 공통 유효 위치를 고정해 resume target으로 저장한다. 요청 목표, 확인된 위치, 버퍼링 복구 위치를 분리한다. 사용자가 멈춤/탐색/뒤로가기를 누르면 intent와 세대를 무효화한다.

통과 기준: 5초 버퍼링 후 5초 주변에서 재개. 반복·정규화·짧은 공통 구간에서도 재생 시작점으로 되감기지 않음. 버퍼링 중 멈추면 준비되어도 자동 재생 안 함.

### F04 · P1 · 복구한 정상 앞판이 다음 저장 실패에서 손실될 수 있음

근거: `native/src/compare/storage.ts:55`, `:116`.

load는 깨진 json 대신 정상 prev를 읽을 수 있다. 그러나 다음 save는 json의 유효성을 확인하지 않고 '파일이 존재하면' prev로 이동한다. 깨진 json이 정상 prev를 덮은 뒤 tmp→json 설치까지 실패하면 정상 앞판이 사라진다.

재현: 정상 prev + 깨진 json → load는 `recovered:true` → tmp 설치 단계 실패 주입 → 이후 load는 `reason:corrupt`. 이 저장 어댑터 경로는 실제 순수 함수를 사용했다.

개선: 검증된 정상 판을 새 판 설치 확인 전까지 보존한다. 복구 상태를 저장에 전달하거나, 영구 세대 파일/검증된 교체 전략을 쓴다. 실패 시 tmp·prev를 무조건 정리하지 말고 복구 가능성을 우선한다. 실제 expo-file-system 어댑터의 move/덮어쓰기 의미도 검증한다.

통과 기준: write·기존 판 이동·새 판 설치·정리의 각 실패 지점에서 최소 하나의 정상 판을 다시 읽을 수 있음. 정상 앞판을 깨진 파일로 교체하지 않음.

### F05 · P2 · 기준 전 반복 구간이 저장 왕복에서 사라짐

근거: `native/src/compare/doc.ts:319`, `:379`.

영상의 절대 in/out과 기준 기준의 상대 반복 구간에 같은 range 파서를 쓴다. 상대 구간은 음수가 유효하지만 파서는 `start >= 0`을 요구한다.

실제 문서 함수로 `loop={start:-1,end:1}` → JSON 저장/parse를 실행하면 `loop=null`이 됐다.

개선: 절대 영상 범위와 상대 구간 파서/타입을 분리한다. 유한값과 start<end를 확인하고 해당 pair의 공통 구간과 교차 검증한다. 기준 변경 때 기존 loop를 재계산하거나 명시적으로 초기화한다.

통과 기준: -1~+1, 전부 음수, 전부 양수 반복 구간의 왕복 보존. 범위 밖·NaN·역전 값은 안전하게 거절.

### F06 · P2 · 새 스키마 문서를 저장 API가 덮어쓸 수 있음

근거: `native/src/compare/storage.ts:108`.

load는 schemaVersion이 높은 문서를 `newer`로 거절하지만 save는 owner 오류만 차단한다. `newer` 결과를 신규 문서처럼 취급해 현재 스키마로 덮는다. 화면 DocLoader가 보통 진입을 막으므로 현재 정상 진입마다 발생한다는 뜻은 아니지만, 저장 API의 버전 보존 보장이 깨져 있다.

재현: 디스크 schemaVersion 2/revision 7 준비→load `newer`→schemaVersion 1 문서로 save→성공하며 디스크 버전 1로 변경.

개선: missing만 새 문서 저장으로 처리한다. newer/owner/corrupt/io는 각각 명시적인 결과로 중단한다. 의도한 복구/교체는 별도 API와 사용자 흐름으로 분리한다.

통과 기준: 미래 스키마·소유자 불일치·읽기 실패에서 원본 바이트 불변. 정상 missing만 첫 저장 허용.

### F07 · P1 · 한 영상에서 추가 B를 사진 앱/촬영으로 고르는 흐름이 끊김

근거: `native/src/app/pitch/compare.tsx:126`, `native/src/compare/ui/workbench.tsx:670`, `native/src/compare/store.ts:76`.

첫 StartPicker에는 사진 앱/촬영이 있지만 Workbench의 B 선택은 일반 VideoGallery만 연다. 비교를 위해 가져온 사진/촬영 영상은 의도적으로 내 영상 목록에 등록하지 않는다. 따라서 앱 내 영상이 없는 새 사용자가 한 영상만 가져온 후 `비교 영상 추가`를 누르면 사진 앱에서 두 번째 영상을 고를 수 없다. 이미 들어온 비교용 source도 전체 선택 후보로 노출되지 않는다. A 교체도 독립적인 선택 흐름이 없다.

이 항목은 UI 소스의 분기/전달 props로 확인했다. 사진 선택기의 실제 기기 동작 검증과는 구분한다.

개선: `selectSource(slot, existingSelection)` 하나를 신규/추가/교체/재연결에서 재사용한다. 앱 내 영상·현재 문서 source·사진 앱·촬영·Files를 같은 선택기로 제공한다. A/B 취소 시 기존 pair/기준/편집 복원. 가져온 자료는 임시 소유 단계에서 문서 인계까지 추적하고 취소·화면 종료·계정 변경 시 정리한다.

통과 기준: 앱 내 영상 0개 계정에서 사진 하나→열기→사진 B 추가→맞춤 비교가 됨. 촬영 A+촬영 B, A만 교체, B 취소, 현재 source 재선택, 같은 파일 두 보기, 실패/중단 시 파일 누수 없음.

### F08 · P2 · 현재 고급 UI의 접근성/표현 정확성 추가 검증 필요

아래는 코드에서 확인한 구조/누락이며, 실기기 화면 결함으로 확정한 항목은 아니다.

- 현재 `worthSaving`은 편집하지 않은 한 영상 세션을 남기지 않는다. 기록 없는 간편 분석과 최근 재개 요구를 충족할지 정책을 명확히 하고, 비교용 복사본 유실/누수와 함께 처리한다.

## 기능 누락과 구현 결함의 구분

기존 대장은 미완료를 비교적 정직하게 적었다. 다음을 F01–F07의 버그와 구분해 남은 구현 범위로 관리해야 한다.

| 묶음 | 남은 기능 | 요구사항 |
| --- | --- | --- |
| 핵심 입력/정확성 | Files, 촬영 FPS/렌즈 제어 연결, PTS·편집된 슬로모션 시간 매핑, 정확한 장면 이동 | R02–R04·R07 |
| 분석 UI | 영상별 trim, 공간 정렬 UI, 점 단위 주석 수정, 필터/기준 투구 관리, 복사/재연결 UI | R09·R11·R13·R19·R20·R31 |
| 결과 활용 | 음성 메모, 주석 정지 화면/스토리보드 파일, 합성 영상, 해설 녹화, 실제 공유 | R15–R18·R23 |
| 투구 근거 | 3D 결과 연결 저장, 출처·시각·단위·정의판 관리 | R33 |
| 관리/협업 | 클라우드·오프라인 관리, 플레이리스트, 코치 권한 리뷰, 다중뷰 선택 UI | R21·R22·R24–R26 |
| 고급 수집/보조 | 두 기기 리플레이, 외부 카메라, 사건 후보/추적 보조 | R27·R28·R35 |

새 패키지가 없다는 것은 의존성/빌드 작업이 필요하다는 뜻이다. 모든 미구현 항목이 기술적으로 영구 불가능하거나 전부 DB 변경이 필요하다는 뜻은 아니다. Files·일부 정지 화면/공유·자체 촬영 모듈 연결은 기존 바닥/버전 API를 먼저 조사해 최소 변경을 결정한다. AVFoundation도 필요 기능별로 점진적으로 추가한다.

## 개선 실행 순서

### 1차 — 저장/복원/재생 신뢰성

대상 F01–F06. 기능을 늘리기 전에 작은 교정 묶음으로 처리한다.

1. 계정 작업 큐·참조 검사·복구 저장·미래 스키마 거절을 교정한다.
2. 초기 복원 관문과 pair별 재개 상태를 구현한다.
3. 버퍼링 복구 목표를 현재 공통 위치로 보존한다.
4. 상대 반복 구간의 파서를 분리한다.
5. 아래 재현을 **원하는 동작을 주장하는 회귀 검사**로 옮긴다. 테스트는 수정 전 실패/수정 후 통과해야 한다.

완료 관문: 저장 단계별 실패 주입·병렬 문서·누락 인덱스·복원 준비 순서·play→buffer→ready를 실제 저장/훅 연결 경로로 시험한다. 순수 상태 기계만 검사하지 않는다. 문서와 미디어를 잃지 않는 상태가 우선이다.

### 2차 — 두 영상 비교의 첫 사용 완결

대상 F07, R02·R05·R19·R31. 앱 내 영상이 없는 사용자를 기준으로 선택/가져오기/추가/교체/취소를 통일한다. 한 영상 재개와 임시 파일 정리 정책을 함께 구현한다. 과거 source 재선택·기준 투구 A 고정을 완성한다.

완료 관문: '앱 내 영상 0개→촬영/사진 A→B 추가→수동 기준→함께 재생→닫기→최근 재개'가 막히지 않음. 로컬 수동 비교에 업로드나 3D 분석을 요구하지 않음.

### 3차 — 작은 화면의 전문가 도구 정리

대상 F08, R10–R14·R29·R30·R36·R37. 재생 조작을 가까이 두고 측정/메모를 시트로 묶는다. 실제 컨테이너 onLayout 기준으로 크기를 계산한다. 기본 offset 비교를 먼저 안정화하고 정규화는 별도 실험/고급 모드로 분리한다. 정보가 긴 경우에도 닫기/재생/저장을 가리지 않는다.

검증: 320/375/390/430pt, 아이패드/분할창·가로·200% 글씨·다크/네이비·VoiceOver. 현 사용자 지시상 시뮬레이터/Metro는 사용하지 않고 코드 검사와 모의 렌더 검사 후, 물리 기기 항목은 사용자 검증 목록으로 남긴다.

### 4차 — 정확한 미디어 정보와 결과 출력

R03·R04·R07·R15–R18·R23·R33. 설치된 SDK와 기존 네이티브 촬영/파일 기능을 조사해 지원 표를 만든다. PTS/슬로모션 편집 구간→정지 장면 합성→음성 메모→비교 영상→해설 녹화 순으로 진행한다. 사용자가 결과를 코치에게 전달할 수 있게 하는 것이 차별화 우선순위다. 실제 파일 내용과 음성/화면의 시간 대응을 확인한다.

네이티브 코드 추가는 새 바이너리/기능 탐지/이전 설치본 안내까지 포함한다. DB나 배포는 사용자 승인과 프로젝트 절차를 따른다.

### 5차 — 팀/클라우드와 고급 기능

R21·R22·R24–R28·R35. 오프라인 소유권·충돌·권한·삭제 정책부터 정리하고 협업을 추가한다. 외부 카메라/두 기기는 프로토콜·지연·보안·기기 검증이 별도이므로 핵심 비교의 완료를 가로막지 않게 분리한다. 원래 요구사항에서는 삭제하지 않는다.

### 일반 공개 관문

현재 `/pitch/compare`는 베타의 `pitchLog` 잠금에 속한다. 이는 설계의 기존 정책 보존 요구와 일치한다. 사용자에게 대표 기능으로 공개하려면 전체 투구 기록을 한꺼번에 여는 대신 독립 `videoCompare` 권한의 경로·서버 동작·입력 미디어 조회 범위까지 제안하고 명시적으로 결정한다. UI에서만 잠금을 우회하지 않는다. 1·2차 교정과 실제 기기 확인 전에 잠금 해제를 완료 기준으로 삼지 않는다.
