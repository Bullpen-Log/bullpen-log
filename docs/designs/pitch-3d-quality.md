## 0-2. 정밀 모델 · 2단계 보정 · 겹쳐 보기 · 비용(2026-10-08 김민과 대화로 더함 — gstack 검토 전)

사용자: "뼈 15조각이 움직이는거만으로 충분할까? … 진단하고 처방하려면 더 정교하게" · 참고 영상 Driveline "83MPH vs 95MPH Which Skeleton Throws Harder?"
(https://youtube.com/shorts/8HvJW5ah5G4) · "실제로 던지는거랑 3d 애니메이션이랑 차이가 눈에 띄면 아무도 사용을 안하겠지" · "이거 계획 금윤호한테 전달해줘".
**이 절은 아직 gstack 검토를 거치지 않았다 — 만들기 전에 `/gstack-plan-eng-review` 로 이 절을 먼저 볼 것.**

1. **정밀 몸 모델(관절 자유도 35~40, ISB 관절 좌표계)**: 보이는 뼈는 0절의 15조각이지만 움직임 모델을 올린다.
   골반 6 · 몸통은 허리 · 가슴 둘(굽힘 · 옆굽힘 · 회전 각각) · 어깨 3(벌림 · 수평 벌림 · 외회전) · 팔꿈치 굽힘 + 아래팔 엎침/뒤침 · 손목 2 ·
   엉덩관절 3 · 무릎 · 발목 2. 어깨뼈는 직접 못 보니 위팔 움직임에서 계산(어깨 리듬 규칙). 보이는 몸통 조각도 허리 · 가슴 둘로 나눈다.
2. **결과**: 모든 관절 각도의 시간 그래프 + 각속도 + 운동 사슬 순서(골반 → 몸통 → 팔 최고 속도의 순서 · 간격) + 순간 지표 30여 개
   (Driveline OpenBiomechanics 와 같은 이름 · 정의로 맞춰 견줄 수 있게). 팔꿈치 내반 토크는 '실험' 표시.
3. **1차 = 코드 · 규칙**: 뼈 길이 고정 · 관절 한계(예: 어깨 외회전 0~185°, 팔꿈치 0~150°, 엎침 · 뒤침 범위 — 표로 정하고 시험) ·
   관절별 저역 필터(13~20Hz 안팎) · 가가속도 벌점 · **투구 표준 곡선**(착지 → 최대 외회전 → 릴리스 → 엎침 순서에 맞춘 관절별 각도 곡선)을
   확신만큼 섞음(잘 보인 장면은 영상, 흐리거나 가려진 장면은 곡선 쪽) · 손가락 점으로 손바닥 방향 → 아래팔 엎침을 직접 잰다.
4. **부자연스러움 찾기(규칙)**: 각속도 튐 · 관절 한계에 붙음 · 뼈가 몸을 뚫음 · 디딘 발 미끄러짐 · 골반 → 몸통 → 팔 순서 어긋남.
5. **2차 = AI 보정(영상에 묶임)**: 4번이 찾은 장면만 작은 동작 모델로 다듬는다. 다듬은 뒤에도 뼈대를 두 영상에 다시 비춘 자리가
   관절 점에서 **키의 1.5% 안**이어야 한다(영상에 보이는 것은 못 바꾼다 — 실제 결함을 지우지 않게). AI 가 바꾼 구간은 기록 · 재생 막대에 엷게 ·
   그 구간 숫자는 믿음을 낮추고 진단에 안 쓴다. 모델은 1차 결과 중 잘 찍힌 것 + 사용권이 되는 자료로 우리가 학습(AMASS 같은 비상업 자료 피함).
   앱 'AI 안 씀' 원칙의 예외(영상 인식 · 동작 모델, 대화형 AI 아님 — 김민이 직접 제안). 1차가 자리 잡은 뒤 붙인다.
6. **겹쳐 보기**: 큰 3D 칸은 그대로 돌려 본다. 옆 · 뒤 **원본 영상 칸**에 '겹쳐 보기' 단추 — 같은 3D 뼈대를 그 폰의 실제 자리(보정에서 찾은 카메라)에서 본
   모습으로 영상 위에 반투명하게. 같은 시계. '내 팔과 뼈가 같이 가는지'를 사용자가 직접 확인하는 장치(신뢰).
7. **장면 수(E-CAP 바뀜)**: 착지부터 릴리스 뒤 0.1초까지는 240fps 그대로, 나머지는 120fps(원래 답은 전체 120fps · 600장). 김민: "팔은 240프레임
   슬로우모션으로 보면 관찰가능하지않아?" — 맞다. 흐림은 셔터(밝기)가 정하니 촬영 안내에 '밝은 곳(낮 야외) · 240fps · 원본 파일 · 삼각대 · 두 폰 60~120°'.
8. **정확도 검증(R1) 다시 살림 + 출시 기준**: 진단 · 처방에 쓰려면 증거가 있어야 한다. 겹침 오차 중앙값 키의 1.5% 밑 · 95% 장면 3% 밑 · 장면 사이 튐 0 ·
   관절 한계 넘음 0. 기준을 못 넘으면 '참고만'. 출시 전에 투수 10명쯤에게 겹쳐 보기를 보여 '내 투구 같다' 점수. 같은 영상 두 번 · 같은 투수 5구 반복성.
   기준 자료 후보: Driveline OpenBiomechanics(투수 100명 마커 데이터, GitHub 공개) — **사용권 확인 필요**(비상업 조건일 수 있음).
9. **진단 · 처방(다음 단계)**: 지표가 기준에서 벗어나면 원인 후보 → 앱 드릴 139개에서 처방(규칙, AI 없음). 이 계획 범위 밖, 별도 설계.
10. **제안(검토에서 정할 것)**: Driveline 영상처럼 해골 둘 나란히 비교(이번 공 vs 지난 공 또는 기준 선수, 착지에 맞춰 같이 재생).
11. **비용(어림, 1달러 ≈ 1,400원)**: 한 번 분석 약 60~120원(1차 GPU 2~3.5분 · 55~100원, 2차 AI 10~30초 · 5~15원, L4 시간당 0.8달러 × 아시아 1.5배).
    Modal 무료 크레딧 월 30달러 → 월 400~600번 공짜. AI 보정 모델 학습은 한 번 30~150달러(실험 10번 안팎). 사용자 1,000명 × 월 4번 = 월 28만~45만 원
    → 공개 때 R3(사용자별 하루 한도)로 상한.

## 4. 비슷한 제품 · 연구(검색, 2026-10-08)

- [Layer 1] 실제로 쓰이는 길: 보정된 여러 카메라 → 촘촘한 2D 관절 → **몸 모델(뼈대 · 근골격)을 시간 전체에 맞춤(역기구학)** → 매끈하고
  뼈 길이가 고정된 움직임. OpenCap(두 아이폰): 2D 키포인트 → 마커 보강 LSTM → OpenSim 역기구학, 평균 4.1°(키포인트만 쓰면 9.6°).
  Theia3D · KinaTrax · Hawk-Eye 도 같은 줄기.
- [Layer 2] PitchAI(폰 한 대, 엘리트 투수 38명): 골반 · 몸통 r² 0.92, 무릎 0.87, 던지는 팔 0.88, 글러브 팔 0.81.
- [Layer 3] 우리 엔진의 병목은 삼각측량 수식이 아니다. **점을 장면마다 따로 구하는 구조 자체**가 끊김 · 떨림 · 뼈 늘어남을 만든다.
  두 영상의 2D 에 '뼈 길이가 고정된 몸'을 시간 전체로 맞추면(시공간 번들 조정) 세 문제가 한 번에 풀리고, 그 결과(관절 회전)가
  곧 3D 사람 모델을 움직이는 값이 된다. 즉 '정확도'와 '보이는 품질'이 같은 한 단계에서 나온다.

## 5. 0A 전제 · 0C 꿈의 상태

- 진짜 문제: 투수 · 코치가 자기 투구를 **사람처럼 보이는 3D 로, 끊김 없이, 믿을 만한 숫자와 함께** 보는 것. 지금은 쓸 수 없다(1.5점).
- 아무것도 안 하면: 베타가 쓰레기로 남고, 3D 분석이라는 차별점이 사라진다.
- v1 계획은 '지표 숫자'라는 대리 목표를 풀었고, 사용자가 보는 것(움직임의 질)은 직접 풀지 않았다.

```
   + 원본 영상 나란히                                  motion.glb(몸 메시 + 애니메이션)
```

작업 상태(job.json):
```
 (없음) ──요청──▶ queued ──Modal 상태 running──▶ running ──Modal done + 결과 두 파일──▶ done
                    ▲                        │  └──실패──▶ failed(code · 까닭)
                    │                        └──15분 넘게 done 아님 · Modal 실패──▶ failed{code:'timeout'}
                    └──── 관리자 '다시 분석'(done · failed 에서) ────┘
 막는 것: queued · running 중 '다시 분석' 거절(서버 동작이 job.json 을 보고) · 상태는 job.json 에 적힌 지금 작업 번호로만 묻는다(옛 작업은 묻지 않음)
```

데이터 흐름 네 길(요청 → 결과):
- 행복: 두 영상 있음 → queued → running → done → 패널이 결과를 읽어 메시를 튼다.
- 없음(nil): 옆 · 뒤 중 하나가 없음 → 서버 동작이 거절('옆 · 뒤 영상이 다 있어야 해요'), job.json 을 쓰지 않는다.
- 빈 것(empty): 영상이 0바이트 · 못 읽는 형식 → 작업자가 failed{code:'video'} → 패널이 까닭 한 줄 + 다시 분석.
- 오류: 저장소 쓰기 실패 → 서버 동작이 오류 한 줄(작업 안 걸림) · GPU 함수 부르기 실패(키 없음 · 503) → job.json 을 failed{code:'gpu'} · 함수 중 실패 → failed{code} · 15분 넘게 알림 없음 → failed{timeout}.

## 검토 6절 — Test Review

```
 새것                         | 시험 종류   | 행복 길                     | 실패 길                         | 끝 경우
 -----------------------------|-------------|-----------------------------|---------------------------------|-------------------------
```

- 핵심 합격(사용자가 본 문제를 숫자로): 샘플 3개 모두 **모든 장면 · 모든 관절이 있음(빈 칸 0)**, 뼈 길이 흔들림 1% 밑(몸 모양 하나로 고정),
  장면 사이 가속 p95 가 v1(0.04~0.096)보다 작음. 핵심의 약속을 재는 것이지 R1(정확도 검증 도구: 반복성 · 합성 · 실험실)이 아니다.
- 정확도(몇 도 맞나)는 R1 로 미뤘다. 이번 결과도 '참고만'.
- 흔들릴 수 있는 시험: 실제 GPU 를 부르는 시험은 손으로만(자동 시험에 넣지 않음).

## 검토 7절 — Performance

- GPU 한 번(어림): 받기 5~10초 · 2D(옆 · 뒤 900장) 20~40초 · 맞추기 30~60초 · 올리기 수 초 · 첫 시작 +20~40초 → 1~2분.
- 결과 크기: analysis-v2.json ≤ 900KB(v1 상한 재사용) · motion.glb 어림 1~3MB(메시 하나 + 장면별 뼈 회전).
- 패널 읽기: 열려 있는 동안 5초마다 job.json 하나. 관리자만이라 무시할 만함. DB 질의 늘지 않음.
- 가장 느린 길: GPU 첫 시작 · 맞추기 · 브라우저의 glb 받기(3MB). p99 어림 3분.

## 검토 8절 — Observability

- job.json 에 단계별 시간(받기 · 2D · 맞추기 · 올리기) · 모델 이름 · 엔진 판 · GPU 실행 id 를 남긴다. 패널 '자세히'에 보인다.
- 서버 동작(요청 · 상태 묻기)은 실패 때 jobId 와 함께 서버 기록(console.error). GPU 쪽 기록은 회사 대시보드에서 실행 id 로 찾는다.
- 경보 · 대시보드: 관리자만이라 없음(R3 공개 때 다시).
- 대응: failed{gpu} → 회사 상태 · 키 확인, failed{timeout} → 실행 id 로 회사 기록 보기, failed{fit} → 품질 숫자로 영상 문제인지 본다.

## 검토 9절 — Deployment & Rollout

- DB 바꿈 없음(job.json · 결과 파일은 저장소).
- 김민 님이 할 일(Claude 가 못 하는 것): GPU 회사 가입 · 카드 · 토큰, Vercel 환경변수 셋, 저장소 버킷이 glb 를 받게 설정(dbc17c8 의 JSON 때처럼).

- 요청: Modal 주소가 503 → failed{gpu} 한 줄, 단위 시험(판단 함수), 사용자에게 보임.
- 구간 찾기: 니업을 못 찾음 → failed{events} v1 글, 자가 점검 아님(손 확인 · 깨진 영상), 사용자에게 보임.
- node 다리: 묶음 JS 가 JSON 이 아닌 것을 돌려줌 → failed{internal} + 단계 기록, 자가 점검(짝 표), 사용자에게 보임.
- 몸 맞추기: NaN → failed{fit}, 자가 점검(불변식), 사용자에게 보임.
- 상태 묻기: Modal 결과 만료 → 결과 파일이 있으면 done, 없으면 timeout, 단위 시험, 사용자에게 보임.

  옆 = 3루 쪽 수평 · 뒤 = 2루 쪽(투수 뒤) 수평 · 포수 = 홈 쪽 가슴 높이 · 위 = 70° 내려다봄. 처음은 옆. 손가락 끌기는 좌우 돌리기(위아래 각 5~80°),
  두 손가락 확대, 시점을 누르면 되돌림. 폰을 비스듬히 두었으면 원본 영상과 각도가 조금 다를 수 있다(알고 고름).
- **결정 11(화면 D13 "11A")**: 몸 #c9d1da · roughness 0.62(근육 지도 3D 와 같음). 던지는 팔(어깨~손끝, SMPL-X 부위 표, 좌투는 거울) #0a84d6 · emissive 0.22.
  발 밑 부드러운 접촉 음영. 격자는 빼고 마운드 방향 화살표 하나. 손가락은 손 관절 확신이 낮으면 자연스러운 쥐기로 고정.
- **결정 12(화면 D14 "12A")**: 3D 가 기준 시계. 구간 = 니업 0.5초 전 ~ 릴리스 0.5초 뒤. 영상은 멈춤 · 끌기 때 currentTime 을 맞추고 재생 때 playbackRate 를 맞춘다.
  속도 1× · ½× · ¼×(기본 ½× 되풀이, 처음 열 때만 결정 9). 화면 녹화(30fps)는 ¼× 에서 뚝뚝 끊길 수 있다.
- **결정 13(화면 D15 "13A")**: 두 영상에서 관절 확신이 낮았던 장면을 재생 막대에 엷은 회색 구간으로. 그 구간을 누르거나 그 안에서 멈추면 '이 구간은 영상에서 잘 안 보였어요.' 한 줄.
