2026-11-09 · 금윤호 Codex · 검토 대상 `intake/external-video-submission`의 `524b1f0a`. 원격 조회 후 origin도 같은 커밋임을 확인했다. main은 `6b829da4`이다.

## 확인한 문제와 원인

### 1 운영과 앱에서 이용할 준비가 끝나지 않음

우선순위 P1. 원격 main에 접수 기능이 병합되지 않았고, 접수 DB 변경은 `prisma/pending-migrations/`에 있다. 기존 인계에는 버킷 미생성·환경변수 미적용으로 기록돼 있다. 이번에는 운영 DB나 버킷의 상태를 직접 조회하지 않았다. 접수 브랜치의 웹 3D 개발 관리자에는 `/admin/intake` 연결이 있지만 정식 native 앱에는 접수 전용 연결이 없다. main의 3D 개발 관리자 진입 보완은 외부 접수 브랜치 병합과 별개다.

해결: 접수 브랜치에서 main의 관리자 진입 보완을 보존하며 통합한다. 앱 관리자에도 외부 영상 접수·초대 만들기 진입을 추가한다. 초기에는 인증 동기화를 갖춘 기존 앱 웹뷰를 재사용할 수 있고 `APP_UA`를 반드시 붙인다. 일반 계정에서 메뉴를 숨기는 것과 별도로 서버 권한을 그대로 검사한다. DB가 준비되지 않은 경우 초대 만들기를 비활성화한다. 현재 웹 목록은 준비 안 됨을 표시하면서도 초대 만들기 버튼을 표시한다.

완료 조건: 대표관리자는 PC와 앱에서 접수함·초대 생성에 진입하고, 일반·준관리자는 서버에서 거부된다. 발급 주소는 외부에서 접근 가능한 정식 HTTPS 주소를 사용한다. 개발 서버에서 생성한 localhost 주소를 실제 받는 사람에게 보내지 않는다.

### 2 공개 API가 응답을 끝내지 않으면 화면이 계속 대기함

우선순위 P1. `lib/intake/public-client.ts:49`의 공통 call에는 요청 signal과 대기 시간 제한이 없다. fetch뿐 아니라 `res.json()`도 제한 없이 기다린다. 재시도는 요청이 실패한 뒤에만 실행되므로 미완료 요청은 복구 흐름으로 넘어가지 않는다. `components/intake/intake-flow.tsx:127`은 첫 상태 읽기가 끝나야 로딩을 벗어난다.

재현: 실제 createIntakeClient에 절대 끝나지 않는 가짜 fetch를 전달했다. signalPassed=false, 관찰 시간 뒤에도 pending이었다. 이 검사는 현재 코드에 자체 제한이 없음을 확인한 것이며 실제 서비스 장애를 재현한 것은 아니다.

해결: 요청 시작부터 본문 읽기까지 하나의 AbortController로 제한한다. 상태·초안·권한 요청은 우선 20초를 제안하며 실측 후 조정한다. 전체 영상 전송에 같은 20초를 적용하지 않는다. 외부 취소와 시간 초과를 구분하고 타이머·이벤트를 finally에서 정리한다. 단계별 입력과 선택 파일을 유지하고 재시도 버튼을 제공한다. 완료 요청 시간 초과는 서버 반영 여부가 불명확하므로 기존 완료 키로 확인·재시도하고 새 접수를 만들지 않는다.

완료 조건: 응답 머리가 안 오는 경우와 머리만 오고 본문이 멈추는 경우 모두 제한 시간 뒤 복구 화면을 표시한다. 완료 응답 유실 후 다시 눌러도 같은 영수증과 한 개의 제출 판만 남는다.

### 3 화면을 떠나 중단 신호가 발생해도 다음 업로드가 시작될 수 있음

우선순위 P1. `components/intake/use-send.ts:70`은 정리 시 abort하지만, `lib/intake/upload-run.ts`의 자산 예약·토큰 발급·도착 확인에는 신호가 전달되지 않는다. sendOne은 업로드를 먼저 시작한 다음 abort 리스너를 붙이며 이미 취소됐는지 확인하지 않는다. 예약 응답을 기다리는 사이 취소되면 이미 지난 abort 이벤트를 놓친다.

재현: 실제 runUpload의 가짜 reserveAsset에서 controller.abort()를 실행했다. 이후 업로드 start 1회, abort 호출 0회, 도착 확인 1회였고 runUpload가 성공 반환했다. 브라우저 프로세스 전체 종료 후에도 전송이 보장된다는 뜻은 아니다. 페이지가 살아 있는 동안 비동기 준비가 남은 상황의 취소 누락이다.

해결: 해시 전후, 예약 전후, 토큰 전후, 전송 시작 전, 확인 전후, 완료 제출 직전에 취소 여부를 검사한다. 재시도 대기와 API에 signal을 연결한다. TUS 시작과 리스너 등록 사이에서도 취소를 놓치지 않도록 시작 전 검사와 등록 직후 재검사를 하거나, 시작 함수 자체가 signal을 받게 한다. 취소 시 이미 받은 파일은 보존하고 같은 파일 재선택 후 이어 보내게 한다. 이미 서버에 접수 완료 요청이 도착한 경우에는 취소 성공으로 단정하지 말고 결과 확인으로 복귀한다.

완료 조건: 준비 중 어느 await에서 취소해도 그 뒤 새 전송과 완료 제출이 시작되지 않는다. 취소 이후 화면 갱신도 차단한다. 진행 중 취소한 파일은 다음 방문에서 원본 해시를 대조한 뒤 재개한다.

## 운영 전 확인해야 할 위험

### 대용량 검증이 서버 실행 시간을 넘길 가능성

`lib/intake/storage-core.ts:201`은 원본 전체를 읽어 SHA256을 계산한다. `verifyAsset`은 이 호출에 제한 signal을 넘기지 않는다. 크론은 최대 세 파일 검증에 앞서 다른 일도 처리하고 라우트 제한은 300초다. 시간 초과 후 재시도는 해시를 처음부터 다시 읽는다. 실제 1GiB에서 실패했다고 확인한 것은 아니다.

계획: 100MB·500MB·1GiB 파일의 업로드·도착 확인·전체 해시 시간을 따로 측정한다. 검증 단계에 실행 예산을 두고 남은 시간이 부족하면 다음 작업을 시작하지 않는다. 한 파일도 예산 안에 못 끝내면 파일 검증을 전용 지속 작업자로 옮기거나 측정된 지원 한도를 안내한다. 파일 해시 일치 검증을 생략하거나 제출 성공과 검증 완료를 합치지 않는다.

### 분석 동의 문서가 확정 전이라 기본 설정에서 GPU가 차단됨

`lib/analysis-consent.ts`의 다섯 PENDING과 분석 결과 보유 기간이 미확정이다. `analysisRunGate`가 기본적으로 실행을 막는 것은 의도한 동작이다. 운영 장애를 해결하려고 `INTAKE_ALLOW_DRAFT_ANALYSIS=1`로 우회하는 것을 출시 해결책으로 삼지 않는다.

계획: 실제 처리 장소·연락처·보유 기간과 동의 방식을 담당자가 확정해 코드 문서에 반영한다. 문서 판을 갱신하고 기존 접수의 재동의 흐름을 시험한다. 지운 원본에는 분석 재개를 약속하지 않는다. 대리 제출과 만 14세 미만 정책을 최종 표시와 일치시킨다. 이 검토는 법률 적합성 판정이 아니다.

### 초대 생성 응답 유실의 복구가 불편함

초대 원문 토큰을 저장하지 않고 한 번만 보여 주는 방식은 적절하다. 다만 `createInvitation`은 매번 새 초대를 만들고 생성 요청 키가 없다. 서버 생성 뒤 응답만 유실되면 기존 링크를 복원할 수 없고 다시 누르면 빈 초대가 더 생길 수 있다. 코드 경로에 따른 판단이며 이번에는 응답 유실로 DB 중복 생성을 별도 재현하지 않았다.

계획: 관리자가 링크를 못 받은 초대를 식별하고 폐기·재발급할 수 있게 한다. 재발급은 권한과 상태를 확인하고 이전 토큰을 무효화하며 감사 기록을 남긴다. 제출이 시작된 접수의 재발급은 기존 자료 연결·결과 접근까지 검토한다. 편의를 위해 토큰 원문을 평문 저장하거나 로그에 남기지 않는다.

## 실행 순서와 합격 기준

1. P1 시간 제한·취소 누락을 접수 브랜치에서 보완하고 재현 검사를 회귀 시험으로 만든다. 앱 진입·초대 생성 복구를 함께 정리한다.
2. 환경파일 없는 독립 복사본에서 브라우저 공개·관리 전체 흐름을 다시 실행한다. 수정 브랜치의 실제 화면·라우트·DB 연결을 사용하고 결과를 검증표에 갱신한다.
3. 사용자에게 보유 정책 판단을 확인한다. 고침 대기 최대 14일, 재제출의 90일 시계 재시작, 철회 이후 기산일 등 기존 문서의 결정을 확정하고 화면과 삭제 시험에 반영한다.
4. 공유 DB 적용은 협업자에게 알리고 백업한 뒤 승인된 범위에서 진행한다. pending SQL·버킷·환경변수·크론·서버·앱의 적용 순서를 맞춘다. 금지된 migrate dev·db push·reset을 사용하지 않는다. 브랜치 병합 전에 자동 배포와 DB 반영 범위를 확인한다.
5. 실제 가상 사용자 전용 초대를 만들고 iPhone Safari, 카카오 인앱, PC에서 아래 시나리오를 검증한다. 실제 사용자 자료는 시험 대상으로 쓰지 않는다.

| 시나리오 | 합격 기준 |
|---|---|
| 옆·뒤 120fps와 240fps MOV·HEVC | 실제 선택·재생 한계·분석 가능 여부를 구분해 표시하고 원본을 재인코딩하지 않음 |
| 사진 앱·파일 앱·iCloud 선택 | 내려받기 대기·실패·파일 읽기 권한 해제에서 복구 안내 |

| 통신 끊김·화면 잠금·재방문 | 같은 파일 재선택과 해시 확인으로 이어 보내며 다른 파일을 이어 붙이지 않음 |

| 보유 삭제·삭제 재시도·크론 | 실제 저장소 객체 부재를 확인하고 삭제 완료를 표시, 남은 객체는 재시도 |
| 분석·공개·비공개 | 관리자 실행과 공개 승인 후에만 수신자에게 정확한 현재 결과 표시 |
