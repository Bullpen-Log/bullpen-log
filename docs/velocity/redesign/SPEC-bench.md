# Spec: `bench` — 구속 측정 고정 시험대

능력 지도 `map.md` 의 첫 모듈. 다른 모듈은 이 시험대 점수로만 들어간다.

## Objective

**모든 구속 엔진 변경을 같은 현장 자료로 재서, 나아졌는지 · 어디서 틀렸는지를 숫자로 낸다.** 지금은 고칠 때마다 손에 있던 공으로 맞추고 같은 공으로 확인해
새 현장에서 무너졌다(판 65번). 쓰는 사람은 우리 둘과 Claude.

첫 질문 둘에 답해야 한다.
1. **퇴화는 코드 탓인가 조건 탓인가** — 옛 판(1.9 · 2.0 · 2.4 · 2.7 · 2.8)을 같은 자료로.
2. **틀린 곳이 어디인가** — 10-23 잰 3구는 앱이 쓴 거리 19.5 · 19.5 · 20.4m(실제 20m, 김민)인데 구속이 10~14% 낮았다(127 → 109 · 109, 132 → 119).
   거리 말고 다른 곳(공 길 시간 · 궤적 맞추기 · 잰 구간)이 틀렸다. 공마다 단계별로 갈라 본다.

## 자료(fixtures)

| 묶음 | 공 | 스피드건 | 실제 거리 | 쓰임 |
| --- | --- | --- | --- | --- |
| 10-23 세션 녹화 컷 | 19(건 17) | ○ | 판 → 망 20m(폰 → 망 20.5m) | 확인용(떼어 둠) |
| 10-21 · 10-09 · 10-07 앱 클립(`--live`) | 26 | ○ | 그날 줄자(있으면) | 맞추기용 / 확인용 날짜째 가름 |
| 녹화 rec-49def374 · gA · gB | 15 | ○ | — | 맞추기용 |
| 카메라 앱 파일(09-28 · 10-03 · 10-06) | 31 | ○ | 10-03 20m · 10-06 18m · 09-28 모름(김민) | 진단용(앱 길이 아님, 문에 안 씀) |

**실제 거리 — 투수판 → 망(김민). 엔진의 거리는 폰 → 망이라 폰이 판 뒤 몇 m 인지를 더해야 한다(아직 모름).** 실제 거리로 옮겨 본 구속 차(가운데):

| 폰이 판 뒤 | 10-03(13구) | 10-06(4구) | 10-23 잰 3구 |
| --- | --- | --- | --- |
| 0m | −11.8% | −3.9% | −11.7% |
| 1m | −7.0% | +1.8% | −7.0% |
| 1.5m | −4.6% | +4.7% | −4.6% |
| 2m | −2.2% | +7.6% | −2.2% |

**김민: 폰은 대개 판 뒤 50cm, 폰 → 손 떠나는 곳 1m 안팎** → 폰 → 망 = 10-03 · 10-23 20.5m, 10-06 18.5m. 그 거리로 옮기면:

| 날 | 공 | 실제 거리에서 구속 차(가운데 · 범위) | 엔진 자동 거리 차 |
| --- | --- | --- | --- |
| 10-03 | 13 | −9.4% (−20 ~ −7) | +8.3%(멀게) |
| 10-06 | 4 | −1.1% (−18 ~ +20) | +1.1% |
| 10-23 | 3 | −9.3% (−9 ~ −9) | −4.9%(가깝게) |

→ **거리 밖에서 구속이 9% 쯤 낮게 나오는 날이 있다**(10-03 · 10-23). 10-03 은 자동 거리가 8% 멀게 나와 그것을 덮었고, 10-23 은 거리마저 5% 가깝게
나와 겹쳐 10~14% 낮았다. 공 크기 상수가 거리를 늘려 구속 치우침을 메우는 구조라 날마다 무너진다. 거리 밖 9% 의 자리(궤적 맞추기 · 시간 ·
끝 판정 · 기울기)를 찾는 것이 시험대의 첫 진단 과제. 앞으로 현장마다 **폰 → 망 거리**를 줄자로 재 둔다.

- 날짜(세션)째 맞추기용 · 확인용으로 나눈다 — 같은 날 공이 양쪽에 섞이지 않게. **문은 확인용으로만.** 확인용을 보고 상수를 고치면 그 묶음은 맞추기용으로 넘긴다.
- 영상은 저장소 밖 `~/bullpen-velocity-lab/bench/`(개인 영상), 목록 `fixtures.json`(공 id · 묶음 · 스피드건 · 실제 거리 · 손 떠난 때 · 조건 꼬리표)은 저장소
  `scripts/velocity-bench/fixtures.json`(DB id 만, 개인 정보 없음).
- 새 현장 세션이 생기면 묶음 하나로 더한다(스피드건 + 세션 녹화 + 가능하면 줄자).

## 재는 것(공마다 → 묶어서)

- 잡음: 공 길을 찾았나(던진 공 중 몇 %). 잼: 믿음 '높음'으로 냈나.
- 구속 차: 낸 값 − 스피드건. MAE · 90% · ±3km/h 안 비율 · 치우침(속도 띠 100~115 · 115~130 · 130+ 따로).
- 단계별 갈래(어디서 틀렸나): 거리 차(실제 거리가 있을 때) · 공 길 장면 수 · 손 떠난 때 차 · 처음 잡힌 깊이 · 끝 판정(튕김 · 이어 찾기) ·
  '거리를 실제로 넣었다면' 구속 차(거리와 나머지 오차를 가름).
- 목표(지도의 1판 목표) 대비 통과 · 미달.

## Commands

```
npm run velocity:bench -- --engine=lib/velocity-engine            # 지금 엔진, 확인용 묶음
npm run velocity:bench -- --engine=git:<커밋> --set=all --json=<파일>  # 옛 판 · 모든 묶음
npm run velocity:bench -- --compare=<a.json>,<b.json>             # 두 결과 견주기(공마다 · 묶어서)
npm run velocity:bench:fetch                                       # fixtures.json 의 영상을 받기(읽기만, .env)
# 2026-10-25 설계안 첫 묶음(작업 A · C · D)
npm run velocity:bench -- --net=<netseen.json> --modes=app,guided   # 모델 후보 안내(guided) vs 기존(app) 을 같은 영상에서 — 안내로 찾은 비율 · 실패 까닭(no-chain · no-seed · no-flight)
npm run velocity:bench -- --shifts=0.05,0.1,0.2                     # 분석창 민감도 — 공 시각을 ±s 옮겨 다시 재고 값 차이(2km/h 안 비율 · 잘린 구간 따로)
npm run velocity:bench -- --dump=<폴더>                             # 공마다 궤적 · 후보 · 이은 길 JSON → scripts/velocity-bench/overlay.html 로 원본 위에 겹쳐 본다(라벨 찍기도)
npm run velocity:bench -- --labels=<폴더> --modes=app,label-link    # 사람이 찍은 중심(SPEC-labels.md)을 안내로 — 단계 B 진단
npm run velocity:bench:report -- <결과.json> --strict               # 확인용 목표 미달이면 끝 코드 1(CI)
```

화면 규칙(기록할 공 · 세션 거리)은 `screen.mjs` 가 **앱과 같은 함수**(`lib/velocity-session.ts screenPitch · withSessionDistance`)로 받은 차례대로 건다 — 옛 `app-rules.mjs`(복제 규칙)는
2026-10-25 에 지웠다. lib 이 `@/` 를 써서 `velocity:bench` 는 `--import ./scripts/alias-register.mjs` 로 돈다(`gun-table.mjs` 도).

## Project Structure

```
scripts/velocity-bench/
  fixtures.json        자료 목록(DB id · 묶음 · 스피드건 · 실제 거리 · 꼬리표)
  fetch.mjs            영상 받기(download.mjs · download-recording.mjs 를 감쌈)
  run.mjs              엔진 하나로 모든 공 재기 → 결과 JSON(길: app · guided · label-link · true · true±5 · base, --shifts · --dump)
  screen.mjs           화면 규칙 — 앱과 같은 lib/velocity-session.ts 함수로(2026-10-25, app-rules.mjs 대신)
  labels.mjs           사람이 찍은 공 라벨 읽기(SPEC-labels.md)
  overlay.html         개발용 오버레이 · 라벨 찍기(정적 쪽 — 덤프 JSON + 영상)
  report.mjs           묶기 · 표 · 견주기 · 목표 대비 · 안내 vs 기존 · 분석창 민감도 · --strict
  engines/             git:<커밋> 엔진을 꺼내 둔 곳(.gitignore)
docs/velocity/redesign/bench-results.md   판마다 결과 표(사람이 읽는 곳)
```

## 실행 길

- 앱과 같은 길: 앱이 하는 그대로 클립 + 옵션(공 시각 둘레 BALL_RANGE · 화각 · fovKnown · 자동 거리 · 기울기)을 엔진에 넣는다(`prod-smoke.mjs` ·
  `gun-table.mjs` 의 길을 하나로). 엔진은 헤드리스 브라우저에서 돈다.
- 아이폰은 WebKit 이라 1판은 **크롬과 WebKit 둘 다**(Playwright webkit) 돌려 차이를 본다 — 예전에 WebKit 이 덩어리를 0.5~1.8px 크게 잡았다.
- 옛 판은 `git worktree` 로 `lib/velocity-engine` 만 꺼내 같은 실행기로 돈다(실행기는 엔진 입출력 모양이 판마다 다르면 맞춰 주는 얇은 층을 둔다).

## Code Style

지금 실험 도구(`scripts/velocity-lab/*.mjs`)와 같게 — 한국어 주석 · 출력, Node ESM, 의존성 더하지 않음(Playwright 는 이미 있음). 출력 한 줄 예:

```
10-23 #9  건 127 | 109.1 high · 거리 19.5(실제 20, −2.5%) · 거리 맞췄다면 111.8 · 장면 33 · 처음 깊이 3.7m · 끝 튕김
```

## Testing Strategy

- 같은 엔진을 두 번 돌리면 결과 JSON 이 글자까지 같다(시각 · 판 정보 빼고) — 시험대 자신의 시험.
- 작은 묶음(공 3개) 연기 시험 `--limit=3` 이 1분 안.
- 결과 수는 사람이 센 현장 기록과 맞는다(10-23: 던진 공 19 · 건 17).

## Boundaries

- Always: 확인용 묶음 점수로만 '나아짐'을 말한다. 결과 표에 엔진 판 · 커밋 · 브라우저를 적는다. DB 는 읽기만.
- Ask first: 확인용 묶음을 맞추기용으로 넘기기, 묶음 나누기를 바꾸기, 새 의존성.
- Never: 확인용 공을 보고 상수 맞추기, 시험대 숫자를 고쳐 통과시키기, 영상을 저장소에 넣기.

## Success Criteria

1. 위 네 묶음(공 91)을 지금 엔진으로 맥에서 15분 안에 끝까지 잰다(크롬 · WebKit).
2. 두 번 돌린 결과가 같다.
3. 옛 판 다섯을 같은 자료로 잰 표가 나오고, '코드 탓인가 조건 탓인가'에 숫자로 답한다.
4. 10-23 잰 3구의 10~14% 낮음이 어느 단계에서 생겼는지 공마다 갈래로 나온다.
5. 결과가 `bench-results.md` 에 판마다 한 줄씩 쌓인다.
