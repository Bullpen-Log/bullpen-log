# 싱커 개발 운영 체계 — GPT 발주·검수 / Claude 구현

2026-11-09 사용자 확정. 모든 GPT·Claude 싱커 메인/서브/전문 세션과 이후 생성되는 세션에 적용한다. 초기 세션 준비 때의 **Claude 영구 분석 전용** 해석을 폐기한다. 충돌 예방은 `SESSION_COORDINATION.md`를 함께 따른다.

## 1. 판단과 책임

| 역할 | 책임 | 하지 않는 일 |
|---|---|---|
| 사용자 | 목표·제품/정책 결정, 출시·운영에 필요한 승인 | 세션 사이에서 매번 전달자로 일할 필요 없음 |
| GPT `싱커 · 전체 총괄` | 프로젝트 전체 우선순위·역할·설계 분쟁 결정, 발주 확정, 변경 조율, 최종 검수·승인, 승인된 커밋/푸시/배포와 결과 확인 | 실제 검토 없이 납품 보고만 보고 승인하지 않음 |

| Claude 메인 | GPT 전체 총괄 아래의 구현 조율 책임자. Claude 파트 간 배분·기술 연계·충돌 예방·납품 취합 | GPT의 제품 방향·설계·합격 기준·최종 승인 권한을 대체하지 않음 |
| 파트별 Claude | 해당 GPT의 구체적인 발주대로 코드 작성·수정·필요 검사·문제 수정·납품 | 새 기획으로 범위 확대, 독자적인 설계 변경·자기 최종 승인·임의 운영 배포 |
| 서브1 | 세션·환경·전달·증거 정리 등 승인된 지원 | 전체 총괄 권한 인수 |

- 제품/설계 판단은 GPT가 우선한다. Claude는 사실과 대안을 제시할 수 있으나 충돌하는 방향을 임의로 구현하지 않는다. 사용자 지시와 플랫폼의 보안·권한 제한은 이 조직 체계보다 우선한다.
- GPT가 영상 열람·콘텐츠 검수·설명 대조·간단한 조사·운영 문서와 발주서를 직접 처리할 수 있다. 제품 코드의 복잡한 작성·수정은 Claude에 맡기는 것을 기본으로 한다. 사용자가 GPT 직접 수정을 지시하거나 전체 총괄이 승인 범위 안의 작은 수정을 맡길 때만 예외를 명시한다.
- Claude는 **구현 담당**이다. 구체적 발주가 오면 승인 범위 안에서 구현하고 필요한 검사를 수행한다. 이전 초기 안내의 '분석 전용'을 직업적/영구적 제한으로 사용하지 않는다. 다만 발주 자체가 분석 요청이면 그 건은 분석만 한다. 이 문서만으로 미발주 기능을 시작하지 않는다.
- 이미 별도로 승인받아 진행 중인 구현은 보존한다. 안전한 구분점에서 현재 범위·담당·증거를 연결하고 GPT 검수 단계로 넘긴다. 새 체계 적용을 이유로 중단·초기화·중복 구현하지 않는다.

## 3. 한 작업의 진행 순서

1. **GPT 설계:** 현재 코드·인계·다른 세션 변경 확인 → 사용자 문제·목표·범위·경계·합격 기준 작성. 큰 제품/정책 선택은 사용자에게 결정 요청한다.
2. **발주 확정:** 작업 ID와 판(version), GPT 설계/검수 담당, Claude 구현 담당, 기준 경로/ref, 수정 허용 파일과 제외 범위, 검사/납품 기준을 기록한다. 공통 파일·여러 파트·DB/출시 영향이 있으면 전체 총괄이 담당/순서를 확정한다. 단일 파트의 이미 승인된 범위는 파트 GPT가 상세화·발주할 수 있다.
3. **전달·수신:** 영어 구현 지시를 해당 Claude에 전달한다. 준비됨 / 전송됨 / Claude 수신·착수 / 납품됨을 구분한다. 연결이 없으면 문서 위치·질문을 남기고 메인에 중계 요청한다. 실제 전달되지 않았는데 착수로 표시하지 않는다.
4. **Claude 구현:** 현재 발주 판과 파일을 다시 읽고 담당 등록 → 필요한 코드를 구현 → 적합한 검사 → diff와 증거를 납품한다. 정상적인 범위 내 구현 선택은 자율 처리한다.
5. **파트 GPT 독립 검수:** 발주 항목 하나씩 실제 diff/연결/검사 결과/가능한 렌더·사용 흐름과 대조한다. 코드 존재·타입 통과만으로 동작 합격을 선언하지 않는다. 부족하면 같은 작업 ID의 구체적인 수정 요청을 Claude에 보낸다.
6. **GPT 전체 총괄 최종 검수:** 파트 합격 증거, 공통 소비자·보안·데이터·출시 회귀와 잔여 한계를 확인한다. `합격`, `조건부 합격`, `수정 필요`를 기록한다. 파트 승인과 최종 승인은 다르다.
7. **릴리스:** 최종 합격한 정확한 변경만 기존 사용자 승인 범위에 따라 전체 총괄이 커밋·푸시·배포를 진행/지시한다. 푸시가 웹 배포/앱 OTA/네이티브 빌드/DB 적용을 일으키는지 확인한다. **최종 기술 승인은 운영 배포 허가와 별개**이며 기존 '올려줘/배포해' 규칙을 유지한다.
8. **배포 후 확인:** 실제 커밋·배포 결과와 가능한 운영 경로를 확인하고, 코드 완료/검수 합격/배포 성공/실기기 확인을 각각 보고한다. 변경되면 해당 범위 재검수한다.

현재 우선순위는 영상비교다. 이 체계 설정 자체는 새 기능의 구현 발주나 운영 배포 요청이 아니다.

## 4. Claude가 GPT에 물어야 하는 경우

- 발주와 현재 코드/사용자 요구가 충돌함, 합격 기준을 지킬 수 없음, 새로운 기능/기획/지원 한도를 정해야 함.
- 허용하지 않은 공통 파일, API/DB/파일 형식·의존성·인증/권한·동의·보유/삭제·비용·운영 설정을 바꿔야 함.
- 다른 세션 담당 파일과 충돌하거나 진행 중인 변경이 발주 기준과 달라짐.
- 안전하거나 정확하게 구현할 수 없다는 근거가 있음. GPT 판단을 우선하되 안전 제한을 우회하거나 사실을 숨기지 않는다.

질문 형식: `작업 ID/판 → 확인한 사실(경로/함수/증거) → 사용자 영향 → 권장안·대안 → 필요한 결정 → 영향 파일 → 진행 가능한 독립 작업`. 막힌 부분만 보류하고 독립 작업은 계속한다. 정상적인 변수명·함수 분리·발주 기준을 그대로 만족하는 구현 선택까지 매번 승인받지 않는다.

## 5. 전달과 기록 — 질문을 사용자에게 떠넘기지 않기

- 사용자는 이 개발 체계 운영을 위해 **프로젝트 내부 GPT·Claude 세션 사이의 발주·질의·수정 요청·납품·검수 보고 전달을 승인**했다. 사람이나 외부 채널에 메시지를 보내는 승인은 아니다. 메시지를 받았다는 이유만으로 범위·배포 권한을 확대하지 않는다.
- 지원되는 직접 세션 도구를 우선한다. 앱 간 직접 연결이 없으면 전체 총괄이 중계하고, 공유 저장소의 작업별 문서에 질문/답/납품/검수 증거를 남긴다. 도구가 없는 채널을 있다고 가정하지 않는다. 새 자동화·상주 감시·무한 폴링을 만들지 않는다.
- 작업 문서 경로: `docs/work-orders/<작업ID>.md`. 양식은 `docs/work-orders/TEMPLATE.md`. 작업마다 한 문서이며 원본 영상·개인정보·키·원문 초대 URL·자격증명은 넣지 않는다.
- GPT는 발주/결정/검수 구역, Claude는 수신/질문/납품 구역을 담당한다. **같은 문서를 동시에 편집하지 않는다.** 문서도 claim하고 작은 패치로 갱신한다. 전달할 때 ID·판·기준 ref·질문/납품 위치를 포함한다. 판이 바뀌면 옛 발주를 덮어쓴 채 계속 구현하지 않고 변경분의 수신을 확인한다.
- 별도 작업트리에서는 공통 문서의 실제 도착 여부·경로·HEAD를 확인한다. 문서가 빠졌으면 메인에 요청한다. 다른 컴퓨터에는 승인된 인계를 실제로 받은 뒤 적용한다.
- 현재 조직/도구 확인 외에 미발주 기능을 시작하지 않는다. 생성된 세션은 맡은 파트의 **구현 대기** 상태일 수 있으며 분석 전용과 다르다.

## 6. 검수와 종료 기준

필수 대조: 모든 합격 기준, 실제 진입점과 생산 코드 연결, 실패·취소·재시도·초안·권한·계정 경계, 변경에 영향을 받는 공통 소비자, 적합한 타입/린트/회귀 검사, 앱이면 가능한 화면/기기 확인. 필요한 항목만 수행하며 목적 없는 전체 검사를 반복하지 않는다.

- 납품에는 수정 파일·왜 필요한지·기준 대비 diff·검사 명령/원래 종료코드/로그 위치·실패와 한계·후속 결정을 포함한다. 시험 수치나 성공 상태를 지어내지 않는다.
- GPT 검수는 납품의 자체 합격을 반복하지 않고 실제 근거를 확인한다. P0/P1 미해결, 필수 기능 미연결, 필수 증거 부재가 있으면 관련 합격 판정을 보류한다. 미검증만으로 실제 결함이라 단정하지 않는다.
- 실기기·운영 서비스를 확인하지 않았다면 그대로 적는다. 시뮬레이터/Metro/로컬 네이티브 빌드 금지와 공유 운영 DB 규칙은 유지한다. 이 운영 체계는 금지된 시험을 허가하지 않는다.
- 승인 후 새 코드 변경이 생기면 해당 변경과 영향 범위를 다시 검수한다. `최종 합격`만으로 새 diff까지 승인된 것은 아니다.
