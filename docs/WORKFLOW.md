## 1. 판단과 책임

- 제품/설계 판단은 GPT가 우선한다. Claude는 사실과 대안을 제시할 수 있으나 충돌하는 방향을 임의로 구현하지 않는다. 사용자 지시와 플랫폼의 보안·권한 제한은 이 조직 체계보다 우선한다.
- GPT가 영상 열람·콘텐츠 검수·설명 대조·간단한 조사·운영 문서와 발주서를 직접 처리할 수 있다. 제품 코드의 복잡한 작성·수정은 Claude에 맡기는 것을 기본으로 한다. 사용자가 GPT 직접 수정을 지시하거나 전체 총괄이 승인 범위 안의 작은 수정을 맡길 때만 예외를 명시한다.
- Claude는 **구현 담당**이다. 구체적 발주가 오면 승인 범위 안에서 구현하고 필요한 검사를 수행한다. 이전 초기 안내의 '분석 전용'을 직업적/영구적 제한으로 사용하지 않는다. 다만 발주 자체가 분석 요청이면 그 건은 분석만 한다. 이 문서만으로 미발주 기능을 시작하지 않는다.
- 이미 별도로 승인받아 진행 중인 구현은 보존한다. 안전한 구분점에서 현재 범위·담당·증거를 연결하고 GPT 검수 단계로 넘긴다. 새 체계 적용을 이유로 중단·초기화·중복 구현하지 않는다.
- **부서 자율 원칙(2026-11-10 사용자 정정):** 승인된 작업 한 묶음의 설계·발주·검사는 부서 GPT가 결정하며 정상 구현 선택마다 총괄 재승인을 기다리지 않는다. 다만 **납품 검수 뒤에는 해당 부서 채팅에서 사용자에게 종합 보고하고, 다음 Claude 보완/추가 발주는 사용자 지시 후 진행**한다. 부서 자율은 사용자 확인 없는 무한 검수·재발주 권한이 아니다. 공통 파일은 실제 담당끼리 한 소유자로 조율하며 미해결 충돌·기존 허가 밖 DB/데이터·비용·중요 정책·배포만 필요한 결정권자에게 올린다.

### 계획 밖 추가 작업 배분 — 2026-11-10 사용자 확정

- 원래 계획에 없던 변수·추가 작업은 기존 서브 또는 해당 전문 세션에 배정한다. 총괄 채팅은 장시간의 개별 조사·설계·구현에 묶이지 않고 프로젝트 전체의 우선순위·충돌 조정·진행 확인·최종 검수를 유지한다.
- 총괄은 요구·현재 조사 결과·허용 범위·담당·납품 기준을 인계한다. 서브 GPT가 조사·상세 설계·영어 구현 지시문을 준비하고 대응 Claude가 실제 구현한다. 기존 전문 담당이 있으면 협업하며 중복 발주·동일 파일 동시 수정은 하지 않는다. 새 채팅은 사용자가 요청한 경우에만 만든다.
- 사용자 승인 안의 정상적인 작업은 위임 후 계속 진행하되, 제품 방향 변경·공통 계약/파일 충돌·비용·정책·배포 같은 결정은 총괄 또는 사용자에게 올린다. 총괄은 서브 결과를 확인하고 최종 발주·검수 판단을 유지한다. 진행 중 총괄에 새 요청이 들어와도 위임된 작업은 보존한다.
- 첫 적용 VP01: GPT 서브1이 설계·발주·파트 검수를 맡고 **기존 Claude 서브1**이 구현한다. 이전 운동영상 Claude는 변경/검사/claim 인계를 남기고 해제한 뒤 자문·회귀 협업을 한다. 새 담당은 인계와 실제 변경·해제를 확인한 뒤 이어받으며 병렬 편집하지 않는다. 사람의 순차 검수 기록은 보존하고 커밋·푸시·운영 배포 허가는 확대하지 않는다.

### Claude 모델·노력·Ultracode 선택 — 2026-11-10 사용자 확정

- **모든 GPT 세션**(총괄·서브·각 파트)은 승인된 자기 작업의 강도·고도화·실패 영향을 판단해 대응 Claude의 모델, 노력 단계, Ultracode 사용 여부를 정하고 실제 설정하도록 지시할 권한이 있다. 이 선택에 총괄 중간 승인은 필요하지 않다. 다만 **Fable(페이블)은 어떤 노력 단계든, Max(최대)는 어떤 모델이든 사용자에게 먼저 설명하고 명시적 허락을 받아야 한다.** 둘을 함께 쓰려면 둘 다 승인 범위에 들어 있어야 한다. 일반적인 작업 승인이나 과거 다른 작업의 승인을 대신 쓰지 않는다.

| 작업 분류 | 모델 선택 출발점 | 노력·Ultracode | 판단 예 |
|---|---|---|---|
| 가벼운 작업 | 현재 사용 가능한 적합한 Sonnet 또는 Opus | 낮음/중간, Ultracode 생략 가능 | 전달·문구·문서 정리, 영향이 명확하고 독립적인 소규모 수정 |
| 일반 제품 구현·실질적인 버그 수정 | Opus 5.5 등 현재 사용 가능한 강한 구현 모델 | **높음 + Ultracode 기본** | 실제 기능 작성, 여러 사용자 상태·공통 소비자·실패 복구가 있는 수정 |
| 고난도·큰 실패 영향 | Opus 계열의 강한 모델, 가벼운 모델로 축소 금지 | 높음 또는 매우 높음(xhigh) + Ultracode; 담당 GPT가 근거로 선택 | 동시성·권한·검증 격리·복합 재생 상태·여러 플랫폼 통합 |
| 예외 | Fable 또는 Max 사용 | **사용자 사전 허락 필수** | 필요한 이유·대상 작업·예상 이점/사용량 영향을 설명하고 승인 대기 |

- 모델과 노력은 별개로 판단한다. 무거운 일을 저성능 모델에 높은 노력만 주어 대신하지 않는다. 단순 전달/마지막 문서 갱신 때문에 고난도 제품 구현 전체를 낮은 설정으로 실행하지 않는다. 반대로 가벼운 작업에 불필요한 대규모 workflow·중복 에이전트를 쓰지 않는다. 품질·검증을 유지하는 범위에서 작업 단위로 선택·재평가한다.
- Ultracode는 모델 이름이나 Max의 다른 이름이 아닌 Claude Code의 별도 workflow 옵션이다. 설치 버전/화면에서 높음과 함께 지원되는지 확인한다. 공식 문서상 최근 버전은 노력과 독립적으로 켤 수 있다. CLI의 `--effort ultracode`는 xhigh도 함께 선택할 수 있으므로 높음+Ultracode를 의도했다면 실제 노력 값을 따로 확인한다. 미지원 옵션은 켰다고 주장하지 말고 담당 GPT에 차이를 알린다. 이 지시로 제3자 동명 플러그인을 설치하지 않는다.
- 발주에 `난도·판단 근거 / 요청 모델 / 노력 / Ultracode 켬·끔 / Fast mode 꺼짐 / Fable·Max 승인 여부`를 남긴다. Claude는 실제 적용 모델·노력·Ultracode·적용 시점과 확인 근거를 수신/납품에 기록한다. 프롬프트에 쓴 것, UI/지원되는 설정 도구로 적용한 것, 실제 다음 응답에서 적용된 것은 구분한다. 세션별 차이나 UI 도구 부재는 문서/outbox·앱 중계로 처리하며 전 세션이 바뀌었다고 추정하지 않는다.
- 하위 에이전트·workflow·재시도·자동 모델 대체도 같은 기준과 Fable/Max 승인 경계를 따른다. 자동 fallback으로 금지 선택을 쓰지 않도록 하고 실제로 강한 모델을 사용할 수 없으면 가벼운 모델로 조용히 대체하지 말고 해당 무거운 단계만 알린다. 설정 권한은 새로운 유료 크레딧 구매·요금제 변경·보안 권한 확대·제품 범위·배포 승인을 포함하지 않는다.
- 진행 중인 일을 무작정 중단하거나 초기화하지 않는다. 담당 GPT가 현재 난도를 판단하고 다음 안전한 구분점/다음 응답부터 맞는 설정으로 진행한다. 낮은 설정으로 이미 수행한 무거운 부분은 필요한 범위만 추가 검증하고 전체 작업을 이유 없이 다시 만들지 않는다. 기존 **모든 세션 Fast mode 꺼짐** 방침은 유지한다.
- 설정 의미 확인 출처(2026-11-10): [Claude Code 모델·노력·Ultracode 공식 문서](https://code.claude.com/docs/en/model-config), [Claude 앱 모델·노력 설정](https://support.claude.com/en/articles/8664678-change-the-model-effort-and-thinking-settings). 실제 선택지/지원 버전은 작업 당시 환경을 다시 확인한다.

## 3. 한 작업의 진행 순서

1. **GPT 설계:** 현재 코드·인계·다른 세션 변경 확인 → 사용자 문제·목표·범위·경계·합격 기준 작성. 큰 제품/정책 선택은 사용자에게 결정 요청한다.
2. **부서 발주 확정:** 작업 ID/판, GPT 설계·검수 담당, 대응 Claude 구현 담당, 기준 경로/ref, 허용 파일·제외 범위와 AC를 부서 GPT가 확정한다. 공통 파일은 실제 담당끼리 소유권/순서를 먼저 조율한다. 해결되지 않는 부서 간 충돌이나 기존 승인 밖 DB/데이터·정책·비용·릴리스 결정만 총괄/사용자에게 올린다.
3. **전달·수신:** 영어 구현 지시를 해당 Claude에 전달한다. 준비됨 / 전송됨 / Claude 수신·착수 / 납품됨을 구분한다. 연결이 없으면 문서 위치·질문을 남기고 메인에 중계 요청한다. 실제 전달되지 않았는데 착수로 표시하지 않는다.
4. **Claude 구현:** 현재 발주 판과 파일을 다시 읽고 담당 등록 → 필요한 코드를 구현 → 적합한 검사 → diff와 증거를 납품한다. 정상적인 범위 내 구현 선택은 자율 처리한다.
5. **파트 GPT 독립 검수·사용자 체크포인트:** 납품을 실제 diff/생산 연결/검사/가능한 사용자 흐름과 대조한다. 코드 존재·타입 통과만으로 합격을 선언하지 않는다. 검수를 마치면 해당 부서 채팅에서 사용자에게 종합 보고하고 다음 작업안을 묻는다. 부족한 항목도 먼저 이 보고에 모으며 곧바로 Claude에 재발주하지 않는다.
6. **사용자 방향 확인 → 필요한 최종 기술 검토:** 사용자가 다음 보완 범위/추가 기능/종료를 결정한다. 보완이면 그 승인 범위를 같은 ID의 다음 발주로 명시한다. 사용자가 채택한 최종본의 통합·릴리스 단계 등 총괄 기술 판정이 필요한 때에만 정확한 diff/ref·AC 증거·공통 영향·잔여 위험을 묶어 총괄에 올린다. 총괄을 사용자의 부서 결과 확인을 대신하는 일상 보고 수신자로 삼지 않는다. 사용자 방향 확인·파트 판정·총괄 기술 판정·배포 허가는 서로 다르다.
7. **릴리스:** 최종 합격한 정확한 변경만 기존 사용자 승인 범위에 따라 전체 총괄이 커밋·푸시·배포를 진행/지시한다. 푸시가 웹 배포/앱 OTA/네이티브 빌드/DB 적용을 일으키는지 확인한다. **최종 기술 승인은 운영 배포 허가와 별개**이며 기존 '올려줘/배포해' 규칙을 유지한다. **2026-11-10 사용자 명시:** 해당 기능을 “올려줘/배포해”라고 하면 원격 작업 브랜치 공유에서 끝내지 않고, 필요한 운영 준비·최종본 통합·운영 웹/앱 반영·배포 결과와 실제 사용 가능 여부 확인까지 총괄이 책임진다. 이미 받은 같은 배포 허락은 다시 묻지 않는다. 다만 미확정 정책·실제 처리 지역·계약 사실을 임의 확정하거나 동의/권한 차단을 우회하는 허가는 아니며, 외부 접근이나 사람의 결정이 꼭 필요한 경우 완료한 준비와 정확한 차단 조건만 묶어 알린다. 푸시·배포 성공·기능 사용 가능·실기기 확인을 구분한다.
8. **배포 후 확인:** 실제 커밋·배포 결과와 가능한 운영 경로를 확인하고, 코드 완료/검수 합격/배포 성공/실기기 확인을 각각 보고한다. 변경되면 해당 범위 재검수한다.

현재 우선순위는 영상비교다. 이 체계 설정 자체는 새 기능의 구현 발주나 운영 배포 요청이 아니다.

### 개발용 관리자 로그인 — 2026-11-13 사용자 지속 승인

- 사용자가 직접 제공한 개발용 관리자 계정으로 **싱커·덕아웃 내부의 필요한 로그인과 승인된 개발 확인**을 GPT·Claude가 직접 수행할 수 있다. 같은 로그인 권한을 반복해서 묻거나, 이미 제공된 자격정보가 현재 승인된 문맥에 있는데 사용자에게 다시 입력을 요구하지 않는다. 기존 로그인 세션을 우선 사용한다.
- 비밀번호·인증 쿠키·토큰은 저장소, 공유 문서, `.env`, 검사 로그나 보고에 기록하지 않는다. 실제 로그인 화면에서만 사용하고, 인계에는 계정 값 대신 승인 범위·로그인 성공 여부만 남긴다. 자격정보를 실제로 사용할 수 없는 환경이나 추가 인증이 필요한 경우에만 구체적인 장애를 알린다.
- 이 승인은 은행·이메일·Supabase·Vercel 등 다른 서비스의 로그인이나 계정/보안 설정 변경, 새 권한 획득, 미발주 DB·콘텐츠 변경·삭제·커밋·배포 허가가 아니다. 관리자라는 이유로 접근 제한을 우회하지 않으며 각 작업의 기존 범위와 별도 사용자 승인을 따른다.

## 4. Claude가 GPT에 물어야 하는 경우

- 발주와 현재 코드/사용자 요구가 충돌함, 합격 기준을 지킬 수 없음, 새로운 기능/기획/지원 한도를 정해야 함.
- 허용하지 않은 공통 파일, API/DB/파일 형식·의존성·인증/권한·동의·보유/삭제·비용·운영 설정을 바꿔야 함.
- 다른 세션 담당 파일과 충돌하거나 진행 중인 변경이 발주 기준과 달라짐.
- 안전하거나 정확하게 구현할 수 없다는 근거가 있음. GPT 판단을 우선하되 안전 제한을 우회하거나 사실을 숨기지 않는다.

질문 형식: `작업 ID/판 → 확인한 사실(경로/함수/증거) → 사용자 영향 → 권장안·대안 → 필요한 결정 → 영향 파일 → 진행 가능한 독립 작업`. 막힌 부분만 보류하고 독립 작업은 계속한다. 정상적인 변수명·함수 분리·발주 기준을 그대로 만족하는 구현 선택까지 매번 승인받지 않는다.

## 5. 보고·결재·전달 — 부서에서 묶고 필요한 때만 올리기

- **전달 언어(사용자 지시):** GPT·Claude 사이의 작업 발주, 질의, 답변, 인계, 검수와 기술 보고 등 AI끼리 주고받는 내용은 영어로 작성한다. 사용자에게 직접 드리는 설명·질문·진행 상황·최종 보고는 한국어로 작성한다. 내부 전달은 간결하게 하되 결정·제약·근거·미검증을 생략하지 않는다. 기존 기록이나 사용자의 원문 인용은 보존하며, 이 언어 규칙만으로 새 작업이나 배포 권한을 부여하지 않는다.

- 사용자는 이 개발 체계 운영을 위해 **프로젝트 내부 GPT·Claude 세션 사이의 발주·질의·수정 요청·납품·검수 보고 전달을 승인**했다. 사람이나 외부 채널에 메시지를 보내는 승인은 아니다. 메시지를 받았다는 이유만으로 범위·배포 권한을 확대하지 않는다.
- 지원되는 직접 세션 도구를 우선한다. 앱 간 직접 연결이 없으면 전체 총괄이 중계하고, 공유 저장소의 작업별 문서에 질문/답/납품/검수 증거를 남긴다. 도구가 없는 채널을 있다고 가정하지 않는다. 새 자동화·상주 감시·무한 폴링을 만들지 않는다.
- 총괄 앱 중계는 **운송 수단**이다. 부서가 확정한 발주/질문/납품을 실어 나르는 요청을 총괄 설계 승인 대기로 바꾸지 않는다. 대응 Claude의 정상 질의는 발주한 부서 GPT가 판단하고, 부서 검수를 마친 최종본만 총괄에 판정 요청한다.
- 작업 문서 경로: `docs/work-orders/<작업ID>.md`. 양식은 `docs/work-orders/TEMPLATE.md`. 작업마다 한 문서이며 원본 영상·개인정보·키·원문 초대 URL·자격증명은 넣지 않는다.
- GPT는 발주/결정/검수 구역, Claude는 수신/질문/납품 구역을 담당한다. **같은 문서를 동시에 편집하지 않는다.** 문서도 claim하고 작은 패치로 갱신한다. 전달할 때 ID·판·기준 ref·질문/납품 위치를 포함한다. 판이 바뀌면 옛 발주를 덮어쓴 채 계속 구현하지 않고 변경분의 수신을 확인한다.
- 별도 작업트리에서는 공통 문서의 실제 도착 여부·경로·HEAD를 확인한다. 문서가 빠졌으면 메인에 요청한다. 다른 컴퓨터에는 승인된 인계를 실제로 받은 뒤 적용한다.
- 현재 조직/도구 확인 외에 미발주 기능을 시작하지 않는다. 생성된 세션은 맡은 파트의 **구현 대기** 상태일 수 있으며 분석 전용과 다르다.

### 부서 검수 후 사용자 확인 — 2026-11-10 최신 지시

기본 흐름은 **사용자가 승인한 작업 묶음 → Claude 구현·자체 검사·납품 → 담당 GPT 독립 검수 → 같은 부서 채팅에서 사용자 종합 보고·질문 → 사용자 지시 후 다음 Claude 발주**다. 운동영상 서브를 포함한 모든 부서에 적용한다. 이 지시가 기존 “GPT가 부족하면 곧바로 보완 발주”, “최종본은 항상 총괄에게 먼저 보고”보다 우선한다.

- **한 차례 경계:** 이미 맡긴 구현과 납품 전 필요한 자체 수정/검사는 승인 범위 안에서 마친다. GPT가 납품을 검수한 뒤에는 `사용자 검토·다음 발주 대기`로 두고 추가 Claude 보완/확장/재검토 workflow를 자동 실행하지 않는다. 미완료·조건부·수정 필요도 솔직히 보고하고, 승인받기 전에 할 수 있는 현재 납품 검수부터 완료한다.
- **사용자에게 직접:** 총괄로 보고를 보내고 끝내지 말고 해당 GPT 부서 채팅에서 사람이 이해할 수 있는 종합 결과를 보여 준다. 문서 경로만 던지지 않는다. 총괄 중계가 발주/납품 운송에 필요해도 사용자의 방향 확인을 대신하지 않는다.
- **필수 보고 내용:** ① 이번에 무엇을 왜 고쳤고 실제 동작이 어떻게 달라지는지 ② 검수에서 확인한 정상/문제와 근거·미검증 ③ 필수 수정과 선택 개선을 구분한 보완안·이유·영향 ④ 사용자가 결정해야 할 구체적 질문·대안/권장 ⑤ 다음 Claude에 맡길 정확한 작업 범위와 예상 영향, 또는 여기서 종료해도 되는 상태인지. 필요한 설명은 충분히 하되 원문/ACK 이력은 반복하지 않는다.
- **실제 다음 발주 확인:** 보고 끝에서 다음 보완을 Claude에 맡길지, 제안 중 어느 범위로 진행할지 또는 종료/보류할지 묻는다. 모호한 “어떻게 할까요” 대신 검수 결과로 만든 구체적인 선택안을 제시한다. 응답 지연·과거의 포괄적 “진행해”·총괄의 전달 성공을 새 보완 승인으로 보지 않는다. 현재 보고의 다음 범위를 명확히 승인한 사용자 답변이나 그 범위의 사전 명시 위임이 있어야 한다.
- **무한 반복 차단:** 사용자 확인 전 새 R번호/새 판/새 에이전트 팀을 만들어 다음 수정에 들어가지 않는다. 같은 검사·반박 검토를 새 근거 없이 반복하지 않는다. 사용자가 승인한 후속 작업도 완료 조건·검사 범위·다음 사용자 체크포인트를 정해 한 묶음으로 수행한다. 기능 확장이나 임의의 완벽도 높이기를 다음 작업에 몰래 섞지 않는다.
- **기존 진행 작업:** 현재 승인되어 수행 중인 작업은 초기화/중단하지 않고 그 납품과 GPT 검수까지 마친 뒤 이 체크포인트를 적용한다. 이미 GPT 검수가 끝났다면 사용자 종합 보고를 우선하고 새 Claude 작업을 시작하지 않는다. 실제 위험의 확산 차단은 즉시 하되 제품 수정·배포 권한을 임의 확대하지 않는다.

### 보고·결재 등급 — 사용자 체크포인트와 함께 적용

목표는 보고 문장의 무조건적인 축약이 아니라 **불필요한 보고·전송·검토 자체를 없애는 것**이다. 부서는 판단과 보완을 종합해 결재 가능한 한 묶음으로 올린다. 아래 기준이 앞선 공지의 일률적인 “수신 회신·상태표 전송·총괄에 매번 알림”보다 우선한다. 문서상 정확한 상태 기록과 상위 채팅에 메시지를 보내는 것은 별개다.

| L0 · 부서 내부 처리 | 승인 범위 안 설계·구현 선택, 보통의 오류 수정·재시도, 파일 읽기·claim·수신, 정상 모델 설정, 변화 없는 대기 | 담당끼리 처리하고 필요한 결정/증거만 작업 문서에 모은다. 총괄 보고·사용자 알림·회신 요구 없음 |
| L1 · 파트 납품·담당 협의 | Claude가 검수 가능한 기능 묶음을 완성, 현재 발주 안 실질 질문, 실제 담당 간 파일/계약 조율 | Claude→담당 GPT/관련 담당끼리 처리한다. GPT 납품 검수 후에는 아래 사용자 체크포인트로 넘어가며 자동 재발주하지 않는다. 직접 채널이 없으면 필요한 운송만 요청 |
| L2 · 사용자 종합 보고·필요한 총괄 결재 | 부서 납품 검수 완료(합격/수정 필요 모두), 다음 보완·방향 선택, 승인 밖 범위·정책·비용, 미해결 부서 충돌·통합/릴리스 판단 | 부서 GPT가 사용자에게 해당 부서 채팅에서 한 묶음으로 보고·질문한다. 다음 Claude 작업은 사용자 지시 후 시작한다. 부서 간 충돌 조정이나 사용자 채택 최종본의 기술 판정이 필요한 경우만 총괄에 묶어 올린다 |
| L3 · 긴급 예외 | 실제 서비스 장애, 정보 노출·데이터 손상/유실·권한 우회·무승인 배포의 구체적 징후, 계속하면 피해가 커지는 잘못된 실행, 확정된 출시 차단 결함 | 확인된 사실과 추정을 구분해 즉시 필요한 담당/총괄에 보고한다. 영향 작업만 멈추거나 차단하고 독립적인 안전한 작업은 계속한다. 일괄 보고 시점을 기다리지 않는다 |

- 등급은 파일 수·검사 수·작업 시간으로 올리지 않는다. **다음 행동에 누구의 판단이 필요한지, 승인 범위를 넘는지, 지연하면 어떤 피해가 있는지**로 판단한다. 해결 가능한 일반 검사 실패·한 함수 버그는 L0/L1이며 그 자체로 총괄 보고 사유가 아니다. Fable/Max, DB·정책·배포 등 기존 사용자 허락이 필요한 선택은 계속 사전 허락을 받는다.
- 정상 흐름은 `부서 설계/발주 → Claude 기능 묶음 납품 → GPT 검수 → 사용자 종합 보고·다음 작업 선택`이다. 결함은 한 번의 검수에서 모아 사용자에게 제안하고, 다음 발주 허락을 받은 뒤 같은 ID의 수정 요청 한 묶음으로 보낸다. 통상적인 중간 구현·모델 설정·수신을 별도 결재로 만들지는 않는다. 긴급 위험은 즉시 필요한 담당에게 알린다.

### 결재 가능한 보고 묶음

작업 문서의 최신 보고 구역 하나를 기준으로 아래 중 관련 있는 항목을 작성한다. 짧게 보이려고 근거·위험·대안을 빼거나 정해진 글자 수에 맞추지 않는다. 판단에 필요한 설명은 충분히 쓰고, 반복 원문과 무관한 실행 이력만 덜어낸다.

1. **표지:** 작업 ID/판, 보고 등급·수신자, 기준/최종 ref 또는 정확한 미커밋 diff, 이번 요청(승인·선택·최종 검토 등).
2. **결과·부서 결정:** 사용자 문제가 어떻게 바뀌는지, 묶어서 확정한 주요 결정과 이유, 승인된 범위와 변경 경계.
3. **근거:** 부서가 직접 확인한 생산 연결·실패/복구·권한·공통 영향, 검사 명령/원래 종료코드와 재현·전체 로그 위치. Claude 자체 보고·GPT 확인·실기기/운영 미검증을 구분한다.
4. **쟁점·선택지:** 남은 위험과 영향, 대안/권장안 및 비용·일정 등 관련 차이, 부서에서 결정할 수 없는 이유. 중요한 실패는 경로만 던지지 말고 원인·재현·영향을 본문에 설명한다.
5. **결재 항목·후속:** 정확히 승인/결정할 대상, 배포 허가 유무, 필요한 다음 행동과 담당, 새 판단이 필요한 조건.

사용자에게는 해당 부서 채팅에서 결과·남은 문제·권장 보완·결정 질문·다음 작업 범위를 직접 설명하고 문서/근거를 연결한다. 내부 운송 채팅에는 목적·새 결론/요청·문서 위치와 판을 한 번 전달하며 여러 중계자가 전문을 계속 복사하지 않는다. 후속 보고는 이전 기준 대비 **실제 변경과 영향**을 설명하되 필요한 판단 근거는 생략하지 않는다. 문서 접근이 안 되거나 긴급 판단에 본문이 필요하면 필요한 전체 내용을 직접 전달한다.

### 전송·확인·검토의 낭비 방지

- **ACK 회신 사슬 금지:** “받음/전달함/확인함/대기 중”만으로 새 메시지·수신표·별도 outbox·추가 확인 요청을 만들지 않는다. 수신/실제 적용 증거는 다음 정상 납품·질의 또는 기존 문서 상태에 함께 남긴다. 소유권 인계·모호한 발주·전송 실패처럼 잘못 진행할 위험이 있을 때만 담당 간 확인을 요청한다. 보내기 성공을 수신·적용·합격으로 바꾸지는 않는다.
- **공지 한 번:** 영향을 받는 세션에 필요한 규칙만 1회 전달하고 회신을 요구하지 않는다. 현 작업의 안전한 구분점부터 적용하며 진행을 중단하거나 모든 세션을 돌며 읽음/설정 상태를 수집하지 않는다. 적용 불가·충돌·진짜 승인 필요 사항만 해당 담당이 알린다. 기존의 단순 공지 수신표 수집 요청도 이 기준으로 종료한다.
- **필요한 중계만:** 직접 채널을 우선하고 문서 경로/판/목적과 확정된 지시·질문을 모아 한 번 중계한다. 한 안건을 메인·서브·파트에 각각 중복 발주하지 않는다. 총괄은 단순 중계를 새 설계 심사로 만들지 않고 전송 확인만으로 사용자에게 계속 알리지 않는다. 전송 실패나 응답 부재가 실제 다음 작업을 막을 때만 조치한다.
- **변화 없으면 조용히:** 새 증거·결정·담당/범위 변경·결재 가능한 최종본이 없으면 재보고하지 않는다. 보고 자체에 대한 답장·그 답장의 수신 확인도 하지 않는다. 사용자에게는 실질 완료·의미 있는 변경/실패·필요한 결정 때 알리며, 사용자가 상태를 묻거나 실제 장시간 작업의 진행 안내가 필요한 경우는 설명한다.
- **폴링·대독 금지:** 상주 감시·새 자동화·변화 없는 세션/파일 반복 조회를 만들지 않는다. 시작/재개·실제 납품 알림·의존 작업 인계 때 필요한 문서/변경만 읽는다. 사용자가 완료 추적을 요청한 실제 진행 작업은 필요한 범위에서 확인한다. 도구 출력은 필요한 상태·오류·변경 부분만 보고 전체 원자료는 근거 경로로 보존한다.
- **검수는 역할별로 한 번:** Claude는 납품 전 자체 검사, 부서 GPT는 독립 검수 후 사용자에게 보고·다음 범위를 확인한다. 총괄은 필요한 최종 통합/출시 기술 판정을 하며 동일 시험을 관성적으로 전부 반복하지 않는다. 현재 검수의 새 실패·증거 부족·새 위험은 필요한 만큼 조사/확인하되 다음 Claude 보완 발주는 사용자 확인 전 시작하지 않는다. 토큰 절약을 이유로 검증을 생략하거나 미검증을 합격으로 올리지 않는다.
- **증거와 메시지 분리:** 상세 로그·재현·결정은 한 작업 문서와 증거 파일에 남기고 작은 상태 변화마다 전체 문서를 다시 쓰지 않는다. 자동 설정이 확인 불가하면 미확인으로 기록하고 실제 판단/작업에 필요한 때만 해결한다. 같은 도구 경로가 반복해서 실패하면 지원되는 대안/문서 경로를 택하고 무작정 UI 재시도·중복 메시지를 늘리지 않는다.

### Claude에서 GPT로 직접 보낼 수 없을 때 — 2026-11-10

- 현재 확인된 채널은 GPT 총괄의 Claude 앱 화면 입력·읽기와 Claude 사이의 내부 전달이다. Claude의 보내기 도구로 GPT에 직접 전송할 수 있다고 가정하지 않는다. 직접 채널이 없는 것은 문서 납품을 생략하거나 사용자에게 반복 복사·붙여넣기를 요구할 이유가 아니다.
- Claude는 `docs/work-orders/<작업ID>.md`의 자신의 수신·질의·납품 구역을 현재 내용 확인 → claim → 작은 패치 → release 순서로 기록한다. 작업 ID/판, 실제 checkout/기준 ref, 변경 파일과 정확한 diff, 검사 명령·원래 종료코드·로그 위치, 미검증, 필요한 판단, 기록 시점을 함께 적는다.
- 해당 문서를 GPT가 검수·편집 중이면 기존 기록과 검수 중인 기준 ref/제품 파일을 그대로 보존하고 `docs/work-orders/<작업ID>-claude-outbox.md`를 별도로 claim해 납품한다. 기존 outbox도 담당 중이면 덮어쓰지 말고 메인에 조율을 요청한다. outbox의 후속 기록은 판·기준을 구분해 남기고 GPT가 확인 중인 납품을 바꾸지 않는다. 제품 수정은 검수 대상 동결과 현재 발주 범위에 따라 조율한다.
- Claude는 납품 경로·작업 ID/판·기준 ref와 “GPT 수신 확인 필요”를 기존 Claude 서브/메인에 전달할 수 있다. 이것은 **Claude 내부 전달**이며 GPT 수신 확인이 아니다. 직접 채널이 없으면 총괄의 앱 화면 중계를 요청하고, 도착하지 않은 별도 checkout/다른 컴퓨터 문서는 승인된 인계로 전달한다.
- 대응 GPT는 시작·재개·실제 납품 중계 시 필요한 작업 문서와 outbox를 읽고 동시 편집을 피하며 자신의 검수 구역에 경로·판·ref·수신/검수 상태를 기록한다. 기존 문서를 편집할 수 없으면 다음 정상 납품/실질 질의에 함께 남기며 수신만 보고하는 별도 왕복은 만들지 않는다. 소유권·기준 혼동으로 작업이 위험할 때는 필요한 확인을 한다. 실제 읽은 뒤에만 “GPT 수신 확인”으로 표시하며 합격/최종 승인과 구분한다.
- 상태는 `작성됨 → Claude 내부 전달됨/총괄 중계 요청됨 → GPT 수신 확인 → 검수 중/보완 요청/판정`으로 구분한다. 확인 전에는 미수신·미확인이라고 보고한다. 자동 실시간 알림이나 상주 감시가 아니며 비공개 API·접근 권한 확대·상주 bridge·새 자동화·무한 폴링으로 보완하지 않는다. 운영 공지와 개별 구현 발주는 별개다.

- 승인 후 새 코드 변경이 생기면 해당 변경과 영향 범위를 다시 검수한다. `최종 합격`만으로 새 diff까지 승인된 것은 아니다.
